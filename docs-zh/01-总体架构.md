# 01 · 总体架构

## 仓库布局

```
bifrost/
├── core/            # 核心 Go 库 —— 引擎（请求调度、Provider、MCP、对象池）
├── framework/       # 持久化与公共服务（配置库、日志库、向量库、模型目录、流式聚合）
├── plugins/         # 11 个内置插件，各自独立 go.mod（治理、日志、缓存、遥测…）
├── transports/      # HTTP 网关（bifrost-http，唯一的 transport 实现）
├── ui/              # React Web 控制台（构建产物嵌入网关二进制）
├── cli/             # 终端 TUI（@maximhq/bifrost-cli，编码助手多路复用器）
├── cmd/             # e2eseed 等辅助二进制
├── npx/             # 3 个 npm 包装包（下载预编译二进制）
├── docs/            # Mintlify 官方英文文档（docs.getbifrost.ai）
├── tests/           # E2E（Playwright / Newman）、集成、治理、缓存等测试套件
├── helm-charts/     # 官方 Helm Chart
├── terraform/       # AWS/GCP/Azure/K8s Terraform 模块
├── recipes/         # make 一键部署配方（Fly.io、ECS、本地 K8s）
├── examples/        # 配置样例、Docker Compose、K8s 清单、插件/MCP 示例
├── scripts/         # LiteLLM 迁移 CLI、realtime 测试客户端
├── community/       # 社区维护的 MCP Library 目录数据
├── AGENTS.md        # 面向 AI 编码助手的代码库说明（很有参考价值）
└── Makefile         # 2800+ 行，所有构建/测试/部署命令入口
```

## Go 多模块工作区

仓库是 **multi-module Go workspace**，共 15+ 个独立 module：

```
core         github.com/maximhq/bifrost/core        ← 叶子模块，不依赖仓库内其他模块
framework    github.com/maximhq/bifrost/framework   ← 仅依赖 core
plugins/*    每个插件一个 module                      ← 依赖 core（多数还依赖 framework）
transports   github.com/maximhq/bifrost/transports  ← 组合根：依赖 core + framework + 9 个插件
cli          github.com/maximhq/bifrost/cli         ← 独立 TUI 应用
```

依赖方向严格单向：**core ← framework ← plugins ← transports**。

- `core` 只定义接口（如 `core/schemas/plugin.go`）并执行请求管道，从不 import framework/plugins。
- `transports/bifrost-http` 是组合根（composition root）：构造 framework 的各类 Store、实例化内置插件、注入 core。
- ⚠️ 本地开发**必须**执行 `make setup-workspace` 生成 `go.work`（被 gitignore，克隆后不存在）。没有它，跨模块引用会解析到**已发布的旧版本**，IDE 会大面积报错。详见 [10-开发指南.md](10-开发指南.md)。

## 一次请求的完整生命周期

以 `POST /v1/chat/completions` 为例（源自 AGENTS.md，与代码对应）：

```
客户端 HTTP 请求
  → fasthttp 传输层（解析、校验，约 2µs）
    → SDK 兼容层（OpenAI/Anthropic/Bedrock 格式 → Bifrost 内部格式）
      → 中间件链（lib.ChainMiddlewares，按路由应用：认证、CORS、追踪）
        → HTTPTransportPreHook（HTTP 级插件，可直接短路返回）
          → PreLLMHook 管道（治理鉴权、限流、缓存查询 —— 按注册顺序）
            → MCP 工具发现与注入（请求带 tool_choice 时）
              → Provider 队列（channel 隔离，每个 Provider 独立）
                → Worker 取出请求
                  → Key 加权随机选择（约 10ns）
                    → 调用上游 Provider API（fasthttp 连接池）
                      → 响应 / SSE 流
                → PostLLMHook 管道（与 Pre 相反的 LIFO 顺序）
              → 工具执行循环（响应含 tool_calls 时进入 MCP Agent 循环）
            → HTTPTransportPostHook（逆序）
          → 响应序列化
        → 返回客户端
```

## 核心设计原则

1. **Provider 隔离**：每个 Provider 有独立的 worker 池和队列（`chan *ChannelMessage`），一家挂了不影响其他家。
2. **Channel 异步而非锁**：请求路由靠 Go channel，`ProviderQueue` 用原子标志管理生命周期。
3. **无处不在的对象池**：`sync.Pool` 包装（`core/pool/`）覆盖消息、响应通道、流通道、插件管道、HTTP 对象、scanner 缓冲……以降低 GC 压力。这是 11µs 开销的关键。
4. **插件管道对称性**：Pre-hook 按注册顺序执行，Post-hook 严格**逆序（LIFO）**执行；执行过 Pre 的插件保证会执行对应的 Post。
5. **流式设计**：SSE chunk 经 `chan chan *schemas.BifrostStreamChunk` 流动；`framework/streaming/accumulator.go` 把分片聚合成完整响应供 Post-hook 使用。

## 三种使用形态

| 形态 | 入口 | 适用场景 |
|---|---|---|
| HTTP 网关 | `transports/bifrost-http`（Docker/npx/Helm 部署） | 多语言团队、需要控制台/治理/插件全家桶 |
| Go SDK | `go get github.com/maximhq/bifrost/core` | Go 应用直接内嵌，无 HTTP 开销 |
| 终端 TUI | `npx @maximhq/bifrost-cli` | 让 Claude Code 等编码助手统一走网关 |

## 开源版与企业版

开源仓库即全部 OSS 功能；企业版在其上叠加：SSO/SCIM、RBAC、审计日志、护栏（Guardrails）、集群模式、自适应负载均衡、熔断器，以及 `datadog` / `bigquery` / `pubsub` / `kafka` 四个闭源插件（`transports/bifrost-http/server/server.go` 中仅登记名字，OSS 加载器会静默跳过）。UI 中 `ui/app/_fallbacks/enterprise/` 是企业版页面的 OSS 占位。
