# 审计功能调研与需求建议

> 调研日期：2026-09-08。本文讨论产品功能：谁使用、记录什么、如何查看、能解决什么问题。依据官方产品文档和公开界面截图，未登录付费实例实测。“文档明确”不等于本次已经验证运行行为；“未确认”不等于没有。
>
> 之前的《02-审计竞品实现调研》和工作台方案 v1 是提前进入实现层的材料，不作为已确认需求。本文件先建立产品讨论依据，以下首版范围仍是建议，未经用户确认。

## 一、审计到底解决什么问题

审计是系统自动保存的管理历史。主要给平台管理员、安全人员和负责检查的人使用，不要求操作人手工填日志。

| 遇到的问题 | 用户需要从审计中得到的答案 |
|---|---|
| 昨天能用的模型今天不能用了 | 最近谁改了 provider、Key、模型权限或路由，具体怎么改的？ |
| 团队预算突然提高了 | 谁把哪个团队的预算从多少改成多少，什么时候改的？ |
| 怀疑凭据泄露 | 谁查看、导出或更换过相关凭据？是否有异常登录？ |
| 有人说“这个配置不是我改的” | 对应的操作账号、时间、来源和结果是什么？ |
| 需要向安全部门提供证据 | 能否筛出某段时间的相关记录并交付？是否完整保存？ |

上述是本产品候选场景，不是各竞品都已覆盖全部细节。审计记录只能说明所识别的账号；多人共用账号时，不能据此辨认背后的自然人。

## 二、竞品实际上提供了哪些用户功能

### 2.1 Portkey：组织范围的管理操作历史

**面向谁：** 组织所有者和管理员。**入口：** Admin Settings → Audit Logs。产品文档明确标为 Enterprise 功能。

记录工作区、API Key、模型目录、配置、提示词、护栏等资源的管理活动；动作不止增删改，还包含发布、导出、轮换、复制等。列表提供时间、操作人、工作区、动作、资源、结果状态和来源。可按人、工作区、资源、动作、时间及来源筛选；文档说明长期保留与自定义保留策略。[官方功能说明](https://portkey.ai/docs/product/enterprise-offering/audit-logs)

**用户价值：** 从一个统一入口追查各工作区发生过的管理操作。官方 API 文档也提供组织、用户、资源、动作、结果等查询维度；API 读取仅允许带相应权限的 Admin Key，Workspace Key 不能读取。[查询说明](https://portkey.ai/docs/api-reference/admin-api/control-plane/audit-logs/list-audit-logs)、[访问权限说明](https://portkey.ai/docs/help-center/you-do-not-have-enough-permissions)

**未确认：** 所有操作是否都有字段前后值；审计页面是否提供直接下载文件按钮。记录“导出动作”不等于“能导出审计记录”，不把普通请求日志导出功能算作审计导出。

### 2.2 LiteLLM：围绕 Key、团队、用户和模型追查变更

**面向谁：** Proxy Admin。**入口：** Logs → Audit Logs。官方明确要求 Enterprise license。

官方描述覆盖 Key、团队、用户、模型的创建、更新、删除和重新生成。用户可看到操作人、对象与时间；文档用团队预算变更举例，记录旧值和更新值，同时说明旧值可以为空，不能推断每个事件都有完整差异。还支持将审计记录导出到外部 S3，并与普通调用日志分开保存。[官方审计功能说明](https://docs.litellm.ai/docs/proxy/multiple_admins)

**用户价值：** 删除了哪把 Key、谁调整了团队设置，有记录可追查；审计资料可以留在企业自己的存储中。官方试用指导明确给出“删除虚拟 Key，再到审计标签查看”的验收场景。[企业试用指导](https://docs.litellm.ai/docs/learn/enterprise_quickstart)

**未确认：** 登录失败是否包含在该页、默认保留期、独立只读审计员权限，以及界面是否提供一键 CSV 下载。本次不从代码推导完整产品承诺。

### 2.3 Bifrost 企业版：覆盖范围更广的安全与管理历史

官方将事件分为认证、授权、配置变更、数据访问与安全事件；示例包括登录、预算调整、provider Key 更新、敏感配置访问及数据导出。提供按人、动作、资源、时间检索，声明支持保留期、导出、归档和完整性验证。[官方审计文档](https://docs.getbifrost.ai/enterprise/audit-logs)

**用户价值：** 同时服务管理追责与安全调查。它是我们当前 OSS 之外的上游企业版功能参照。

**注意范围：** 护栏命中、异常行为检测等还依赖相应安全功能。不能因为审计页列出这些事件，就把内容检测、风险识别一起算进基础审计开发。文档对不可篡改与合规的描述仅作厂商声明，本次未实测；有审计功能也不能自动证明通过认证。

**未确认：** 具体审计角色权限矩阵、全部操作的字段差异展示、每类事件与商业套餐的逐项对应。

### 2.4 JumpServer：最直观的“操作记录 → 变更详情”参考

它不是 AI 网关，但管理员审计界面很适合参考。官方入口为审计台 → 日志审计 → 操作日志，文档明确审计员可以查看详细变更。[官方操作日志说明](https://docs.jumpserver.org/zh/v4/manual/admin/audit/session_audit/log_audit/operation_logs/)

本次实际查看了文档中的两张截图：列表有用户、资源、来源地址、日期、动作、资源类型，以及搜索和日期范围；点击“查看”弹窗后，按“变更字段 / 变更前 / 变更后”三列展示。侧栏把登录日志、改密日志和操作日志分开。

**用户价值：** 排查时先定位哪一次操作，再阅读具体差异；只做检查的人有专门的审计入口。

**未确认：** 截图中的下载图标具体支持何种文件格式；该手册没有逐项说明社区版与企业版差异。本项目有公开源码，但不因此把截图中全部能力都判为社区版免费可用。

## 三、对照后的产品结论

| 用户能力 | 调研依据 | 对我们的启发 |
|---|---|---|
| 自动记录谁操作了什么 | Portkey、LiteLLM、Bifrost 文档 | 基础目标，不只是给开发者看的技术日志 |
| 记录关键配置的变更前后值 | LiteLLM 预算示例、JumpServer 详情截图 | 预算、权限、路由等要让人看懂改动 |
| 按人、对象、时间查找 | Portkey、Bifrost 文档，JumpServer 列表 | 用户需要查某件事，而不是浏览海量流水 |
| 区分登录与管理操作 | Bifrost 事件分类、JumpServer 侧栏 | 可用分类/标签组织，不必首版就做多个独立系统 |
| 敏感读取也留痕 | Bifrost 数据访问类别；Portkey 的导出动作 | 不能只记增删改；凭据查看、导出值得单独评估 |
| 谁能看审计 | Portkey 所有者/管理员，JumpServer 审计员 | 能查历史不必拥有修改业务配置的权限 |
| 对外提供记录与长期保存 | LiteLLM S3、Bifrost 导出归档、Portkey 保留策略 | 安全部门需要可交付资料，保留期限要产品明确 |

以上是不同竞品功能的归纳，不表示所有产品都拥有表中每一项。按团队“筛选”也不等于团队间“权限隔离”。

### 免费与企业版边界

| 产品 | 本次可以确认的边界 |
|---|---|
| Portkey | 审计文档明确为 Enterprise 功能 |
| LiteLLM | 审计文档明确要求 Enterprise license；试用不等于社区版免费 |
| Bifrost | 上游企业审计功能；本仓 OSS 页面是占位，不能当作已有实现 |

## 四、建议我们做什么：先定义用户能完成的事

以下是结合网关场景提出的建议，不是竞品事实，也不是已经批准的排期。

### 4.1 首版候选：管理变更记录 + 登录与敏感操作记录

| 需求 | 应当覆盖的业务动作 | 用户看见的结果 |
|---|---|---|
| 厂商和 Key 历史 | 新增、修改、删除、启停、更换凭据 | 哪个厂商/Key 被怎样调整，谁操作，是否成功；凭据只显示“已更换” |
| VK 与授权历史 | 创建、禁用、删除，允许模型/provider 范围调整 | 哪把 VK 的权限从什么变成什么 |
| 预算和限流历史 | 金额、周期、请求数/token 限额调整 | 归属对象和前后值，便于解释费用或访问变化 |
| 路由与系统配置历史 | 目标模型、规则、影响访问的关键设置调整 | 变更摘要与可读详情 |
| 登录与访问记录 | 登录成功/失败、退出、无权操作 | 账号或未验证身份、时间、来源、结果 |
| 敏感操作记录 | 查看/导出真实凭据，导出敏感记录 | 谁访问了什么；不把被查看的秘密再次写进审计 |

账号、角色和组织变更的审计应随多用户功能一起接入。尚不存在的功能不为了凑事件清单而额外建设。

### 4.2 首版页面需要什么

**列表：** 时间、操作人、操作类别、目标对象、变更摘要、结果、来源。默认最近操作在前。

**查找：** 时间范围、操作人、对象类型、对象名称/标识、动作、成功/失败；有团队归属时提供团队筛选。

**详情：** 操作基本信息与变更字段，非敏感内容展示前后值；失败操作展示可读原因。缺少旧值时明确“未记录”，不能把它显示为空值。

**交付记录：** 建议提供按当前筛选条件导出的基础能力，便于发给安全人员或同事；大规模归档后续再扩展。格式、权限与最大范围待产品确认。

**权限与保留：** 普通调用方不默认看到全部审计；管理员与后续只读审计角色分开。记录不可在页面任意编辑，删除和自动清理规则明确；保存天数待客户要求确定，不凭空设定。

### 4.3 用一个示例检验需求是否清楚

以下是我们期望的示例，不是竞品实际截图或本系统已有记录：

| 时间 | 操作人 | 对象 | 动作 | 变更摘要 | 结果 |
|---|---|---|---|---|---|
| 09-08 14:32 | 张三 | 研发团队 | 修改预算 | 月预算 100 元 → 1,000 元 | 成功 |
| 09-08 14:40 | 李四 | 生产环境 Key | 更换凭据 | 凭据已更换，内容不展示 | 成功 |
| 09-08 14:45 | 未验证身份 | 管理控制台 | 登录 | 身份验证失败 | 失败 |

预算金额只是产品示例；实际币种沿用当前产品能力，不把人民币功能偷偷并入审计。

看完第一行，用户应该能回答“是谁把预算提高了”，而不是只知道有人调用了一个接口。人员归因的细度也受账号体系限制：首期单管理员只能记录共享账号，个人追责依赖后续多用户。

### 4.4 后续能力，按真实场景再决定

- 异常事件提醒：连续登录失败、批量删除、频繁凭据访问。
- 更长期的外部归档、对接企业安全平台。
- 记录完整性验证与更强的防删除/防修改保障。
- 跨团队、跨组织的审计权限与调查流程。
- 护栏事件、内容违规复核：依赖内容安全模块，另行定义。

审批、配置回滚、自动修复不是审计记录本身。需要时单独列需求，不把“能看历史”误写为“能恢复配置”。

## 五、下一次讨论应确认的范围

先确认管理变更、登录事件和敏感读取三类是否都属于首版；再确认关键对象的覆盖清单、详情深度、基础导出与保留要求。确认后才重写需求与开发方案，当前不承诺实现方式和工期。

产品调查的核心依据是上面的官方文档与界面，不因某个实现方便就删掉用户真正需要的功能，也不因某家企业版有高级能力就把它全部加入首版。
