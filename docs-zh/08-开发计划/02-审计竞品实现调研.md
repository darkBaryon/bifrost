# 管理操作审计：竞品开源实现调研

> 调研日期：2026-09-08。只读公开仓库源码，未运行竞品实例或测试。以下链接固定到本次抓取的 commit，描述的是这些快照中的实现，不代表所有历史版本。重点是管理操作审计，区别于 LLM 请求日志、费用日志和会话录像。
>
> 结论：优先参考 New API 的“中间件兜底 + 业务显式事件”，用 LiteLLM 对照事件模型与导出，用 JumpServer 理解字段差异；Open WebUI 适合作为 HTTP 采集对照。代码公开不等于整套功能都按宽松开源协议提供。

## 1. 对比与阅读优先级

| 项目 | 与本项目关系 | 已读到的采集模式 | 存储 / 结果 | 对我们的价值 |
|---|---|---|---|---|
| New API | 直接竞品，Go + Gin + GORM | 管理鉴权链中的通用兜底，加 handler 显式事件；去重标记 | 独立 audit_logs 表；HTTP 状态 + 可选业务 success；失败写库只记错误 | 最接近 B1，先读 |
| LiteLLM | 直接竞品，Python | 业务端点调用统一记录函数，提供 before_value / updated_values | 数据库 + 外部回调；premium gate；捕获写入异常 | 对照模型和许可边界，不当成 OSS 免费审计方案 |
| Open WebUI | 相邻 AI 应用平台 | ASGI 中间件，按配置捕获元数据或请求响应 | Loguru 结构化日志；本次模块未提供审计列表 API | 理解 HTTP 层采集与正文风险 |
| JumpServer | 非 AI 网关，企业管理审计参考 | Django pre/post save/delete、m2m 信号，计算差异 | DB/ES 存储适配、字段 diff、组织范围、保留清理 | 理解旧值/新值所需的深层接入 |

许可证按仓库文件说明：New API 为 AGPLv3，JumpServer 为 GPLv3；LiteLLM enterprise 目录采用商业许可，目录外按根许可为 MIT；Open WebUI 为带额外品牌条款的项目许可。这里研究设计，不复制实现进 Bifrost。具体路径见各节许可链接。

## 2. New API：最值得先读的直接竞品

源码入口：[审计中间件](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/middleware/audit.go)、[鉴权接线](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/middleware/auth.go)、[显式事件辅助函数](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/controller/audit.go)。

**采集链路。** 管理员/root 认证通过后，包装响应 writer，再执行 handler，最后尝试补通用事件。只对写方法启用一般管理兜底；方法加路由模板映射稳定 action，未登记的管理写路由使用 generic。身份来自认证后的 context。它的管理兜底位于成功认证之后，不能推导为覆盖所有匿名拒绝；access-token 另有更外层的采集路径。

**业务语义。** handler 能调用 recordManageAudit，随后设置 ContextKeyAuditLogged，通用中间件发现标记后不重复写。渠道更新在 Update 成功后比较选定字段，记录 changed_fields；Key 只表示变更，不记录其内容。这是“哪些字段变了”，不是完整 before/after 快照。

具体样例：[渠道更新与密钥查看](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/controller/channel.go)；事件最终写入：[RecordOperationAuditLog](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/model/log.go)。显式辅助路径默认成功，因而调用时点属于契约；不能在任意位置调用就认为能自动判定业务结果。

**结果判断。** writer 最多暂存 64 KiB 响应，优先看 HTTP 错误和 JSON success；一般路径解析失败时退回 HTTP 状态。TokenOperationAudit 对缓冲截断另有 handler 成功标记兜底。不是所有路径都能统一避免 HTTP 200 业务失败的误判。Bifrost 不宜照搬响应正文缓存，应优先使用协议明确的状态与显式结果。

**数据与失败。** [AuditLog / RecordAuditLog / GetAuditLogs](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/model/audit_log.go) 单独保存事件 ID、操作者角色快照、action、认证方式、路由、结果和关联 ID；TokenRef 为凭据指纹。写入是直接数据库 Create，失败打印错误，不向业务调用者返回错误；因此没有业务与审计的原子持久化保证。其日志表刻意独立于 usage 清理/TTL。查询按角色过滤，并对返回扩展元数据分级裁剪；这比单纯隐藏页面更有参考价值。

**验证可借鉴。** [审计测试](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/controller/access_token_audit_test.go) 包含角色变化后历史角色快照、隔离权限、数据库矩阵、独立日志库和故障行为等用例。本次只读测试，未执行。[许可证](https://github.com/QuantumNous/new-api/blob/71c1fd7caad738db4d13aabbf28eeadb293d0cfe/LICENSE)。

## 3. LiteLLM：业务层事件丰富，但审计存在企业限制

源码入口：[统一事件构造、写库与回调](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/management_helpers/audit_logs.py)。

事件包含 changed_by、changed_by_api_key、action、table_name、object_id、before_value、updated_values。调用方负责提供变更前后的值，记录器本身不通过 HTTP 自动推导。changed-by header 只有在认证身份的 metadata/team_metadata 明确允许后才优先采用，否则回到认证用户 ID 或管理员名。

外部回调通过异步任务分发，支持单独的 S3 审计参数；数据库写失败捕获并记录错误。开启 store_audit_logs 并不等于绕过 enterprise 限制：实际 create_audit_log_for_update 中仍有 premium_user 判断。这条路径不能提供强持久化保证。

**必须注意调用时点。** [Key 管理端点](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/management_endpoints/key_management_endpoints.py) 的 block-key 样例在数据库 update 之前创建异步审计任务，记录 action=blocked 与旧记录。因此本次看到的事件不能自动等同于“修改已成功提交”；这是静态调用顺序结论，未进行故障注入。

**查询与许可。** [审计分页查询](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/enterprise/litellm_enterprise/proxy/audit_logging_endpoints.py) 支持操作人、对象、动作、时间等筛选，部分 JSON 条件仅 PostgreSQL 支持。该文件位于 enterprise 目录：[根许可证](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/LICENSE) 明确目录外 MIT、目录内另行许可；[企业许可证](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/enterprise/LICENSE.md) 对生产使用设企业授权要求。公开可读，但不能把这部分当 MIT 代码复制。

## 4. Open WebUI：通用 HTTP 审计不是字段变更审计

核心实现集中在 [audit.py](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/backend/open_webui/utils/audit.py)。

它提供 NONE、METADATA、REQUEST、REQUEST_RESPONSE 四档，默认审计方法为 POST/PUT/PATCH/DELETE，可选 GET，支持路径包含/排除和正文大小上限。请求结束在 finally 中写结构化日志；优先复用 request.state.user，必要时再走用户解析，解析失败可记录无用户。

这套采集记录的是 HTTP 请求响应，而不是数据库 old/new。当前代码只在 REQUEST_RESPONSE 分支捕获响应状态，所以不能假定低档位也有结果状态。正文处理只看到了 password 的正则遮罩，同时会记录完整 request URI；不适合直接用来保存可能含 API Key、令牌和查询串的网关管理请求。

写日志异常被捕获后报告。这个模块没有数据库审计模型/查询页面，也没有强持久性协议。本次没有追查所有日志 sink，不对部署后的日志交付可靠性下结论。

许可见 [项目许可证](https://github.com/open-webui/open-webui/blob/0a7c15832fb30b1903753e83f81dc7d27e5b0944/LICENSE)，带额外品牌限制，不能笼统称为无附加条件的 BSD/MIT。官方配置背景见[安全加固文档](https://docs.openwebui.com/getting-started/advanced-topics/hardening/)。

## 5. JumpServer：字段差异来自 ORM 生命周期

源码入口：[模型信号采集](https://github.com/jumpserver/jumpserver/blob/cc7f8d8f8c07af39df804f25e4774d9dc937eed6/apps/audits/signal_handlers/operate_log.py)、[身份、差异计算和存储分发](https://github.com/jumpserver/jumpserver/blob/cc7f8d8f8c07af39df804f25e4774d9dc937eed6/apps/audits/handler.py)。

保存/删除前查询旧对象并暂存；保存/删除后计算 before/after；另外处理多对多关系。只对登记模型和满足用户条件的操作采集，跳过部分模型、服务账号和内部更新。所以这不是“给所有请求包个中间件就有完整差异”。

操作处理器要求已认证用户，携带组织 ID、资源标识和远端地址；按字段名规则处理敏感值。当前旧值缓存按实例 ID 命名、TTL 为 3 秒，后续读取计算差异；由此推断并发同对象操作或长事务值得重点测试，不能将该方案直接等同于事务提交证据。

它按存储可用性尝试默认后端回退，save 异常捕获并记录。代码中有 transaction.atomic，但 ES、缓存和业务事务的关系并不因此自动变成分布式原子操作。

**存储与保留。** [OperateLog 模型](https://github.com/jumpserver/jumpserver/blob/cc7f8d8f8c07af39df804f25e4774d9dc937eed6/apps/audits/models.py) 保存组织范围和 diff；[数据库存储适配](https://github.com/jumpserver/jumpserver/blob/cc7f8d8f8c07af39df804f25e4774d9dc937eed6/apps/audits/backends/db.py) 把 before/after 合并成字段差异；[定时清理](https://github.com/jumpserver/jumpserver/blob/cc7f8d8f8c07af39df804f25e4774d9dc937eed6/apps/audits/tasks.py) 按 OPERATE_LOG_KEEP_DAYS 删除过期操作记录。许可见 [GPLv3](https://github.com/jumpserver/jumpserver/blob/cc7f8d8f8c07af39df804f25e4774d9dc937eed6/LICENSE)。

## 6. 对 Bifrost 审计方案的调整建议

### 6.1 采用两种事件来源，统一写入

```text
管理请求 → 现有认证与业务处理
                  │
                  ├─ 有明确业务事件：记录资源、动作、安全的变更信息
                  └─ 无业务事件：生成受控的 HTTP 操作记录
                                  ↓
                       统一事件模型、持久化、查询、页面
```

借鉴 New API 的结构，但我们应让业务层“补充事件”，由统一出口最终写一次，减少两处写库和去重状态耦合。补充标记只表示语义信息已提供，不表示已经可靠落库。

建议事件增加 detail_level/source，区分 http_operation、changed_fields、field_diff。只有能证明的层级才展示对应文案。数据库预留扩展字段，不自动采集任意 before/after。

### 6.2 先做有价值的关键动作，不承诺一开始全量 diff

- provider/key 新增、删除、启停与修改；敏感凭据最多记录“已更换”。
- VK 的创建、禁用、权限范围修改，以及预算/限流调整。
- 补上“查看或导出密钥”这类敏感读取；不能把所有 GET 都排除后就认为覆盖完整管理审计。具体 Bifrost 路由仍需核实。
- 登录成功/失败、退出、认证拒绝走安全事件，不能完全依赖位于认证之后的兜底路径。

对于预算等非敏感值，有可靠业务接入点时可以记录 old/new；没有时只记录动作和已确认的字段名。竞品证明了实现形式，不证明 Bifrost 包壳已经有相同扩展点。

### 6.3 有两点继续保留原建议

**安全元数据允许清单。** New API 在渠道更新中不保存 Key 内容，适合学习；Open WebUI 的 password 正则不足以覆盖网关凭据，不照搬。客户端 IP、账号快照和导出字段都需明确可信来源。

**明确写入失败契约。** 本次核对的 New API、LiteLLM 和 Open WebUI 路径均捕获或仅报告审计写入错误，未看到与业务操作共同保证原子提交的协议；JumpServer 有存储回退，但不能据此承诺跨后端原子性。这支持“基础版可以选择业务继续、审计异常可见”的可行性，不代表用户已接受丢事件风险。

### 6.4 Bifrost 独有的接入限制仍需解决

New API 可以直接改 handler；JumpServer 控制 ORM 信号；LiteLLM 可以在业务端点显式调用。我们沿用上游 handler，ServerCallbacks 又不可注入，因此不能承诺零上游改动就获得相同语义深度。

下一步选“修改一个 Key”和“调整一个预算”核对完整写入链，判断是否存在可用业务接口/服务装饰入口。若必须改上游，提供最小扩展点方案和维护成本，再决策。仅在请求前后重新查询数据库会混入并发变化，不能假装是可靠的替代。

本调研不自动修改 v1 的范围或通过状态，不开始业务实现。正式 v2 应把事件来源、敏感读取和统一写入纳入设计，再经过复核。
