# 11 - 程序入口与依赖注入(DI)

> 回答两个问题:这个项目的入口在哪?为什么没有 DI 框架、依赖注入在哪里完成?

## 一、所有 main() 入口清单

本仓库**不遵循** Go 社区常见的"所有二进制放 `cmd/<name>/`"布局。全部 8 个正式入口:

| 入口 | 二进制 | 作用 |
|---|---|---|
| `transports/bifrost-http/main.go` | **bifrost-http(主网关)** | 就是 `npx @maximhq/bifrost` 跑的那个,API + 控制台 |
| `cli/main.go` | bifrost-cli | 终端 TUI(编码代理启动器) |
| `cmd/e2eseed/main.go` | e2eseed | 给 OSS API e2e 测试灌种子数据 |
| `tests/cmd/{seed,seedvks,e2eseed}/` | 测试工具 ×3 | 各类测试数据填充 |
| `tests/e2e/api/webhook-receiver/` | webhook-receiver | e2e 测试的回调接收器 |
| `tests/scripts/{1millogs,migration-checker}/` | 压测/迁移工具 | 百万日志压测、迁移校验 |
| `scripts/bifrost-migration-cli/` | migration-cli | LiteLLM → Bifrost 迁移 |
| `scripts/realtime-test/` | realtime-test | WebSocket 实时接口练习客户端 |

(`examples/` 下还有十几个演示用 MCP server/插件模板,不算正式产品。)

**为什么主入口不在 `cmd/` 而在 `transports/` 里?** 两个硬约束:

1. `main.go:73` 的 `//go:embed all:ui` —— UI 静态产物必须和 main 包同目录,而 UI 拷贝目标就是 `transports/bifrost-http/ui/`;
2. 多模块仓库的边界 —— 网关代码全在 `transports` 这个 Go module 里,入口放外面就要跨模块 embed,不可行。

## 二、启动链:薄 main + 胖 Bootstrap

`transports/bifrost-http/main.go` 只有 176 行,只做四件事:

```
解析 flags → 打 banner → server.Bootstrap(ctx)   ← 全部装配在这
                        → server.Start()          ← 阻塞至 SIGINT/SIGTERM
```

真正的装配都在 `server/server.go` 的 `Bootstrap()`(2355 行起),**顺序即依赖关系**:

| 步骤 | 代码位置(server.go) | 产出 | 依赖 |
|---|---|---|---|
| 1. 加载配置 | `lib.LoadConfig` :2365 | `s.Config`(含 ConfigStore/LogsStore/VectorStore/ModelCatalog/KVStore) | app-dir、config.json、环境变量 |
| 2. WebSocket + 通知服务 | :2374-2378 | EventBroadcaster、NotificationPublisher | Config |
| 3. 动态插件加载器 | :2389 | SharedObjectPluginLoader(含 SSRF 白名单校验) | ServerConfig |
| 4. 日志清理/异步任务清理协程 | :2415, :2424 | LogsCleaner、AsyncJobCleaner | LogsStore |
| 5. **加载全部插件** | `s.LoadPlugins` :2428 | 内置 8 插件 + 动态 .so 插件实例 | 各类 Store(见下) |
| 6. Webhook 投递器 | :2435 | WebhookDispatcher | ConfigStore + LogsStore |
| 7. 异步任务执行器 | :2450 | AsyncJobExecutor | LogsStore + governance 插件 |
| 8. **核心引擎初始化** | `bifrost.Init` :2469 | `s.Client`(worker 池、Provider 队列、MCP) | Account + 插件列表 + MCPConfig |
| 9. 中间件 | :2509(CORS)、:2605-2609(Tracing) | 中间件链 | Config、ModelCatalog |
| 10. 注册路由 | `RegisterAPIRoutes` :2021 起 | 27 个 Handler,全部构造注入 | Client + Config + 各服务 |
| 11. 启动监听 | `Start` :2714 | fasthttp 服务器 | 以上全部 |

内置插件的固定装配顺序在 `server/plugins.go`:telemetry(1) → prompts(2) → logging(3) → governance(4) → otel(5) → semanticcache(6) → compat(7) → maxim(8),modelcatalogresolver 以 `order = MaxInt` 永远垫底(最后兜底解析模型归属)。每个插件的 `Init(...)` 显式接收它需要的 store:如 `governance.Init(ctx, config, logger, configStore, logsStore, pricingManager, ...)`。

## 三、DI 在哪里做?——手工组合根(Composition Root)

**本项目没有 wire/fx/dig 等 DI 框架,依赖注入 = `Bootstrap()` 这个函数本身。**这是 Go 生态的主流做法,有个正式名字叫组合根模式:所有依赖在程序入口处、按拓扑顺序、手工 `New` 出来并层层传入。

项目里的三个 DI 要素:

**1. 依赖倒置——接口定义在最底层的 `core/schemas`**

`Account`、`Logger`、`Plugin`(五种 Hook 接口)、`Tracer`、`MCPHeadersProvider`……全部定义在 core/schemas 中。core 只认接口,永远不 import framework/plugins/transports——这就是依赖方向 `core ← framework ← plugins ← transports` 能成立的原因。

**2. 构造函数注入——没有任何全局魔法**

```go
// handlers 层:依赖全部从参数进来
inferenceHandler := handlers.NewInferenceHandler(s.Client, s.Config)
governanceHandler := handlers.NewGovernanceHandler(callbacks, s.Config.ConfigStore, govLogManager, ...)

// 核心引擎:一个配置结构体注入所有依赖
s.Client, err = bifrost.Init(ctx, schemas.BifrostConfig{
    Account:    account,              // 接口,由 lib.NewBaseAccount(s.Config) 实现
    LLMPlugins: s.Config.GetLoadedLLMPlugins(),
    MCPConfig:  mcpConfig,
    Logger:     logger,
    KVStore:    s.Config.KVStore,
    ...
})
```

**3. 聚合结构体当"容器"——`lib.Config` 与 `schemas.BifrostConfig`**

没有反射容器,就用普通 struct 兜住一组依赖往下传。`lib.Config` 是 transport 层的总容器(所有 store、插件实例、特性开关都挂它上面),`schemas.BifrostConfig` 是 core 的注入口。想找"某个依赖从哪来",顺着 struct 字段一路 Cmd+Click 就能追到构造点——这正是手工 DI 的最大优点:**装配路径是可导航的普通代码**。

## 四、为什么不用 DI 框架?

| DI 框架的适用场景 | Bifrost 的实际情况 |
|---|---|
| 依赖图庞大、动态、随环境变化 | 依赖图**静态且浅**(4 层),启动时一次装好,运行期不变 |
| 需要复杂生命周期管理(懒加载、作用域) | 全部单例,随进程生灭;唯一的"作用域"是请求对象,用 sync.Pool 解决 |
| 多团队解耦,模块间互不知晓 | 装配集中在一个 2800 行的 server.go,单团队完全掌控 |
| 愿意接受反射/代码生成的调试成本 | Go 文化:显式 > 魔法,栈追踪必须可读 |

一句话:**当组合根是一个能从头读到尾的函数时,DI 框架只会把"可读的顺序"变成"不可读的注解"。**Kubernetes、Prometheus、etcd 也都是这么做的。

SDK 模式下(不经 HTTP 网关、直接 `go get core`),**用户自己就是组合根**:实现 `schemas.Account` 接口,调 `bifrost.Init` 注入——和 Bootstrap 做的事一模一样,只是换你来写。

## 五、迷你样本:cmd/e2eseed(73 行学完该模式)

```go
opts := seed.DefaultOptions()          // 默认值
fs.StringVar(&opts.ConfigDSN, ...)     // flags 覆盖
configDB, _ := seed.OpenDB(opts.ConfigDialect, opts.ConfigDSN)  // 构造依赖①
logsDB, _ := seed.OpenDB(opts.LogsDialect, opts.LogsDSN)        // 构造依赖②
seed.SeedBase(ctx, configDB, logsDB, opts)                      // 注入使用
```

flags → 构造 → 注入 → 干活,四步。主网关的 Bootstrap 只是这个 73 行样本的 40 倍放大版,模式完全相同。

## 六、二次开发接线指南

想给系统加新依赖/新服务时,对号入座:

| 你要加的东西 | 接线位置 |
|---|---|
| 新的持久化后端/外部客户端 | `lib.LoadConfig`(挂到 `lib.Config` 上) |
| 启动时要跑的后台服务 | `Bootstrap()` 中按依赖顺序插入(参考 WebhookDispatcher) |
| 新管理 API 的 Handler | `RegisterAPIRoutes`:构造注入 + `RegisterRoutes(r)` |
| 请求处理逻辑 | 写插件,在 `server/plugins.go` 注册并选好 placement/order |
| core 需要的新能力 | 先在 `core/schemas` 定义接口,transport 层实现后经 `BifrostConfig` 注入 |
