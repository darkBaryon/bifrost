# 开发工作流:在持续维护的上游之上二次开发

> 核心认知:fork 是完全独立的副本,**上游改动永远不会自动进来**。同步是由你发起、你控制节奏的动作。

## 分支各司其职

```
upstream/dev   官方开发线,一直在动          → 只读,永远不往上提交
本地 dev       官方的干净镜像               → 不在这上面写代码
develop        你的主线 = 官方基线 + 你的二开 → 日常开发的家
feature/*      单个功能的工作分支            → 从 develop 切,完成后合回 develop
```

远程配置:`origin` → 你的 fork(darkBaryon/bifrost),`upstream` → 官方(maximhq/bifrost)。

## 两条互不干扰的水流

```
官方: upstream/dev ──●──●──●──●──→ (自己一直往前跑)
                         ↘ ②你定期主动拉进来
你:   develop ──docs──A──M──B──→
                    ↗ ①你的功能合入
      feature/x ──┘
```

**水流①:你的开发(每天发生)**

```bash
git checkout -b feature/xxx     # 从 develop 切出
# ...写代码、提交...
git checkout develop && git merge feature/xxx && git push
```

**水流②:上游同步(每 1-2 周,或想要官方新功能/修复时)**

```bash
git fetch upstream dev --depth=30 # 浅克隆必须带 --depth!见下方说明
git checkout develop
git merge upstream/dev            # 这一刻官方改动才真正进入你的代码
git push
```

⚠️ 本仓库是浅克隆,`fetch` 必须带 `--depth=N`(N 覆盖到上次同步点即可,30 通常够)。
不带 depth 时,若上游有 "Merge main into dev" 类提交,git 会试图拉取整条 main
历史(数百 MB),在代理网络下必超时。2026-08-18 首次同步已实测:带 depth 秒完成、
零冲突(全部改动为新增文件 + main.tsx 两行,印证了最小 merge 税设计)。

## 节奏与冲突

- 每 1-2 周同步一次,小步快跑;拖半年再同步,冲突滚雪球
- 同步完立刻 `make build && make test-plugins` 验证官方改动没弄坏你的功能
- 冲突量取决于改动方式,详见[接线指南](03-接线指南.md)的"黄金原则"——插件化改动几乎零冲突

## 本仓库克隆的特殊性(踩坑记录)

- 本地是 **shallow(depth=1) + blob 过滤**的 partial clone,只有 1 个提交;日常开发无影响,要翻历史时 `git fetch --deepen=200 upstream` 按需加深
- 网络走本地代理(127.0.0.1:1082),推送大对象容易断;fork 建立后推送均为 KB 级增量,无压力
- 提交信息用英文 conventional commits(`feat:`/`fix:`/`docs:`),与上游一致
