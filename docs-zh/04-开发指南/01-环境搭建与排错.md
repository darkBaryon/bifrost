# 10 · 开发指南（含 IDE 报错排查）

## 环境要求

- Go ≥ 1.26.5（本机低版本也行：`GOTOOLCHAIN=auto` 会自动下载所需工具链）
- Node.js（UI 与 npx 包）
- Docker（framework/E2E 测试的后端服务）

## ⚠️ 第一步：生成 go.work（不做 IDE 必定大面积报错）

本仓库是 15+ 模块的 Go workspace，但 `go.work` **被 .gitignore 忽略**，克隆下来没有。缺失时 framework/transports 会去解析**已发布的旧版** core/插件模块，而本地 `dev` 分支代码用了未发布的新 API，于是 gopls/编译到处报 `undefined`、`missing go.sum entry`。

```bash
make setup-workspace   # 官方方式：重建 go.work，纳入 cli、core、framework、transports、全部插件、tests/cmd/*
```

完成后重启 gopls（VSCode：命令面板 → "Go: Restart Language Server" 或直接 Reload Window）。

### 第二个常见报错：`pattern all:ui: no matching files found`

`transports/bifrost-http/main.go` 用 `//go:embed all:ui` 嵌入前端产物，目录不存在时报此错。两种解法：

```bash
# 轻量占位（make dev 内部也是这么干的）
mkdir -p transports/bifrost-http/ui && touch transports/bifrost-http/ui/.tmp

# 或真正构建一次前端
cd ui && npm install && npm run build
```

## 常用命令

```bash
make dev                 # 完整本地开发：UI 热更新(3000) + API 热更新(8080, air)
make build               # 构建 bifrost-http 二进制
make lint / make fmt     # 代码检查 / 格式化
make mod-tidy [MODULE=core|framework|transport|plugins|cli|tests]  # 按模块 tidy
make work-clean          # 删除 go.work（还原为发布版解析）
```

测试命令见 [测试体系](04-测试体系.md)。

## 工作区规则（来自 AGENTS.md）

- `go mod tidy` 要在**具体模块目录**跑，不要在仓库根跑。
- 跨模块 import 本地靠 workspace 解析，但发布时必须在 go.mod 写明 `require`。
- 版本发布顺序遵循 core → framework → plugins → transports 层级（有 `/changelog-writer` 技能辅助）。

## 常见开发任务速查

**加一个新 Provider**：`core/providers/<name>/`，OpenAI 兼容的走极简委托模式，非兼容的实现完整转换器（`types.go`/`errors.go`/`chat.go`…）；转换函数必须纯函数；记得配 `streamingClient`（否则流 30s 被掐）。

**给 API 响应加字段**：`core/schemas/` 加类型 → Provider 响应转换器映射 → 流式聚合器（`framework/streaming/`）处理 → 必要时 HTTP handler 序列化 → 可配置的话更新 `transports/config.schema.json`。

**加插件**：`plugins/<name>/` 独立 go.mod → 实现 `LLMPlugin`/`MCPPlugin`/`HTTPTransportPlugin` → 加进 go.work → transport 层注册 → Makefile 加测试目标。

**改 UI**：`ui/app/workspace/<feature>/` → 保留/补充 `data-testid` → `make run-e2e FLOW=<feature>` 验证。

## 核心禁忌（Gotchas）

1. **池化对象归还前必须清零全部字段**（`pool.Put` 不会自动重置，脏数据会串请求）。
2. **BifrostContext 里不放大数据**——只放 ID/布尔/指针；随流增长的缓冲放 RequestID 键控的管理器。
3. 插件 Post-hook 是 LIFO，逻辑不要假设执行顺序与 Pre 相同。
4. Provider 转换函数保持纯净：无 HTTP、无日志、无副作用。
5. 流式路径一律用 `streamingClient`，一元路径用 `client`。

## 环境排查记录(2026-09-03):worktree 缺 go.work + gopls 假报错

判断原则先说:**终端 `go build`/`go vet` 通过而编辑器标红,问题一定在 gopls,不在代码。**

| 报错 | 根因 | 处置 |
|---|---|---|
| worktree 里 `missing go.sum entry for go.mod file`(semanticcache→mocker) | `git worktree` 不带 gitignore 的 go.work;`make setup-workspace` 在 worktree 里会失败,因为 `go work init` 向上找到主仓库的 go.work 就报 already exists | `cp <主仓库>/go.work <worktree>/go.work`(use 全是相对路径,原样可用),重启 gopls ✅ |
| 同一文件切进切出红线闪烁 | VSCode 打开的是主仓库根目录,主仓库与 worktree 各有一份同名模块(`github.com/maximhq/bifrost/core`),gopls 两个视图互相串 | 主仓库 `.vscode/settings.json` 的 `gopls.build.directoryFilters` 加 `-.claude`;或把 worktree 单独开一个窗口 ✅ |
| `github.com/fasthttp/websocket is not in your go.mod file`,贴在 main.go 第 1 行注释上,多个不相干文件都有,go.mod 里明明有这行 | gopls 的 mod-tidy 诊断:它对 go.work 里**每个**模块离线跑一次 `GOWORK=off go mod tidy`,任何一个模块的 go.mod 缺 `// indirect` 行,就把错误贴到**全工作区所有 import 该包的文件**上。肇事者是 `tests/scripts/1millogs/go.mod`(要求 core v1.7.3,依赖链已把 core 拉到 v1.7.11,新 core 带进 websocket 未登记) | `cd tests/scripts/1millogs && GOWORK=off go mod tidy` ✅ |

### 第三条的定位方法(下次直接用)

```bash
# 1. 用 gopls 命令行复现,输出里 position 0:0-0:N 的 N = 肇事 go.mod 第一行 "module ..." 的长度
gopls check <任意报错文件>

# 2. 对 go.work 里每个模块模拟一次 gopls 的离线 tidy,有 diff 的就是肇事者
for m in $(grep -E '^\s*\./' go.work | tr -d '\t '); do
  t=$(mktemp -d); cp "$m/go.mod" "$t/"; [ -f "$m/go.sum" ] && cp "$m/go.sum" "$t/"
  (cd "$m" && GOWORK=off GOPROXY=off GOFLAGS=-mod=mod go mod tidy -modfile="$t/go.mod" >/dev/null 2>&1) \
    && diff -q "$m/go.mod" "$t/go.mod" >/dev/null || echo "untidy or failed: $m"
done
```

模拟 tidy 失败(rc≠0)的模块不用管,gopls 那边同样失败、不产生诊断;只有 tidy 成功且有 diff 的才会污染全工作区。

### 以后怎么避免

1. **开新 worktree 先 cp go.work**,不要跑 `make setup-workspace`。
2. **主仓库(开发用)go.work 保持全量**,开发要跨模块编译;红线复发按第 3 条修肇事模块即可。只读源码的 worktree 可以把 go.work 精简到 `make setup-workspace` 的 18 个模块,tests/scripts、examples、scripts 这些边缘模块上游经常不 tidy,不读就别登记。
3. **同步上游后若红线复发**,先跑上面的扫描脚本,对肇事模块 `GOWORK=off go mod tidy`,不要去改被标红的文件。
4. **一个窗口一份模块。** 主仓库和 worktree 别在同一个 VSCode 窗口里混着开。
