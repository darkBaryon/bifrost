# 现有功能盘点与开发候选(2026-09-04,基于源码通读)

> 数据来源:07-阅读笔记 15 步通读、docs/features 各页描述、上游 open issues、本机 config.db。和 02-象限A功能对比 的区别:那份横向比竞品,这份纵向盘 Bifrost 自己有什么、缺什么、我们做什么。每项写清"是什么、为什么、怎么做"。

## 一、OSS 现有功能盘点

### 1.1 数据面(core + 插件):请求怎么被处理

**多厂商适配(29 家)**。改一个 base_url 就能把现有 OpenAI/Anthropic/Gemini SDK 的流量接进来,网关翻译成各家上游格式。三种方言各一个底座(openai/anthropic/gemini),其余 26 家借底座只写域名、鉴权、怪癖。国内只内置了 DeepSeek;Qwen、Kimi、智谱等现在靠"自定义 provider"配置接入(指定 base_provider_type 和 base_url),上游 #6053 正在把这三家做成内置。

**50 种请求类型**。不只聊天:Responses API、Embedding、Rerank、OCR、语音合成与转写、图片生成编辑、视频生成、批处理、文件、代码解释器容器、Gemini 缓存内容。全部走同一套编排。原因是"改 base_url 其他不动"的承诺,漏一个接口用户就要绕过网关。

**Key 管理**。一个 provider 配多个 key,按权重随机选;每个 key 可限定允许的模型;429/401/403 这类"这把 key 的问题"自动换 key 重试,5xx 同 key 退避重试;全部 key 试死返回 502。重试默认关(max_retries=0),按 provider 配。

**Fallback 换家**。请求里带 fallbacks 列表(如 openai/gpt-4o 失败换 anthropic/claude),主 provider 失败后按顺序换;取消的请求不换,插件标记 AllowFallbacks=false 的不换。只对 12 种推理类请求生效,批处理查状态这类带上游 ID 的不换。

**故障隔离**。每家 provider 一条独立队列和一组 worker,一家慢只堵自己;队列满可配"等"或"丢";每家独立 HTTP 连接池。

**流式**。SSE 逐块转发,断线心跳探测,客户端断了但上游已算 token 的照样计费(弃单计费)。

**治理(governance 插件,21k 行)**。这是 OSS 最重的功能,子项:
- *Virtual Key*:客户端只持 VK,真实厂商 key 永不出网关;VK 可限定允许的 provider、模型、MCP 工具
- *层级预算与限流*:VK → Team → Customer 三级,加 provider 级和模型级;预算按周期归零(30s 到 1M);内存实时拦截,10 秒落库
- *路由规则*:用 CEL 表达式按请求属性(模型、header、复杂度等级)改写目标 provider/模型,支持加权多目标和链式规则,控制台有决策树可视化
- *复杂度路由*:对最后一条用户消息按代码、技术、推理三类信号的关键词加长度加权打分(0 到 1),分四档(simple/medium/complex/reasoning);出现两个以上推理关键词直接判 reasoning;路由规则可按档位选模型,比如问候走便宜模型、推理题走旗舰模型
- *必填 header*:强制每个请求带指定 header,否则拒绝

**请求日志与统计(logging 插件 + logstore)**。每个请求一行:模型、token、费用、延迟、状态、可选正文;控制台有二十来种直方图和排名(按时间、provider、模型、team、customer);正文可选不存或存到 S3/GCS。总花费是查询时 SUM(cost),不是预存。

**语义缓存**。相同或语义相近的请求直接返回上次的回答,不调上游;向量库四选一(Weaviate/Redis/Qdrant/Pinecone);缓存命中在 pre-hook 短路。

**观测**。Prometheus 指标(/metrics,可推 Push Gateway)、OpenTelemetry trace 导出到任意 OTLP collector(支持 GenAI 语义约定、OpenInference、Vercel AI SDK 三种格式)、Maxim 自家平台。

**提示词仓库**。控制台建模板、版本、playground 调试;请求头带 x-bf-prompt-id 就把模板消息插到请求前面,模板参数当默认值。

**MCP 网关**。把 MCP 工具服务器接进网关:注册 server(mcp-registry,含一个可安装的 server 库)、OAuth 和 per-user header 两种凭据、每个 VK 限定可用工具、agent 模式(模型返回工具调用时网关自动执行并回填,循环到完成)、code mode(用 Starlark 让模型写代码调工具)、对外也能当一个 MCP server(/mcp)。

**Skills 仓库**。管理 Agent Skills(SKILL.md 加附件),SemVer 发版,Bifrost 当作 Claude Code / Codex 的 skills 市场。

**异步推理 + Webhook**。/v1/async/... 提交后轮询,或配 webhook 端点在任务完成/失败时收签名回调,至少一次投递带退避重试。

**兼容层**。15 个前缀(/openai、/anthropic、/genai、/bedrock、/litellm、/langchain、/cursor 等)接各家 SDK 和框架的方言,加 compat 插件做 LiteLLM 兼容的参数增删。

**数据面缺的**:内容护栏(企业版闭源)、记忆(谁都没有)。

### 1.2 控制面(server + 22 个 OSS 页面):管理员日常在网页上做什么

按管理员的工作分四类,每个页面写清"打开看到什么、能做什么"。

**装 provider、管 key(providers、model-catalog、model-limits、custom-pricing)**。providers 页是最常用的:加一家厂商,填 base_url,贴几个 key,给每个 key 设权重和允许的模型,点"刷新模型列表"从上游拉一次真实可用的模型。model-catalog 是只读的模型字典,每个模型的定价、上下文长度、支持哪些参数,数据来自定价表同步。model-limits 给单个模型设预算和限流,比如"gpt-4o 全局每天最多花 100 美元",和 VK 的预算是独立的一层。custom-pricing 是定价覆盖:同步表里的价不对或者是空的,在这里按"全局 / 某 VK / 某模型"手动指定单价。

**发 key 给业务方、控成本(virtual-keys、governance、routing-rules、complexity-router)**。virtual-keys 是给下游团队发放的"网关 key":一个 VK 绑定允许的 provider、模型、MCP 工具,业务方拿 VK 调网关,永远看不到真实厂商 key。governance 页管 VK 之上的层级:team 和 customer,以及挂在它们身上的预算(多少钱一个周期)和限流(每分钟多少请求或 token),VK 的花费往上累加到 team 再到 customer。routing-rules 写 CEL 条件改写目标:比如"header 里 x-env=dev 的请求全部转到便宜模型",页面右侧有决策树可视化。complexity-router 配复杂度分档的参数:三类信号的关键词表和四档的分数边界,路由规则里可以按档位选模型。

**看发生了什么(dashboard、logs、mcp-logs、observability)**。dashboard 是总览:总花费、总 token、延迟曲线、按 provider 和模型的排名,全部是对日志表现算的。logs 是每一条请求的检索,能看到请求和回答正文(可配不存)、用了哪个 key、走没走 fallback、缓存命没命中。mcp-logs 是 MCP 工具调用的日志,一次 agent 循环里调了哪些工具各花了多久。observability 页不是看数据的,是配置往外推 trace 的格式(OTel GenAI 约定、OpenInference、Vercel AI SDK 三选一)。

**接 MCP 工具(mcp-registry、mcp-settings、mcp-sessions、oauth-grants)**。mcp-registry 是注册 MCP server 的地方,带一个可直接安装的 server 库,注册后能看到它暴露的工具、给工具改名、设"允许所有 VK 用"。mcp-settings 是全局参数:agent 循环最多几层、工具执行超时、code mode 绑定级别。mcp-sessions 和 oauth-grants 管 per-user 的凭据:有些 MCP server 每个用户要各自 OAuth 授权,mcp-sessions 是授权流程页,oauth-grants 列出已授权的 token,绑定到哪个 session 或 VK、什么时候过期、能吊销。

**扩展与系统(plugins、prompt-repo、skills-repo、webhooks、config、docs)**。plugins 页列出内置和自定义插件,能启停、改配置、调顺序。prompt-repo 建提示词模板和版本,带 playground 试跑。skills-repo 管 Agent Skills,发版后 Claude Code 和 Codex 能把 Bifrost 当 skills 市场装。webhooks 配异步任务完成时的回调端点。config 是客户端级配置:代理、header 白名单、日志保留天数、CORS。docs 是内嵌的文档站。

**鉴权只有一个账号**。整个控制台一个管理员用户名密码(AuthConfig 里就 admin_username 和 admin_password 两个字段),session 登录,没有用户表、没有角色、没有"谁改的"这个概念。文档里有一页"SSO with Google & GitHub"标着 Coming soon,代码里没有。这是企业采购时第一个被问倒的地方。

**定价数据从哪来**。启动时从 https://getbifrost.ai/datasheet 拉一份 Maxim 维护的表(4473 行,每 24 小时同步,可换成 file:// 走内网),请求时查内存。只有美元。国内模型有 1177 行,92% 有价,但几乎全是海外第三方托管(together、fireworks、deepinfra)的价,厂商官方端点那一行多为空。

### 1.3 企业版闭源的功能:OSS 里是"联系我们"占位页

按企业采购清单的顺序。每项写它解决什么问题。

**身份:RBAC、SSO/用户供应、数据访问控制**。RBAC 是多用户加角色(超管/团队管理员/只读),权限点到页面和按钮;用户供应(User Provisioning)用 OAuth 2.0/OIDC 登录,后台定时从身份系统(Okta、Entra、Keycloak、Zitadel、Google Workspace)同步用户、团队、角色和业务单元,离职自动失效;数据访问控制(Data Access Control)是行级可见性:按调用者的角色、团队、身份过滤他能看到的 VK、日志、配置。解决"几个人共用一个密码"过不了安全审计,以及"团队管理员看到别人团队数据"的问题。

**审计日志**。每一次管理操作(谁、几点、从哪个 IP、改了什么)记一条带 HMAC 签名的事件,可按人/动作/目标/时间检索,导出 JSON、JSON Lines、Syslog 给 SIEM,按天保留,可归档到 S3 做多年留存。解决"出了事能追责、监管来查有证据"的问题。

**护栏**。请求和回答两个方向的内容检查:内置密钥检测(Gitleaks 规则)、自定义正则(带 PII 模板)、LLM 判官(自然语言写策略让模型判),外接十家内容安全服务(Presidio、Azure、Bedrock、Google Model Armor、Lakera 等)。规则用 CEL 定何时查,档案定怎么查,命中后拦截或脱敏,流式分段检查。解决内容合规的问题,也是国内最缺的一块,因为它接的全是海外服务。

**集群**。多个网关实例共用一个数据库,在任一实例改配置其他实例秒级生效(gossip 广播),预算用量跨实例汇总,节点挂了从日志表补回它没落库的用量。解决"单实例撑不住"的问题。

**自适应负载均衡与熔断**。自适应负载均衡按健康监测和性能预测在多个 provider/key 间动态分流;熔断器根据上游返回的 HTTP 响应头信号(如限流、降级标记)判断主端点退化,自动切到配置的备用 provider,恢复后切回。解决上游不稳定时的体验问题,数据面里少有的企业版功能。

**Access Profiles、MCP Tool Groups、用户级治理**。Access Profile 是可复用的策略模板(允许的 provider、模型、预算、限流、MCP 工具),挂到用户、团队或业务单元(business unit)上后自动给每个人发一把绑定该策略的 VK,不用手工建;MCP Tool Groups 把工具编成组,可挂到 VK、团队、客户、用户、provider 或 API key 上,请求时强制生效;用户级治理让预算和限流细到单个用户。解决 VK 和工具授权数量多了以后的管理问题。

**数据连接器**。把每个请求的 trace 推到 Datadog、BigQuery、Kafka、Pub/Sub。解决接入企业已有数据栈的问题。

**Bifrost Edge(终端管控,alpha)**。装在每台员工电脑上的客户端(macOS/Windows/Linux),把这台机器上所有 AI 流量——桌面聊天应用、浏览器里的 AI、终端和 IDE 里的编码 agent、它们连的 MCP server——强制经过公司的 Bifrost,让 VK、预算、审计、护栏管到员工实际在用的 AI,而不只是配了 base_url 的那些。MDM 批量部署,控制台管设备列表、审批哪些应用和 MCP server 可用、下发配置。解决"影子 AI"的问题:员工自己装的工具绕过网关。

**其余**:告警(用 CEL 表达式对治理指标写规则,预算或限流触顶时推到 Slack、Teams、PagerDuty 或 webhook)、品牌定制(换 logo)、license 管理。

### 1.4 上游给包壳留的插座:不改上游文件就能接进去的地方

企业版是闭源仓库,它接进 OSS 靠的是 OSS 里预留的一批"插座"。我们的 ee/ 用同一批。每个写清"插上去能干什么"。

| 插座 | 在哪 | 插上去能干什么 | 我们用它做 |
|---|---|---|---|
| IsEnterprise ctx 标记 | Bootstrap 前往 ctx 塞一个值 | Bootstrap 看到就跳过 OSS 的治理插件和鉴权中间件,由包壳补自己的 | 初期不设(要自己重写治理);做 RBAC 时设,换掉鉴权 |
| ServerCallbacks 参数 | RegisterAPIRoutes 的第二个参数 | 传自己的包装类型,handler 回调时走包壳的方法,先做自己的事再转调 OSS | 集群广播:每次 Reload* 后通知其他节点 |
| 三处 callbacks.(XxxProvider) 断言 | RegisterAPIRoutes 里 | 包壳实现了对应接口就自动接入:日志脱敏映射、MCP 日志脱敏、治理路由整体替换 | 暂不需要 |
| ShellRewriter / OAuth2IdentityResolver / ExternalQuotaBudgetResolver | server struct 的可选字段,注释 "nil on OSS" | Bootstrap 前赋值:换 UI 的 logo、按用户隔离 MCP、外部配额来源 | 品牌换 logo 白送;后两个做 RBAC 和 Access Profile 时用 |
| SyncLoadedPlugin | server 的公开方法 | 把一个进程内 new 出来的插件注册进 Config 和 core,不用 .so、不受 Go 版本约束 | **所有自研插件都走这里** |
| ConfigStore.DB() | ConfigStore 接口导出的方法 | 拿到同一个 GORM 连接,自建表、自跑迁移 | **所有自建表都走这里**:审计事件、护栏规则、拦截记录 |
| KeySelector / KeyPoolFilter | BifrostConfig 的两个函数字段 | 换 key 选择算法、过滤 key 池 | 自适应路由才用,后排 |
| BifrostGuardrailDebug 共享类型 | core/schemas | 护栏把检测元数据填进响应的 ExtraFields,日志和 UI 直接显示 | A1 直接对齐 |

这张表就是"包壳能做什么"的边界:能做的都在表里,表里没有的就要给上游提 PR 加插座,或者改上游文件。

## 三、开发候选

每项四段:是什么(用户视角)、为什么、怎么做、验收与工作量。

### A. 插件(数据面,挂在请求路径上)

#### A1 内容安全护栏 —— P0

**是什么**:管理员在控制台建"检测档案"(接阿里云内容安全、百度、腾讯,或内置的中文 PII 正则、提示词注入检测),建"规则"决定哪些 VK 的哪些请求在输入/输出阶段用哪个档案查;命中后按配置拦截(返回一段看起来像模型自己拒答的回复)或脱敏(替换敏感片段后放行);每次检测记一条事件,检测服务超时放行并计数。

**为什么**:生成式 AI 备案和等保要求"不得生成、不得传输"违法内容,采购时第一个问的就是有没有内容安全对接;企业版有但闭源且只接海外服务;国内竞品 Higress 有(ai-security-guard),New API 没有。

**怎么做**:LLMPlugin,PreLLMHook 取最后一条 user 消息、PostLLMHook 取回答,调检测后端;拒绝返回 ShortCircuit{Error{StatusCode 200, AllowFallbacks=false, 拒答文案}};规则和档案表用 ConfigStore.DB() 自建,内存副本 + Reload;检测结果填进 OSS 已有的 schemas.BifrostGuardrailDebug,日志和 UI 直接显示;流式第二期用 HTTPTransportStreamChunkHook 分段攒缓冲。配置面照 Higress:六个维度各设阈值(max/high/medium/low)、按 VK 覆盖、fail-open。管理面部分(档案 CRUD、规则页、拦截记录页)是包壳。

**验收与工作量**:非流式聊天在阿里云后端下能拦、能脱敏、能放行、超时放行有计数;拦截记录可查。核心 2-3 周,流式 +1 周,管理页 +1 周。依赖:阿里云内容安全账号。

#### A2 记忆 —— P1

**是什么**:按用户(或 VK)自动记住跨对话的事实("用户在上海""偏好 Python"),下次请求自动把相关记忆拼进上下文;控制台能查看、删除某用户的记忆;可配置作用域(会话/用户/组织)和遗忘策略。

**为什么**:网关赛道空白;有记忆的网关让上层应用零改造获得个性化。

**怎么做**:两段。请求路径上是 LLMPlugin:PreLLMHook 按用户 ID 检索(向量相似 + 时间新近 + 重要性)取前几条拼 system;PostLLMHook 把这轮对话异步扔给提取管线。提取管线是后台 worker:门控(值不值得记)→ 提取候选事实(LLM)→ 与已有记忆整合(新增/更新/删除/无操作,LLM)→ 评分 → 落库;定时任务做衰减、合并、冲突清理。存储复用 VectorStore 接口 + 自建元数据表。建议第一版直接接 mem0 的开源库做提取整合,自己只写两个钩子和管理页。

**验收与工作量**:同一用户两次会话,第二次不重复告知的信息能被模型用上;删除后不再出现;写入不增加请求延迟。接 mem0 版 2-3 周,自研整合 4-6 周。

#### A3 国内观测导出 —— P2

**是什么**:把每个请求的 trace/日志推到阿里云 SLS、腾讯 CLS,把告警发到飞书/钉钉群。

**为什么**:企业版的 Datadog/Kafka/BigQuery 连接器在国内没有对应物;国内运维栈是 SLS/CLS 加 IM 告警。

**怎么做**:实现 ObservabilityPlugin.Inject(响应写完后异步收到完整 trace),转成 SLS/CLS 的日志格式推送;照 otel/maxim 插件的形状;飞书/钉钉告警走 webhook。

**验收与工作量**:SLS 里能按 VK 搜到请求。每个后端 3-5 天。

### B. 包壳(控制面,请求路径之外)

#### B1 审计日志 —— P0

**是什么**:每一次管理操作(谁在几点从哪个 IP 改了哪个 provider 的 key、删了哪个 VK、导出了什么)记一条不可篡改的事件;控制台按人/动作/目标/时间检索;可导出 JSON、JSON Lines、Syslog 给 SIEM;按天保留,可归档到对象存储。

**为什么**:等保三级和企业采购的必选项;OSS 完全没有(logging 记的是推理请求,不是管理操作);企业版闭源。

**怎么做**:ee/ 包壳里给 /api 路由组加一层中间件,在 handler 之后取用户、方法路径、目标实体、结果、耗时,HMAC 签名后写自建表 ee_audit_events(ConfigStore.DB());读接口 /api/ee/audit 加页面;保留清理照 LogsCleaner 起定时器;归档照企业版文档的窗口 + manifest 方式写 S3/OSS。"改了哪个字段"的语义要在 handler 层拿,所以中间件之外还要在几个关键 handler 的回调里补事件。

**验收与工作量**:改一个 key 后审计页出现一条含发起者和目标的事件,篡改库里一行后验签失败,导出的 Syslog 能被 SIEM 收。2 周。无外部依赖,建议第一个做:包壳骨架(中间件、自建表、路由、页面)在这一步成型。

#### B2 多用户与 RBAC —— P0

**是什么**:多个管理员账号,角色(超管/团队管理员/只读),权限点到页面和操作;团队管理员只看得到自己团队的 VK、日志、预算。

**为什么**:OSS 只有一个账号密码,几个人共用一个密码在企业里过不了审;审计的"发起者"字段没有用户体系就是空话;企业版闭源。

**怎么做**:自建用户和角色表;用 Casbin 做权限模型;包壳里替换 OSS 的 auth 中间件(IsEnterprise 标记或直接换 AuthMiddleware),session 里带用户和角色;每个 handler 前按路由做权限检查;行级过滤用 OSS 已有的 visibility.go 实体过滤接口(它就是给 RBAC 留的)。UI 侧 rbac 页面 OSS 有占位组件,照它的形状做。

**验收与工作量**:只读角色改不了 key,团队管理员看不到别的团队的 VK。3-4 周。

#### B3 SSO / OIDC —— P1

**是什么**:用企业已有的身份系统登录(飞书、钉钉、企微、Keycloak、任意 OIDC),用户和组自动同步,离职即失效。

**为什么**:企业采购必选;国内 IdP 和企业版支持的 Okta/Entra 不重合。

**怎么做**:go-oidc 接 OIDC;飞书/钉钉/企微各一个 OAuth 适配;登录回调建或更新 B2 的用户;组映射到角色。依赖 B2。

**验收与工作量**:飞书扫码登录进控制台,角色按组自动分配。1-2 周(B2 之后)。

#### B4 人民币定价与国内官方端点价格 —— P1

**是什么**:控制台总花费和预算可以按人民币显示和设定;Qwen/Kimi/智谱/DeepSeek 官方 API 的价格准确。

**为什么**:定价表只有美元;国内模型的价是海外第三方托管的价,官方端点行是空的,国内用户看到的费用不对。

**怎么做**:OSS 已有 pricing-overrides(按范围覆盖单价)表和页面,扩展:加币种字段和汇率配置;维护一份国内官方端点价格覆盖文件(数据文件,不写代码里),启动时导入覆盖表;UI 显示时按币种换算。不改 datasheet 同步。

**验收与工作量**:调一次 qwen 官方端点,日志里的费用等于官方定价乘 token 数,dashboard 显示人民币。1 周。

#### B5 离线/内网部署 —— P1(几乎白送)

**是什么**:没有外网的机房也能启动和更新定价表、模型参数、MCP server 库。

**为什么**:国内私有化部署常见无外网;Bifrost 启动默认拉 getbifrost.ai。

**怎么做**:上游已支持,framework.pricing.pricing_url / model_parameters_url / MCP library URL 都接受 file://,有官方 air-gapped 指南。我们只需一个镜像脚本(定时拉 getbifrost.ai 放到内网 HTTP 或文件)加中文文档。

**验收与工作量**:断网启动成功,定价表是镜像的。1-2 天。

#### B6 集群 —— P2

**是什么**:多个网关实例共用一个数据库,在任一实例改配置其他实例秒级生效;预算在实例间汇总。

**为什么**:单实例撑不住时必须;企业版闭源。

**怎么做**:包壳覆盖 ServerCallbacks 的 Reload*/Remove* 回调,本地更新后通过 Redis pub/sub(或共享库轮询)通知其他节点各自重读;用量汇总用 governance 已有的 baselines 参数和日志表的 GetNodeUsageAfter。

**验收与工作量**:两个实例,A 改 key,B 一秒内用新 key;B 挂掉后 A 的预算包含 B 挂前的用量。3-4 周。单机能撑很久,后排。

#### B7 事后审查工作台 —— P2

**是什么**:定时扫请求日志批量做内容检测,标出违规,人工复核,申诉,出合规报告。

**为什么**:A1 是事中拦截,监管检查要"证据链"和抽查;A1 fail-open 放过去的要事后补检。

**怎么做**:后台任务读 LogsStore 送检测后端;结果表 + 页面;复用 A1 的后端适配。A1 之后。2 周。

#### B8 小件 —— P3

告警(阈值触发 webhook/飞书)、配置备份恢复、license 开关、品牌换皮(ShellRewriter 与 branding 插座现成;注意 Apache 协议允许使用代码但 Bifrost 名称与 logo 是上游商标,对外交付前必须换掉)。各几天。

### C. 明确不做

- 国内厂商内置适配器(上游 #6053 在做)
- 改上游任何 handler/service 结构(合并成本)
- 自研向量库、自研 RBAC 引擎(用现成件)
- 中转站式充值、分组倍率、渠道倒卖(那是 New API 的地盘,和"企业网关"定位冲突)

## 四、建议顺序

```
第 1 步  B1 审计日志(包壳骨架在这一步成型:中间件、自建表、路由、页面)               2 周
第 2 步  B2 多用户与 RBAC → B3 SSO(多用户是审计"发起者"有意义的前提)               4-6 周
第 3 步  A1 内容安全(插件骨架成型:规则表、pre/post、拒答、fail-open)                3 周
第 4 步  B4 人民币 + B5 离线(小件,穿插做)
之后    A2 记忆、B6 集群、B7 审查台按需求排
```

B1、B2 先于 A1:审计和多用户是所有使用场景的交集(依据见第六节),包壳骨架后面每一样都复用;审计没有外部依赖,内容安全要先申请检测服务的账号和额度,且只有在多团队共用之后才有"给谁管"的问题。

## 六、使用场景与产品形态(2026-09-04 讨论)

开发顺序不是按功能大小排的,是按"谁在用、卡在哪一步"排的。这一节把使用场景摊开,作为第四节顺序的依据,也列出尚未确定、需要拍板的形态问题。

### 6.1 网关前后的五种人

同一台网关前后至少五种人,各自只碰产品的一小块:

- **业务开发者(调用方)**。拿到一个虚拟 key,把 SDK 的 base_url 改成网关地址,之后不再打开控制台。要的只有三件事:SDK 原样能跑、流式不断、错误信息能看懂。上游最用心服务的就是这种人,50 种请求类型、fallback、重试都是为他做的。
- **平台管理员(运维或平台组的一两个人)**。部署网关、接厂商 key、给各团队发虚拟 key、设预算,日常看仪表盘和日志排故障。OSS 的 22 个页面全是为这一个人设计的,单账号密码就是"默认只有他一个人"的假设。
- **团队负责人**。想知道本组这个月花了多少、谁在烧钱,想自己申请或调整预算。OSS 里没有他的账号,只能找管理员要截图。
- **安全与合规**。问的是谁在什么时候把什么内容发给了哪家模型、有没有违规、谁改过配置。OSS 有请求日志,但没有配置变更记录、没有内容检测、没有"操作人"这个概念。
- **采购决策者**。不用产品,只在选型时问"能否私有化、过不过等保、支不支持信创、多人登录怎么管",在续费时看一份成本与合规报告。

OSS 把前两种人服务得很好,后三种人在 OSS 里几乎不存在。候选清单里的审计、RBAC、内容安全,本质上是给后三种人补入口。

### 6.2 两种尚未确定的形态

**形态 A:企业内多个团队直接调网关**。调用方是业务代码或编程 agent(Claude Code、Codex 这类)。网关只认虚拟 key,不知道 key 后面是谁。

**形态 B:员工通过内部应用使用,网关在应用后面**。典型是钉钉/飞书群机器人、内部聊天页面。网关如果要按人管,需要应用把用户身份一路透传过来。

两者对网关的要求差别集中在两点:

| | 形态 A(直接调) | 形态 B(应用内嵌) |
|---|---|---|
| 请求特征 | 超长上下文、大量工具调用、Anthropic 格式直通 | 短消息、人数多、并发分散 |
| 网关关心的 | prompt cache 命中、流式稳定、按 key 计费 | 用户身份、按人内容安全、会话状态 |
| 会话记忆 | 禁止:agent 自己维护完整上下文并自行压缩,网关再塞历史会重复上下文、打乱工具调用序列 | 可选:钉钉每次只推一条消息,必须有人存历史,机器人层或网关层二选一 |

关于会话记忆的两点说明:

- 上游目前没有对话状态。`x-bf-session-id` 是"同一会话粘住同一把上游 key"(为厂商侧 prompt cache 命中),不是记忆;Responses API 的 `previous_response_id` 只透传给厂商。
- 如果将来做,形状应是"有状态的 Responses API":网关存下每次响应,下次请求带 `previous_response_id` 时由网关拼回完整输入再发给任意厂商。客户端 SDK 本来就会说这套协议,国内厂商没有 Responses API 也能用上,机器人应用只需存一个 ID。这与 A2 的长期记忆是两回事:一个是原样回放本次对话,一个是跨对话提取事实。

**形态 B 的范围要分两档,不能笼统叫"内嵌钉钉"。** "企业接入大模型的统一入口"这个意义上,给人用的入口(钉钉)和给代码用的入口(API)都算入口,把钉钉接入归入网关产品没有问题。但"内嵌钉钉"在实现上有两种差一个量级的东西,立项前必须说清楚要的是哪一档:

| | 钉钉接入(薄适配器) | 企业 AI 助手(应用) |
|---|---|---|
| 做什么 | 机器人收群消息,转给网关,把回答发回群里;存最近几轮上下文 | 多轮会话管理、上传文件、知识库问答、按部门权限、群管理、审批流 |
| 依赖 | 网关的虚拟 key + 用户身份头 | 网关之外还要向量库、文件存储、自己的用户与权限模型 |
| 可比产品 | 各家网关的"渠道接入"示例 | Dify、Open WebUI 这类应用平台 |
| 工作量 | 一周左右,几百行 | 按月计,单独立项 |

无论哪一档,**架构上都是网关的一个客户端,不是网关的一部分**:独立进程,收钉钉回调、存会话,调网关时带虚拟 key 和 `x-bf-dim-user`。这样网关本体不因钉钉变形,上游合并不受影响,换飞书或企微是再写一个同形状的进程。产品上它可以叫"网关的钉钉模块",工程上它是一个独立可交付物,工作量单独报。

### 6.3 需要确认的四个问题

这几个问题决定形态 A 还是 B 以及 B 的范围,不涉及技术:

1. 第一个用的是谁:自己公司内部,还是要交付给某一类客户?
2. 网关前面接的是什么:几个开发团队的代码和 agent,还是一个给全员用的聊天或 Agent 应用?
3. 出了事要追到哪一级:追到"哪个 key",还是追到"哪个人"?
4. 如果要接钉钉:要的是机器人能在群里回话(接入),还是一个完整的助手应用(见 6.2 的两档)?

第三个问题最关键,它直接决定用户身份要不要进网关,以及内容安全是按 key 还是按人。
