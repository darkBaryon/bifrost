## 1. 结论与范围

建议按“认证与控制台基础接入 → 角色管理 → 账号管理 → 个人中心与密码记录 → 逐模块收齐权限交互”补齐。登录、权限和工作台外壳需要作为第一批的完整闭环；后续管理页面依赖它们。

判断依据是当前代码、已交付报告与接口契约，而不是上游商业版页面。自有业务包括 `identity`、`rbac`、`branding`、`pricing`、`guardrails`；`host`、`app` 是接入与装配，不各建一套管理页面。UI 中文化和品牌设置已有前端；管理操作审计尚待计划。

| 已实现能力 | 前端现状 | 应补内容 |
|---|---|---|

| 内容安全配置与检测 | 已有读/写/重置 API，尚无自有管理页 | 补内容安全配置页面，并对齐 Settings 权限与现有 Guardrails 入口 |

## 2. 必须先解决的接入问题

### 2.1 普通账号可能被外壳的配置查询挡住

`AppContent` 启动就查询 `/api/config`，`FullPage` 根据其中的数据库连接状态决定是否显示业务页；查询错误会显示控制台不可达。Sidebar、Topbar 也依赖同一配置。

但后端给 `/api/config` 配置的是 `Settings.View`。因此，只有路由权限、没有设置查看权限的正常账号会收到 403，并可能被挡在业务页面之外。这是由调用链推导的接入缺陷，尚未通过浏览器复现。

建议新增一个正常会话可读的最小控制台信息投影，或移除外壳对管理配置的依赖。优先方案是新增 `POST /api/console/bootstrap` **（拟议接口，当前不存在）**，仅承载外壳确有需要且适合普通账号读取的状态：例如可用功能、数据库/日志可用性、环境显示标签。字段需要逐项确认；认证状态和当前账号继续由身份接口提供，不复制整份配置或认证设置。

继续保留 `/api/config` 的设置权限。外壳以及 onboarding 的配置、厂商 Key、治理、SCIM 查询均需按功能与权限启动，不能只修改最外层的一次请求。日志、MCP、提示词等业务页也有 `useGetCoreConfigQuery`，随对应模块接入逐项确定应该改用安全投影，还是确实需要设置权限。

证据：[工作台外壳](../../ui/app/clientLayout.tsx)、[菜单](../../ui/components/sidebar.tsx)、[顶栏](../../ui/components/topbar.tsx)、[引导查询](../../ui/hooks/useOnboardingChecklist.ts)、[后端路由权限清单](../../ee/internal/rbac/host/routes.txt)（`GET /api/config`）。

### 2.2 替换登录表单还不够

登录路由 loader 只看 `is_auth_enabled`、`has_valid_token`；已有有效但必须改密的会话会先被跳往工作台。单独覆盖 `loginView` 无法修正这个跳转。

需要共享一套明确的认证状态判定：

```text
检查状态 → 未初始化 → 初始化 → 登录
         → 未登录   → 登录
         → 必须改密 → 仅本人改密/退出 → 重新登录
         → 正常会话 → 加载本人权限与外壳信息 → 可访问的工作台页面
         → 请求失败 → 错误与重试
```

初始化成功不自动登录；改密成功撤销本人所有会话，必须重新登录。受限改密页不能挂在会启动管理查询和通知的完整工作台里。

`/workspace` 目前固定跳 `/workspace/dashboard`，而 Dashboard 需要日志查看权限。应由可访问入口选择器决定落点，全部业务权限为空时仍允许进入个人中心与退出。保留经过校验且有权限的 `goto`；无效或无权目标要有明确退路。

证据：[登录路由](../../ui/app/login/layout.tsx)、[工作台路由](../../ui/app/workspace/layout.tsx)、[登录跳转工具](../../ui/lib/utils/loginGoto.ts)、[身份接口](../../ee/docs/账号认证接口.md)。

### 2.3 EE 构建目前没有真实权限适配器

自有覆盖层未实现 `rbacContext`；fallback 的 `useRbac`、`isAllowed` 始终返回 true。后端已拒绝未授权操作，但页面仍可能展示入口并发出请求。

实现 EE `RbacProvider`，保持现有 `useRbac(resource, operation)` 接口，读取 `/permissions/me` 返回的 matrix。初始未知状态不放行；加载、失败、重试分别显示。新功能需要的敏感权限从原始 permission codes 查询，不靠字符串推断 View/Manage 关系。

功能是否已实现与账号是否有权限是两回事。例如 `Users.View` 的兼容矩阵也映射 `UserProvisioning`，但本仓没有完成 SCIM 前端；菜单还需可用功能过滤，不能因企业构建标记就全部显示。

后端 `AuditLogs` 矩阵项当前始终 false。密码记录有自己的接口授权规则，不能直接套该矩阵项，否则主管理员也看不到入口。

证据：[fallback RBAC](../../ui/app/_fallbacks/enterprise/lib/contexts/rbacContext.tsx)、[后端矩阵映射](../../ee/internal/rbac/http/matrix.go)、[覆盖脚本](../../ee/ui/sync.sh)。

### 2.4 会话失效、通知和缓存需要一起接通

- `baseApi` 的全局 401 跳登录仅在 `!IS_ENTERPRISE` 时执行，企业 refresh 包装目前又是透传。需要在 EE 适配点补身份失效处理；后端没有 refresh 接口，不新增前端刷新令牌逻辑。
- 401 清理当前身份及账号相关查询/状态并转登录；403 表示禁止访问或来源不合法，不能当登出；503/网络失败显示重试。表单登录失败等预期 401 由对应页面处理，公共及临时令牌流程保持各自边界。
- 顶栏通过 OAuth 的 `getUserInfo()` 读身份，自有账号没有该存储；改接响应式的当前账号信息。退出使用身份接口，并关闭旧连接、清理账号相关缓存。
- 通知当前默认作用域可能落到 `local-admin`，多个个人账号会共用本地偏好；改以账号 UUID 隔离。
- WebSocket 有模块级全局连接和自动重试，无通知权限也会申请 ticket；应由正常会话且 `Notifications.View` 控制启动。403 停止重试，登出或切换账号关闭旧连接、清除计时器。禁用连接时仍提供可用的空上下文，避免现有消费者报错。
- 权限初次加载、窗口重新聚焦、相关修改后和权限拒绝时重新查询；撤权后清除受影响的敏感缓存。权限查询本身的 403 不应递归触发重查。无通知权限也必须能刷新权限，不能依赖 WebSocket 才维持正确状态。

证据：[请求基础层](../../ui/lib/store/apis/baseApi.ts)、[旧会话 API](../../ui/lib/store/apis/sessionApi.ts)、[通知同步](../../ui/hooks/useNotificationSync.tsx)、[WebSocket](../../ui/hooks/useWebSocket.tsx)。

## 3. 页面与接口的对应关系

| 页面/功能 | 建议入口 | 接口与交互要点 |
|---|---|---|
| 初始化、登录、受限改密 | 复用登录入口，按状态呈现独立表单 | `/identity/status`、`initialize`、`login`、`me`、`change-password`、`logout` |
| 角色与权限 | 复用 `/workspace/governance/rbac` | `/roles/list/get/create/update/delete`、`/permissions/list`；模块分组编辑、显示系统角色与关联账号数 |
| 用户管理 | 复用 `/workspace/governance/users` | `/accounts/list/create/set-status/delete/reset-password`；列表显示最近登录，独立确认危险操作 |
| 账号角色与有效权限 | 用户详情抽屉 | `/accounts/get-roles/set-roles`；多角色选择、权限来源展示、完整替换提交 |
| 个人中心 | 顶栏账号菜单进入新页面，建议 `/workspace/account` | `/identity/me`、`/permissions/me`、本人改密及本人密码记录；不依赖 `Users.View` |
| 密码操作记录 | 现有日志占位入口可复用，但需调整名称及准入规则 | `/identity/password-events`；管理员查全量/指定账号，其他正常账号只看本人 |

新路径和日志入口名称属于建议。个人中心始终保留安全退路；受限会话只能改密/退出，不能查看个人权限或事件列表。管理员日志入口依照 `Users.Manage`，不要伪装成已实现完整审计。

接口细节统一参考[账号认证接口](../../ee/docs/账号认证接口.md)、[角色权限接口](../../ee/docs/角色权限接口.md)。以下限制会直接影响页面设计：

1. **账号不等于上游 User。** 自有账号是 UUID、登录名、显示名、状态等字段；上游 SCIM/OAuth 用户类型不能直接复用。角色编号是安全范围内的正整数。
2. **创建与分配角色是两步。** 创建只收登录名和显示名，不收密码/角色。初始密码来自部署配置且不返回。分配失败要明确显示“账号已创建，角色未分配成功”，允许对这个账号重试分配；不能重试创建造成重复账号。
3. **列表没有账号角色摘要。** 产品要求每行显示角色，当前 `/accounts/list` 不返回角色。建议在后续账号批次补批量/列表读取投影，避免列表逐行发 N 个详情请求。由装配层组合身份与角色查询，避免让身份持久化层直接依赖 RBAC 表结构。
4. **只有游标分页。** 账号、角色、事件没有总数及通用搜索/排序/状态筛选契约。首版用加载更多或游标翻页；不能把当前一页的前端筛选展示为全库搜索。若确认要搜索，先补相应服务端契约。角色选择器也需处理完整的分页结果，不能只提供第一页。
5. **没有编辑个人资料接口。** 不能设计可保存的“修改用户名/显示名”按钮；也没有任意账号基础详情读取接口，可先从所选列表行打开详情。
6. **授权不会自动补齐。** 多角色取并集；Manage 不包含 View/敏感权限。角色编辑器可提示组合关系，但不能静默勾选额外权限。目录 `available: false` 的预留项不开放操作，编辑已有角色时也不能无提示地丢弃其原值。
7. **保护规则以服务端为准。** 不能修改本人角色/停用本人/重置本人；不能删除固定恢复账号或破坏最后一位启用主管理员。列表未返回全部保护状态，前端只能预先处理已知条件，再展示后端冲突原因。角色被关联时删除冲突使用 `details.account_count` 提示。
8. **密码重置需要稳定操作编号。** 为一次明确操作生成 UUID，网络结果不确定时沿用原编号重试；已确定失败后的新尝试按接口语义生成新编号。权限竞争等 409 与编号冲突不能一概处理。
9. **本人权限不要求用户管理查看权限。** `/permissions/list` 需要 `Users.View`，个人中心不能为了翻译权限名称偷偷依赖它；可复用有版本约束的展示名称映射，或补本人响应的只读展示信息。
10. **密码验证按 UTF-8 字节约束。** 新密码至少 8 字符、最多 72 字节，不 trim、不截断；前端字符数和字节数需分别计算，最终仍由后端验证。

## 4. 既有页面的权限适配范围

接上真实 `useRbac` 能复用已有入口与按钮控制，但不代表所有页面自动正确。按后端[宿主边界说明](../../ee/internal/rbac/host/README.md)和[路由清单](../../ee/internal/rbac/host/routes.txt)逐项核对：

| 检查对象 | 前端应满足的行为 |
|---|---|
| 菜单与直接 URL | 无权菜单不显示；直接访问明确展示没有权限；数据请求在获准后启动 |
| CRUD 操作 | 查看用户不出现管理按钮；加载中不闪现管理入口；提交失败保留输入 |
| 厂商/虚拟密钥 | 正确区分隐藏值、未修改和主动替换；不把脱敏占位值当新密钥提交 |
| 日志 | 分别控制查看、原文、导出、删除；已有 Reveal 控制需验证全部消费者，而非重复重写 |
| 插件 | `Plugins.LoadNative` 与普通管理分开；现有操作枚举未包含该项 |
| 认证设置/导入 | 旧 security 表单不能修改 EE 认证字段；预留功能不可展示成可用 |
| 凭据目标变更 | 从原始 grants 读取 `Security.ChangeCredentialDestination`，根据保存语义提示；不能简单禁止无该权限用户编辑任何 URL |
| 设置/日志配置等组合操作 | 以实际请求所需权限组合决定提交和错误展示，不认为 `Settings.Manage` 可以修改所有配置 |
| 通知 | 无查看权限不发查询/不建连接；按账号隔离偏好；管理操作另判权限 |

敏感目的地权限管的是“将已有凭据用于新地址/TLS 信任”等行为，不是查看密钥权限，也不替代模块管理权限。前端不完整复制后端判定，保存时处理明确的禁止原因。

## 5. 代码边界建议

继续使用现有 React、TanStack Router、RTK Query、RHF/Zod、Radix/本地 UI 组件。业务实现放在 `ee/ui/`，保留已有覆盖模式；不要直接改同步生成的 `ui/app/enterprise`。

建议按业务能力归属文件，路径可在正式方案中细化：

```text
ee/ui/app/enterprise/
  features/
    identity/         登录状态、初始化、登录、改密、当前账号
    access/           权限查询、窄查询接口、路由准入与入口选择
    roles/            角色列表、角色表单、权限选择
    accounts/         账号列表、创建、角色分配、启停/删除/重置
    password-events/  事件查询、列表与显示转换
  components/         既有覆盖入口，仅转接相应 feature
  lib/contexts/       兼容上游 useRbac 等接口的薄适配
  lib/store/          向现有 store 注入 API/必要的会话生命周期适配
```

这是一种职责划分，不是要求每个目录都复制整套分层：

- 页面负责布局、选中账号 ID、打开哪个抽屉；不维护每个表单的字段、请求和错误。
- `AccountRoleAssignment` 通过 `accountId` 查询自己的数据，拥有角色草稿与提交过程；保存通过查询标签失效更新列表/详情。父页面不传整个账号模块的状态对象。
- `RoleEditor` 拥有名称、说明、权限选择；表单内部通过局部表单上下文协调。父页面只决定编辑对象和关闭行为。
- 登录状态 Context 只公开身份状态和少量动作；权限 Context 只提供当前授权查询。不能把所有 CRUD、表单、弹窗和 API 都收进一个 Provider。
- 服务端数据以 RTK Query 缓存为准，表单草稿留在局部；不再复制一份全局账号表/角色表。全局仅保留跨页面确实需要的会话生命周期状态。
- 密码校验、错误分类、权限展示投影、重置重试决策可用小纯函数表达并单测；不要为了文件变短把原来 800 行组件原封不动搬成 800 行 hook。
- 自有组件中文文案、业务说明与 README 同步；超过 300 行评估职责，超过 500 行按仓库规范拆分。

可复用入口：[用户视图路由](../../ui/app/workspace/governance/users/page.tsx)、[角色视图路由](../../ui/app/workspace/governance/rbac/page.tsx)、[Store 注入](../../ui/lib/store/store.ts)。已有角色/用户选择器如绑定了商业版接口，只复用交互基础，提供自有契约的薄适配；遵守实体选择器规范。

### 需要少量上游扩展的地方

仅靠当前覆盖入口无法完成所有接入。预计需要为登录 loader、workspace 落点、外壳基础数据、顶栏账号菜单、通知连接生命周期提供可选扩展点；业务实现仍在 EE。默认不提供扩展时保持上游原有行为，按[上游改动约束](../../product/上游改动/README.md)登记，避免散落大量 `if (IS_ENTERPRISE)`。

新增个人中心路由使用薄路由壳转接 EE 视图；普通构建的入口可见性及 fallback 行为需要一起设计。不能从覆盖目录随意新增路由文件后假定两种构建都正确。

## 6. 建议开发批次与完成标准

| 批次 | 交付内容 | 可独立验收的结果 |
|---|---|---|
| 1：认证与控制台接入 | 状态机、初始化/登录/受限改密、退出、当前账号、真实权限适配、最小外壳信息、可访问落点、通知启停、最小个人退路 | 新实例能初始化；管理员能登录；必须改密不能进后台；只有路由查看权限的账号能进入路由页；零业务权限账号能改密/退出；无通知权限无重连风暴 |
| 2：角色与权限 | 权限目录、角色列表、创建/编辑/删除、预置角色约束 | 能创建自定义角色；权限多选不隐式升级；系统/关联角色删除有正确提示；保存后详情和权限刷新 |
| 3：账号管理 | 列表及角色摘要投影、创建、分配角色、启停、重置、删除、账号有效权限 | 完整创建并授权账号；部分成功可恢复；重置后旧会话失效；自身和最后管理员保护；最近登录与无记录正确展示 |
| 4：个人中心与密码记录 | 个人角色/有效权限来源、完善主动改密、本人记录、管理员事件列表 | 无 Users.View 也能查看本人信息；其他人记录不可见；管理员能按账号查看密码操作；不宣称完整审计 |
| 5：现有业务页逐模块收齐 | 厂商/密钥、治理/路由、日志、MCP/提示词、插件/设置分别小批核对 | 菜单、直接 URL、查询、按钮、脱敏与提交权限一致；有限权限账号不被无关配置查询阻断 |

批次 1 涉及基础接入较多，内部可以拆成会话适配、路由/外壳、登录表单几个可评审提交，但验收要走通同一条登录链路。必要的无权路由/查询保护从批次 1 开始；不能把所有保护推迟到批次 5。批次 5 是按模块收齐复杂交互和组合权限。

建议先实施批次 1；角色先于账号管理，使角色分配有真实可选数据。批次 3 的账号摘要投影与前端同期交付。批次 4 完善的主动改密复用批次 1 的表单和接口，不再实现另一套。

## 7. 开发环境与验证策略

### 环境接入

身份接口严格校验 `EE_PUBLIC_ORIGIN`。当前 Vite 在 3000 端口，`getApiBaseUrl()` 在开发模式直接连 8080；Vite 虽已有 `/api` 代理，但该绝对地址绕过代理，且未配置 `/ws` 代理。

建议 EE 开发统一浏览器访问来源，经代理访问 `/api` 和 `/ws`，后端 `EE_PUBLIC_ORIGIN` 与浏览器实际 origin 精确一致（`localhost` 与 `127.0.0.1` 也不能混用）。采用 EE 可选连接配置，保留上游默认行为。生产同源 Cookie 方式继续沿用。此项需要实际验证 Origin、Cookie、代理和 WS，不能靠关闭来源检查绕过。

依据：[连接地址工具](../../ui/lib/utils/port.ts)、[Vite 配置](../../ui/vite.config.mts)、[身份装配](../../ee/internal/app/identity.go)。

### 测试重点

- **纯逻辑单测**：认证状态转换、允许的登录落点、UTF-8 密码约束、权限矩阵默认拒绝、HTTP 错误分类、重置 operation_id 重试语义。
- **接口/交互测试**：初始化后登录、受限改密、角色全量更新、创建成功但分配失败、关联角色删除冲突、账号操作后的失效标签。针对行为与失败恢复，不镜像实现或堆快照。
- **浏览器端到端**：主管理员、开发者、只读、自定义单模块、无角色、强制改密账号。覆盖直接 URL、两标签页失效、退出后换账号的缓存隔离、无通知权限、脱敏字段保存、503/403/401 的差别。
- **构建回归**：EE 覆盖构建与 OSS fallback 构建都检查；品牌、中文化和公共/临时令牌页面保留。生成目录在隔离构建目录处理，避免破坏正在运行的开发环境。

复用现有 Vitest 与 Playwright。当前 `ui/vitest.config.ts` 只配 `@`，没有对齐 EE 别名/符号链接，也没有 DOM 测试环境；先补必要配置，纯函数直接测，真实交互优先使用已有 E2E 基础设施，不预先引入整套新依赖。测试后端复用 EE 冒烟的隔离进程/临时库思路，不能直接在个人开发库创建、删除账号进行验收。

当前 [FIND-022](../findings.md) 明确以前端接入作为统一错误契约的触发条件：上游 500/422/429 可能使用 `unavailable` code。批次 1 应确定并统一其转换契约、同步接口文档；在此之前前端必须结合真实 HTTP 状态分类，不把所有 `unavailable` 都当 503。

## 8. 进入正式方案时需要明确的接口增量

已有主业务接口足够承载大部分页面；建议控制新增后端的范围：

1. **第一批必要**：外壳不依赖 `Settings.View` 的最小读取能力；可以新接口或等价解耦实现，不能直接放开完整配置。
2. **账号批次必要**：为产品要求的列表角色列提供批量或列表摘要，明确一致性与权限边界。
3. **依交互选择决定**：本人权限的显示名称、账号搜索/过滤、独立账号详情、保护动作元信息。没有确认交互需求前不扩大后端范围。

开发前据此建前端补齐需求及首期方案，把新增投影、上游扩展点和验收账号组合写进检查清单。本文的页面路径、文件布局和批次属于建议，不替代正式方案确认。
