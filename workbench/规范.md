# 流程规范(Engineering Playbook v1.1.0)

> 本目录是 [engineering-playbook](https://github.com/darkBaryon/engineering-playbook) v1.1.0(@78d5a7ef)在本项目内的只读副本。**规范演进以 Playbook 仓库为唯一可编辑源**;工作台外壳(状态机/视图/预飞/站点)源自 xhs-recon workbench(playbook 的前身实践)。

## 理念(为什么要这套流程)

人掌握需求、方案和风险边界;Agent 承担实施、检查和技术评审,用可验证结果证明交付质量。四条支柱:

1. **人必须理解项目将如何变化**——实施前共同讨论目标/接口/数据流/风险/回退;用户不审每个函数,但能回答"为什么这样改、影响什么、失败怎么恢复"。
2. **Agent 在确定边界内连续完成工作**——方案定了之后,命名/组织/测试结构/普通重构自主处理;要动目标、公共接口、数据流、兼容策略,必须回到方案层;真实外部写入/发布/删数据必须用户明确授权。
3. **评审与实施相互独立**——方案和代码都由干净上下文的独立评审者重新检查,不采信实施者自述;只有引发业务/方案层变化时才回到用户。
4. **以证据而不是声明证明完成**——交付前必须实跑检查、验证关键行为;"已验证"的表述必须附带可重放的验证命令。

(完整论述见 [Harness Engineering.md](Harness%20Engineering.md),已归档,本节为其操作性摘要。)

## 本仓实际执行序(单线)

工作台文档类型(见 [SCHEMA.md](SCHEMA.md))沿一条线走完一个 Change:

```text
立案定档(reports/,tier ↔ L1/L2/L3)
→ 方案 v<N> + 方案评审(需修改则出 v+1,至通过)
→ [Gate 1 条件触发:有真正拍板项才打断]
→ 隔离实施(feature 分支;方案尾部补实施记录三章节 → 已实施)
→ 预飞(checklist.yaml + tools/preflight.py,全绿才请评审)
→ 代码评审 ∥ 收敛评审(并行独立;/convergence-review skill;有Blocking 阻塞 Gate 2)
→ Gate 2(用户拍板)
→ 验收记录 + findings.md 台账登记 → 方案已归档、需求已交付
```

## 共同底线(全文各规范均遵守)

- 结论必须绑定精确基线、版本或产物
- 流程重量与风险匹配,拿不准时按较高档准备
- 实际工作偏离已确认范围时先停下、记录并裁决
- 机械检查负责事实,独立复核负责语义判断
- 修订、评审和复测保留历史,不覆盖旧结论
- 用户负责业务取舍、风险接受和最终放行
- 交接依赖落盘文档、commit、diff 和原始证据,不依赖聊天记忆
