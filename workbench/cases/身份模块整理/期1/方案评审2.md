## 结论

**需修改。** [方案 v2](方案v2.md) 关闭了上轮 7 条阻塞中的 5 条（1 部分关闭、2、4、5、7 全关闭），关闭方式在设计层经得起核对：`CreatedAt` 归属逐路径追过没有遮蔽也没有漏赋值，`identity/hasher` 的判定规则自洽且依赖图正确，两个窄接口的七个方法签名与现有实现**逐字吻合**，禁留模式去掉 `\b` 后覆盖全部旧用法且不误伤新名字。但阻塞 3（白名单）与阻塞 6（测试零改动口径）各留一处**可复现的反例**，另有一处新阻塞：步骤 2 的 DTO 键集合断言在它被安排的包里实现不出来。三条都是局部修订，不动设计骨架。

### 阻塞 6：「测试只改构造方式」不成立 —— **未关闭**

组合类型的**机制本身正确**，我逐条核过：

- `services{*SessionService; *AccountService; *PasswordService}` 三个嵌入指针在深度 1，18 个业务方法在三个服务间无重名，`Authenticate/Login/Logout/Me/IssueTicket/ConsumeTicket/ValidateSession`（Session）、`BootstrapLegacy/Initialize/CreateAccount/SetAccountStatus/ListAccounts`（Account）、`ChangePassword/ResetPassword/RecoverAdmin/ListPasswordEvents`（Password）全部唯一提升；
- 只有挂在 `*core` 的 `State` 与 `RequireAccountManager` 会经三条路径在深度 2 产生歧义，§6 正好给了这两个转发方法，深度 0 的显式方法覆盖深度 2 的歧义集合，符合 Go 选择器规则；
- 嵌入的是指针，`*SessionService` 的指针接收者方法进入 `services`（值）的方法集，`s.X(` 写法不用取地址；
- `diagnostics_test.go` 的两处调用（`ChangePassword:43`、`Authenticate:59`）走 `fixture(t)`，同样提升成立。

## 建议（不扩进本期方案）

1. **步骤 1 的自检 grep 恒不为 0。** §5 步骤 1 写「`grep -rn internal/bifrost ee product workbench/规范 workbench/cases/*/期1/checklist.yaml` 为 0」。实跑该命令，除预期的 6 处外还必然命中**本期自己的 checklist**：`workbench/cases/身份模块整理/期1/checklist.yaml:61`（禁留模式里的字面量 `internal/bifrost`）与 `:15`（`test-asserts-unchanged` 里的 `git show SHA:ee/internal/bifrost/auth_test.go`，按设计必须保留旧路径才能取基线）。请把 glob 收窄为 `workbench/cases/账号认证/期1/checklist.yaml`，或加 `--exclude` 说明。checklist 里的禁留项本身没问题，它的 `in` 是 `ee`。
2. **`\|` 与上轮修掉的 `\b` 是同一类可移植性问题。** `test-asserts-unchanged` 的 `grep -c 't\.Fatal\|t\.Error'`（checklist:15）与步骤 5 的 `grep -rn 'identity\.Service[^sA-Za-z]\|identity\.NewService'` 都用了 GNU/ugrep 的 BRE 交替扩展。本机 `grep` 实为 ugrep 7.8.4，实测命令可执行（`python3 -c yaml.safe_load` 取出后 `/bin/sh -n` 语法通过，第一段循环在基线上静默通过，末段因 `ee/internal/host/auth_test.go` 尚不存在而 rc=1，符合预期）。但在 POSIX BRE 下 `\|` 会被当字面量，两侧计数同为 0 → `[ 0 = 0 ]` **假绿**。建议改 `grep -E` 或拆成两次 grep 相加。
3. **§4.6 的「超过万行再评估」没有观察点。** 论证本身可接受，但方案没有任何机制让人知道会话表何时越过阈值——冒烟不测行数，也没有诊断日志。建议在步骤 7 的 `cleanup_test.go` 里顺带断言清理后的行数量级，或把「运维如何自查行数」写进 README 一句话；否则这条自设触发器永远不会被触发。
4. **§2.2 测试表两处描述与实测不符**（计数正确，描述错）：`bifrost/auth_test.go` 是「构造(:47) + **两处**调用（`Initialize:51`、`Login:54`）」；`persistence/diagnostics_test.go` **没有构造**，它用 `fixture(t)`（:33），两处调用是 `ChangePassword:43` 与 `Authenticate:59`。
5. **`test-asserts-unchanged` 的不变量偏弱。** 它只比 `t.Fatal|t.Error` 的**行数**，改掉某个断言的期望值（例如把 `!= 401` 改成 `!= 403`）不会被发现。§6 正文的「diff 行须全部落在允许集合」才是真正的检查，但它没进 checklist、只能人工执行。建议把 §6 那条 `git diff -U0 ... | grep '^[-+]'` 的核对也做成一条必过命令（允许集合可用白名单正则表达），否则预飞事实表给出的绿是弱绿。
6. **同一规则在 `sessions` 与 `handler` 上应用不一致。** §4.3 把服务依赖改成 host 自定义的窄接口，却保留 `handler *identityhttp.Handler` 具体指针。v2 的辩护（`Origin()`/`SameOrigin()` 是方法调用不是字段取用）对编码规范:39 的理解正确，可以接受；但「接口由使用方定义」同样适用于 handler 的三个能力（`Origin`/`SameOrigin`/`RegisterRoutes`）。建议记为观察项，本期不做。
7. **`identity/hasher → identity` 这条边只在加编译期断言时才存在。** `Bcrypt` 结构化地满足 `identity.PasswordHasher`，不 import `identity` 也能编译；§4.7 画了这条边，意味着实现时要照 `store.go:326` 的惯例加 `var _ identity.PasswordHasher = Bcrypt{}`。建议在 §4.4 写明，免得实现与依赖图对不上。

## 剩余风险

1. **DTO 字段泄漏的护栏尚未落位**（N1）：在断言改到能执行的地方之前，「`Account` 增 `CreatedAt` 不改变 `/api/accounts/list` 输出」只有人工抽查（§7）兜底。这是本期唯一带新字段的对外类型。
2. **测试零改动靠人工 diff 核对**（建议 5）：checklist 的机械项只能证明断言**条数**没变，证不了断言**内容**没变；61 处调用点的机械替换若顺手带走一个期望值，预飞仍会全绿。
3. **`identity/hasher` 与 `persistence` 的哈希行为一致性**：`ValidHash` 的完整 bcrypt 形状校验（`store.go:29-36`）是账号认证期1 独立测试 F 轮补的，搬包时若正则或 `bcrypt.Cost` 调用有任何笔误，只有 `auth_test.go` 的旧管理员导入路径会发现。步骤 4 的检查项只写了 `grep framework/encrypt` 为 0，建议同时确认 `hasher` 包内保留了那条正则的原文。
4. **步骤 5 的 diff 规模**：改名先行让它成为「移动」diff，但 `service.go`→`core.go` 改名 + 新建 `session.go` + 三个接收者替换 + 四个包的调用点改写仍在同一提交里，`git diff -M` 能否识别为移动取决于相似度，核对成本可能高于预期。
