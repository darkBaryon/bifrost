## 逐项意见

### 阻塞 1：账号分页零行为保护，而步骤 3 正好改它的契约

§6 称「2.3 列出的四个测试文件与三个冒烟脚本作为表征测试」足以护住本次整理。实测不成立：**`ListAccounts` 在 `ee/` 内没有任何测试调用**（`grep -ocE "s\.(...|ListAccounts|...)\(" ee/internal/identity/persistence/service_test.go` 的 61 处调用中 `ListAccounts` 为 0），冒烟脚本对 `/api/accounts/list` 只发 `{}`（`ee/scripts/identity-smoke.py:179`、`ee/internal/bifrost/auth_test.go:114`），唯一的翻页循环覆盖的是 **password-events**（`identity-smoke.py:225-235`），不是账号列表。

而步骤 3 恰好改这条路径：`Repository.Accounts` 由 `[]Credential` 改 `[]Account`（`model.go:224`、`store.go:300-309`），并给 `Account` 增 `CreatedAt`。这里有一个会静默出错的具体机制：`Credential` 已经在深度 0 自带 `CreatedAt time.Time`（`model.go:129`），`Account` 再加同名字段后，`AccountRecord.CreatedAt` 遮蔽 `AccountRecord.Account.CreatedAt`，Go 不报错；而 `rows.go:24-30` 的 `credential()` 只给外层赋值、内层 `identity.Account{...}` 字面量不含 `CreatedAt`。若 `Store.Accounts` 沿用 `r.credential().Account` 取值，`accounts.go:180` 的 `encodeCursor(rows[n-1].CreatedAt, ...)` 会编出 `At` 为零值的游标，下一次请求在 `accounts.go:153` 的 `c.At.IsZero()` 处被判 `ErrInvalid` → 400。整套现有测试与冒烟都发现不了。

**要求**：把「账号列表分页（至少两页、next_cursor 可继续、无重复无遗漏）」的表征测试作为步骤 3 的**前置**独立提交落地，并在 §4.1 写明 `AccountRecord` 与 `Account` 的 `CreatedAt` 归属（去重还是保留遮蔽），在 §2.3 把「`ListAccounts` 现无覆盖」记为已知盲区。

### 阻塞 4：§4.6「与 login_limits 既有做法同形」不成立，且与既有注释冲突

- **索引层面不同形**。`limitRow.WindowStart` 带 `gorm:"index"`（`rows.go:104`），`store.go:265` 的 `window_start < ?` 删除走索引；而 `ee_identity_sessions` 的索引只有 `token_hash`（唯一）与 `account_id`，`ee_identity_ws_tickets` 除 `hash` 主键外**没有任何索引**（`migration.go:46-54` 七条 CREATE INDEX 全文）。按 §4.6 实现后，每次登录、每次签票都要对这两张表做一次全表扫描的 DELETE。补索引要改 `ee_identity_v1`，与[立案](../../../reports/身份模块整理.md)「不改 `ee_identity_v1` 迁移与表结构」的非目标冲突。请在 §4.6 明写取舍：或接受无索引全表扫描（给出行数量级与可接受理由），或把加索引作为拍板项提出。
- **与既有注释冲突**。`model.go:139-140`：「Session 只保存 token 的摘要；**撤销通过 RevokedAt 标记，记录不删除**」。编码规范硬规则「与代码不一致的注释视为缺陷」（[编码规范:38,92](../../../规范/项目/编码规范.md)），步骤 6 必须同步改这句，方案未列。
- **与账号认证期1 方案v2 无冲突**（可推翻原质疑）。v2 §4.3 的「保留记录，不级联删除」落在 `ee_identity_password_events` 一行（[方案v2:122](../../账号认证/期1/方案v2.md)），`ee_identity_sessions`（:118）与 `ee_identity_ws_tickets`（:120）两行都没有保留承诺。方案把「到期即删、含已撤销」列为拍板项 (c) 是够的。
- **事务与锁相容**（核对通过，无异议）。删除与插入同在 `transaction`（`store.go:228-259`）内，该事务先 `UPDATE state.revision` 取写锁，SQLite 为库级、PG 为行锁，两个节点被串行化，不引入新的加锁顺序。删掉过期会话行后 `AuthByHash/AuthByID`（`store.go:96-113`）由「找到行→`verify` 判过期→401」变为「`ErrNotFound`→`resolve` 折叠为 401」，对外状态码不变；`Logout`（`service.go:273-284`）对已删行走 `ErrNotFound` 分支返回成功，与现状一致。票据 DELETE 不会放开重放，因为消费条件本就是 `consumed_at IS NULL AND expires_at > ?`（`store.go:210`）。

### 阻塞 5：§4.1 的 core 清单与终态文件清单不完整

- **跨线共享函数漏列**：`page`（`accounts.go:143`）与 `encodeCursor`（`accounts.go:160`）定义在账号线，却被密码线使用（`passwords.go:189,198`）。§4.1 的 core 共享清单（verify / resolve / current / authorize / manager / hash / compare / validPassword）没有它们，而终态把 accounts.go 与 passwords.go 分给两个服务，这两个函数的归属必须写明。
- **终态文件清单少一块**：§4.1 只列 model.go / core.go / session.go / accounts.go / passwords.go，`service.go` 是否保留没写。现 `service.go` 里的 `Options` 与 `Options.Validate`（:17-32，**导出符号**）、`now`/`randomID`/`randomToken`/`digest`（:63-89）、`fullSession`（:153-158）在终态无归属；checklist 也没有相应的必存/禁留项。
- **「三条线互不调用」核对通过**（可确认）。逐个方法核过：`accounts.go:76,168` 与 `passwords.go:79` 调的 `RequireAccountManager`、`accounts.go:37` 与 `passwords.go:175` 调的 `State` 都在 §4.1 提升到 core 的两个方法内；`passwords.go:179` 用的是 `s.policy`（core 字段）；会话线的 `IssueTicket/ConsumeTicket` 只用 `manager`/`authorize`（`service.go:291,314`）。除上面两个分页辅助函数外，没有任何一条线直接调用另一条线的导出方法。

### 阻塞 6：§6 的「测试只改构造方式与类型名，不改任何断言」与事实不符

阻塞 2 已量化：拆分后 `service_test.go` 的 61 处调用（以及 `auth_test.go` 2 处、`diagnostics_test.go` 2 处）要从 `s.X(` 改成 `s.Session.X(` / `s.Account.X(` / `s.Password.X(`。这不是「构造方式」，是对行为保护文件本身的大面积改动，正是重构规范要防的情形。§5 步骤 4 的「改 app、host、http、测试的构造」同样低估了工作量。请把口径改成可机械核对的形式（例如：测试文件 diff 只允许出现接收者前缀替换与类型名替换，逐文件用 `git diff -w` 加正则自查，任何断言字面量变化即偏差），并在步骤 4 的检查列写明。

### 阻塞 7：§4.7 终态依赖方向有一处事实错误，并漏了搬 bcrypt 新增的测试级反向边

- 「与现状唯一差别：`host` 不再需要 `persistence`」不成立。现状 `bifrost` 的生产代码**本来就不 import `persistence`**（`auth.go:4-22`、`config.go:4-16` 的 import 块全文），只有 `auth_test.go` import 它；搬走 `Passwords` 之后 `auth_test.go` 仍要 `persistence.NewStore`/`MigrateIdentity`（`auth_test.go:44,47`），这条边也不会消失。
- 真正新增的边方案没写：`persistence/service_test.go` 属 `package persistence`，且把 `Passwords` 当作**嵌入类型**用（`service_test.go:291-292,298,310`）。`Passwords` 搬到 `host` 后，该测试必须 import `ee/internal/host`，即出现 `persistence`(test) → `host` → `identity`/`identity/http`。这不是 Go 的导入环（生产代码里 `host` 不 import `persistence`），但与 §4.7 的终态图相反。请在 §4.7 补这条测试级边，并说明选择（在测试内自备 hasher 桩，还是接受这条边）。
- 顺带：§4.4 把「包装上游 `framework/encrypt` 属宿主接入」当作搬迁理由。这条规则写清楚了才算数——`encrypt` 是上游**库**而非运行中的宿主，搬过去会让离线恢复命令（`app/recovery.go`，全程不碰 `server.BifrostHTTPServer`）间接依赖宿主接入包。请把判定规则写进 §4.4，而不是只写结论。

## 建议（不扩进本期方案）

1. **§2.4 第 4 条的事实要更正**：`dto.go` 实际定义 **20 个**类型（`grep -n "^type" dto.go`），不是 16 个；且现状并非「按出现顺序排列」，而是响应类型在前（:10-114）、请求类型在后（:116-158）、转换函数就近。更要紧的是 `dto.go` 仅 165 行、`handler.go` 274 行，都**低于**编码规范「300 行须评估拆分」的线，而[编码规范:55-62](../../../规范/项目/编码规范.md)明写「默认把需要一起理解、一起修改的代码放在一起；复杂后再拆」「不因它们分别叫 Repository、Error、DTO 就单独建文件」。拆成 4 个端点文件 + 4 个 DTO 文件是用户在立案中已批准的整理项，但方案应记录这项张力与收益判断，并保证 `dto_common.go` 不会退化成只剩零散辅助代码的文件。
2. **§4.3 的收窄没有落到「接口由使用方定义」**。[编码规范:26,39](../../../规范/项目/编码规范.md) 要求「接口由使用方按实际需要定义」「不从其他对象的字段取用」，而 §4.3 传入的仍是具体的 `*identity.SessionService`，`AuthAdapter` 也仍从 `a.http` 取 `Origin()`（`auth.go:213`）与 `SameOrigin(c)`（`auth.go:242`）。方案引用这条规则作为 §2.4 第 1 条的依据，却只换了个更小的具体类型。建议在 host 侧定义窄接口（`Authenticate`/`ValidateSession`/`RequireAccountManager`/`ConsumeTicket`/`Me`）；若本期不做，记为观察项并说明理由。
3. **checklist 的 `\b` 有假绿风险**。preflight 用 `grep -rIn --exclude-dir=__pycache__ -- '<word>' <scope>`（[preflight.py:76](../../../tools/preflight.py)），默认基本正则。`\b` 是 GNU/ugrep 扩展（本机 `grep` 实为 ugrep 7.8.4，实测可用），但在 BSD grep 下 `identity\.Service\b` 会退化为永不命中，禁留检查静默变绿。建议改用 `-w` 或写成不依赖 `\b` 的模式。已实测 `expires_at < ?` 这类含 `?` 的必含符号在 BRE 下按字面匹配可用（对照 `window_start < ?` 命中 `store.go:265`），这一项无问题。
4. **checklist 与方案终态的覆盖面对不齐**：§4.2 的 `dto_common.go`/`dto_session.go`/`dto_accounts.go`/`dto_passwords.go` 四个终态文件不在必存产物里；必含符号缺 `type Services struct` 与 `func New(`；缺一条「`ee/internal/identity/persistence` 不再出现 `framework/encrypt`」的禁留（这才是步骤 2 的实质验收）。其余命令实测可在本仓执行：`ee/scripts/identity-upgrade-smoke.py` 存在，`ui/` 存在，五个 README 与 `ee/internal/app/README.md` 均已存在，`smoke-unchanged` 的 `git diff --quiet <sha> -- ee/scripts` 在 preflight 的 `cwd=repo` 下成立。
5. **改动已归档案的合同要有口径**。步骤 1 要改 `workbench/cases/账号认证/期1/checklist.yaml:18` 的必存产物路径，但该案已 Gate 2 验收归档，且 `workbench/evidence/账号认证-期1-预飞1~9.md:23` 十份事实表都记着旧路径。改了合同、事实表不改，两者不一致；不改合同则该 checklist 不再可重跑。建议在方案里明确选哪种，并说明依据。

8. **`service_test.go` 已 481 行**，步骤 6 再加 FIND-020 用例后会逼近或越过编码规范「超过 500 行必须拆分」的硬线（[编码规范:41](../../../规范/项目/编码规范.md)，明写测试文件同样适用）。建议在步骤 6 顺带按业务线拆测试文件，或在方案里写明本期不拆的理由。

## 剩余风险

1. **最大剩余风险仍是账号列表路径**（阻塞 1）：它是本次唯一同时改数据契约和新增字段的地方，却是整个身份模块唯一没有任何自动化覆盖的对外端点。护栏补齐前，任何回归只能靠人工抽查 `/api/accounts/list`。
2. **FIND-020 的性能面无量化**（阻塞 4）：即便接受全表扫描，方案也没有给出会话/票据表在真实部署的行数量级，无法判断每次登录多一次 DELETE 的代价；本期冒烟不测性能，这项盲区会带到验收。
3. **测试文件大面积改动**（阻塞 6）：65 处调用点的机械替换即使有编译器兜底，也可能顺手改掉断言而不被发现；缓解只能靠 diff 自查口径，没有工具级保证。
4. **文档与归档合同的一致性**（建议 5）：`internal/bifrost` 改名会让已归档案的合同与其历史事实表之一出现不一致，无论选哪种处置都留一点痕迹。
