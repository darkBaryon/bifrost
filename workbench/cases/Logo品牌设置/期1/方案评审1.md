## 逐章核查

### 摘要与 §1 起点

摘要在十行以内，上传/预览/保存/重置、数据库持久化和拍板项明确。`git rev-parse HEAD` 确认完整 SHA；`git status --short` 仅见工作台源文档/生成视图与未跟踪原调研，未见业务改动。需求未填 tier、仍为待计划，准确反映定档未裁决，不能提前转开发中。标准级单期加 L3 Migration 证据要求符合 `规范/风险分级.md`，无需为了风险级别人为拆蓝图。

### §2 现状与约束

亲读 `ee/transports/bifrost-http/handlers/branding.go:18-35`，实际是无状态 GET，三项 false；`ui/app/_fallbacks/enterprise/components/branding/brandingView.tsx` 是 ContactUsView；`ui/lib/store/apis/brandingApi.ts` 已完整定义 GET/PUT/DELETE、合并 payload、URL 状态及标签失效，复用合理，无重复建设。

亲读 hook、登录页/等待卡、侧栏、检索 topbar/updating 调用，方案已识别影响面超过两个 DOM 点。`ee/ui/sync.sh` 确实先删除生成目录再复制 fallback/逐文件链接，故实施前保护其他人工改动是必要约束。`ee/transports/bifrost-http/server/bootstrap.go:39-64` 的 attach 位于上游 Bootstrap 后、Start 前，可取得 DB 和 Router；上游 `server.go:2719` 初始化 AuthMiddleware，方案显式对写路由装配正确，不能误以为所有新增 ee 路由天然继承上游 apiMiddlewares。

已重读路线图 §4.1–4.3、骨架需求与收敛评审、findings。旧评审将 RunSingleMigration 与上游迁移锁语义等同的结论不成立；本方案指出这一点正确，但具体事务组合尚有 B1。

### §3 目标 / 非目标

与需求和原调研逐项相符：本地上传、可选 icon、浅深共用、Logo 回退、保存前不生效、重启保留、取消重置不变；产品名/favicon/配色/深色独立图等未扩入范围。原调研明确“之后再接用户权限”，所以不因并行权限任务而要求本案自建 RBAC。正式素材缺失不阻塞测试，测试几何图片不能当作正式品牌交付。

### §4.1 存储、迁移与并发

数据库单例加明确槽位 patch 可支持省略保留、空字符串清除；两图全部校验后单 SQL 更新，可避免常见读后整行覆盖丢失另一槽位。Reset 保留单例方便一致合并，内容 hash 与旧程序忽略新表的回滚口径合理。须在实施中证明 SQL 仅更新显式列，不能用读取旧对象后 Save 替代。

**B1（阻塞）：**方案称在 RunMigration 回调内的同一事务取得 PostgreSQL 事务 advisory lock，再复制 DefaultOptions 调用 RunSingleMigration；但 `framework/migrator/migrator.go:179-186` 默认 `UseTransaction=true`，`:681-702` 使用直接 `g.db.Begin()/Commit()`，不是支持嵌套的 GORM Transaction/savepoint。`framework/configstore/migrations.go:162-178` 仅构造 migrator 并 Migrate，不会替调用方消解事务；`postgres.go:83-97` 只开临时连接池，`rdb.go:381-386` 只转发回调。按当前文字将外层 tx 传入会二次 Begin；若锁在事务外取得或迁移改传原池，锁又可能不覆盖检查版本、DDL、初始化单例和版本记录。

修订应明确唯一事务所有者及调用顺序，例如回调开启外层事务，设置局部锁超时/取事务锁，复制 options 并明确 `UseTransaction=false`，将同一个 tx 传 RunSingleMigration，返回错误让外层回滚；SQLite 也须明确采用哪层事务。不要修改全局默认。测试须包含建表/种子/版本记录的共同回滚、重复启动保留数据、并发初始化以及锁超时/取消释放，不仅“成功创建表”。这是设计缺口，不能留到实施时随意挑选。

### §4.2 HTTP 与认证

现有 `APIMiddleware`（`middlewares.go:1093-1190`）传入 `allowVirtualKeyAuth=false`，品牌写路径不在系统白名单；认证关闭明确 local admin 放行，用户白名单也会绕过。后续代码有 Cookie session、Basic、Bearer 认证，所以方案中“复用现有认证”的实质可成立，不能宣传为新的多人权限保护。读接口公开服务登录页，写路由精确注册，nil 鉴权启动失败均合理。认证用例应固定“已启用、品牌路径未加入用户白名单”的前提，并保留白名单例外说明。

图像契约覆盖独立槽位、严格 JSON、MIME/base64、先 DecodeConfig 后完整 decode、字节/像素限制、数据库失败不覆盖、404 与 500 区分。3 MiB 可容纳两份各 1 MiB 的 base64 及元数据。亲核 `server.go:2903` 的全局请求体上限来自 ClientConfig，默认值见 `lib/config.go:675` 为 100 MiB；应用内 3 MiB 校验可以限制解码/落库，但不能宣称接收阶段只分配 3 MiB；用户将全局值设得更小时，上游会先拒绝。无需为本案改全局默认，文档和测试应准确表达此边界。

ETag/当前 hash 匹配、清除后旧 URL 404 与 must-revalidate 相容。条件 GET 必须先确认当前槽位/当前 hash 有效，再返回 304，否则旧 If-None-Match 会在 reset 后错误续用旧图。

### §4.3 UI 与图标回退

亲读 `useBranding.ts:134-177`，当前 icon 独立回退默认图，确实不能满足“空 icon 沿用 Logo”；只改共享回退选择而不复制 hook/侧栏是最小落点。侧栏 `sidebar.tsx:1452,1469` 已有 object-contain，登录 view 与 pending card 也有尺寸限制，因此不必为本案改布局。OSS skip query 路径保留默认，可用现有 Vitest 的 @ alias 写行为测试。

草稿/已保存状态分离、请求号防旧读取覆盖、对象 URL 回收、操作互斥、失败保留草稿和恢复确认均明确。只发送脏槽位与后台合并一致。独立 icon 优先、仅 logo、仅 icon、全空、两主题、OSS 缓存残留应实际断言。现 hook 注释还声称独立回退，实施改逻辑时须同步相邻注释；该必要文档变化应包含在共享文件例外里。

### §5 实施步骤

数据库 → handler/认证 → UI → 临时二进制 smoke → 浏览器的顺序可以逐步检查。旧 smoke 的个人 DB、固定端口/按端口清理不应运行；新独立临时目录与仅管理自有 PID 的方案吻合路线图的隔离要求。既有 `ee/Makefile` build/test 会经 workspace 修改 go.work，拟用 GOWORK=off 直接构建避免扩修 Makefile，合理；build-ui 仍会重建覆盖和 embed，须先确认生成目录属于本任务可再生内容。

### §6 测试策略

SQLite 重开、合并并发、错误原子性、真实 APIMiddleware、缓存回退、真实二进制重启及浏览器输入/取消/失败覆盖主要风险，独立测试角色符合 L3。迁移用例须按 B1 补齐失败与锁边界。

PostgreSQL 部分不能以 SQLite 测试冒充。依据 `规范/风险分级.md`“缺账号、数据、服务或平台条件时记为阻塞”，若实施后没有隔离 PostgreSQL 条件，必须记作 **PostgreSQL 验收阻塞**，不能只写“未验证”而机械全绿即视为满足全部数据库承诺。用户若决定缩小验收/交付范围，应记录明确裁决及未交付能力；本轮不要求现在启动实例，也未运行测试。

### §7 验收与 checklist

**B2（阻塞）：**正文承诺基线到工作树的改动白名单（含未跟踪），实际 checklist 仅有分支/SHA/暂存/diff-check/hash、build/test 等，未检查允许改动路径，也没有 Go/TS 格式检查。`git diff --check` 只检空白问题，不是 gofmt/Oxfmt；它也不检查新未跟踪文件内容。当前配置即使改了共享导航、覆盖脚本或别的上游文件，也可以通过。根 AGENTS.md 明确要求格式检查，工作台要求机械项与 checklist 同源。

修订应在 checklist 加可执行、只读的路径和格式守卫：比较指定基线的 tracked diff，合并非忽略 untracked 文件，允许本案精确业务/测试文件、过程文档、生成视图及原调研；原调研仍核 hash，不把整个 ui/ee 宽泛放行。必要的子组件/测试/校验工具路径在方案中明确。检查不应暂存、清理或重置他人文件。格式检查应覆盖本案新增与修改 Go/TS 文件，避免全仓格式化产生越界修改。

### §8 风险、禁止事项与 Gate 待决

FIND-013 的触发是“第一个 B 功能落地或第一次对外构建前”，不是仅正式发布；Logo 已命中前者。方案正面提出延期并交 Gate 1 接受，不能由评审替用户接受。路线图要求公共迁移/构建先由单一负责人整合，当前仅沿用出口、不修探针/Makefile 是边界变更建议，需明确负责人/整合责任或在公共准备未完成时保持阻塞，不可默认为“独立分支天然获豁免”。

以下均仍待 Gate 1：标准级单期采用 L3 证据；表及公开读/鉴权写接口；共享 hook 例外；公共基础隔离/整合安排；FIND-013 延期风险。复核通过只表示方案可供裁决，不代表任一项已获批准。图片格式/像素限额可作为普通实施选择，不应追加无必要素材审批。

2. **B2，未关闭/阻塞：**如果实现者修改 `ui/components/sidebar.tsx` 或添加未经许可的业务文件，当前 checklist 是否必然失败？答案是否；需增加实际机械守卫。格式不合规的新增文件亦无现有守卫。
3. **Gate 待决：**FIND-013 是否已被裁决延期，公共 bootstrap/迁移整合是否已明确负责人？当前材料仅“建议”，无批准事实，不能进入实施。
4. **验收待验证：**同一临时数据库重启后，图片字节/hash 是否不变；PostgreSQL 迁移失败是否不留成功版本？本轮未执行，方案评审不能给出运行时通过结论。

## 建议栏（不立案）

- 认证回归加 Cookie、Basic/Bearer 的实际使用路径，且写清无白名单前提；不用扩建多人权限系统。
- PUT/Reset 成功状态的读取应明确发生在何时，避免“写入已提交、随后 Read 失败而返回 500”与“所有存储失败均不改变旧配置”的承诺相冲突。可让需要返回的状态在同一事务内取得后再提交，或明确区分已提交后的响应故障。
- hook 的缓存注释包含“长 max-age”“server-side 重写品牌”的描述，但当前 EEShellRewriter 只注入 meta。本案不应承诺未做的无闪烁首屏/浏览器历史图回收；无需扩写服务端品牌注入功能。
- 新图片接口公开会提供完整上传字节；按当前产品需求可接受，不额外引入资产服务。使用几何测试图与隔离数据即可，避免把私人素材写入证据。
