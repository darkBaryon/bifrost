## 可证伪质疑

### R1（阻塞）：只读路由账号进入列表时，哪些附属请求会实际发出？其他已开放页面的按钮范围如何验收？

**亲核事实：**

- `ui/app/workspace/routing-rules/views/routingRulesView.tsx:111` 和 `:159` 在空列表、非空列表两条分支都挂载 `RoutingRuleSheet`，没有按 open 或权限阻止挂载。
- `routingRuleSheet.tsx:87–90` 无条件调用规则、厂商和全部 Key 查询；UI 的 open=false 不会阻止这些 hook。`ee/internal/rbac/host/routes.txt:567–575` 明确要求 `/api/keys`、`/api/providers` 具备 ModelProvider.View。只有 RoutingRules.View 的账号会得到这些请求的 403，替换 RBAC Context 或外层路由守卫不能阻止已允许页面内部的请求。
- `routingRuleInfoSheet.tsx:46–55` 只按 scope/id 决定团队、客户、VK 详情请求，没有按对应权限控制。若本期允许点开这类规则，需给缺少关联实体权限的账号确定显示降级和请求策略。
- 更广的按钮目标也不能仅靠现有 Context 解决。例如 `plugins/page.tsx:17`、`plugins/sheets/addNewPluginSheet.tsx:61–62,148` 只使用 Plugins.Create/Update；后端 `rbac/host/plugins.go:128–139` 对原生插件还要求 Plugins.LoadNative。后端拒绝能保护操作，但并不兑现前端“按本人权限显示按钮”的承诺。

**影响：**方案 §4.4 明确承诺测试账号所用页面的按钮/请求控制，§4.5 又禁止修改上述页面，当前白名单没有覆盖可实现路径。仅断言列表存在、创建按钮消失，会漏掉附属请求；仅测试管理员/路由只读/无角色，不能证明其他获准页面的敏感按钮。

**最小关闭方式：**v2 列出本期实际开放的页面及首页次序，区分本期保证的操作/请求控制和暂不交付的复杂操作；将已证明必要的最小接入点加入白名单并说明默认行为，或给出已验证可在 EE 覆盖层实现的路径。测试至少断言只读路由账号在空/非空列表不请求无权厂商/Key，及范围内的详情降级；对明确纳入的敏感按钮补代表性权限组合。若要缩小已经确认的交付范围，应列为 Gate 取舍，不能靠“只测某个账号”隐式缩小。此项不要求补账号/角色 CRUD，也不要求重写全部上游页面。

### R2（阻塞）：未提供 EE 扩展时原行为如何保持，提供后在哪个调用点阻止旧查询和旧连接？

**亲核事实：**

- `product/上游改动/README.md:15–16` 要求工程方案给出上游修改的“接口签名和执行时点”，并以可选扩展保留默认行为。方案 §4.5 目前只有用途表及“一处定义契约类型”，尚未提供可核对的签名、默认值或触发点。
- `ui/components/topbar.tsx:135` 在账号菜单渲染前已调用 `useGetCoreConfigQuery`；只替换菜单展示不会取消订阅。方案只明确 ClientLayout/Sidebar 切窄配置，未说明 EE Topbar 何时停用这条旧请求。这直接影响 §4.4 的无权设置 URL 不发配置查询及没有 Settings.View 的工作台请求边界。
- `ui/hooks/useWebSocket.tsx:70–85` 使用原生 fetch，票据非 2xx 仍建立 Cookie 连接；不会经过 RTK 的 EE HTTP wrapper。当前卸载也不关全局连接。仅描述 enabled/账号作用域，尚不足以核对“EE 401 通知身份失效、403 停止、OSS 保持旧失败回退”的实现契约及异步请求返回后的失效处理。
- 新 bootstrap 不能简单列入现有 managed 分类：`rbac/host/routes.go` 拒绝无权限的 managed 项，`authorization.go:44–46` 拒绝非 managed 进入 Prepare；`host/auth.go:264` 只为已知自管路由绕过管理权限链并交由自身认证。现有 AdditionalRoutes 装配给 RBAC。方案已要求登记所有权，但尚未指定 bootstrap 的实际登记/分流拥有者。

**最小关闭方式：**为真正需要的扩展列出参数/返回值、定义位置、调用顺序及 EE/OSS 默认矩阵；不需要预写完整组件。至少明确 SessionBoundary/RouteBoundary、窄配置、首页/导航、账号菜单、通知/WS 的可选接口；保证 Topbar 的 legacy 查询只在 legacy 路径执行；明确票据 HTTP 失败如何交给 EE、连接在禁用/换账号/卸载时如何失效，而 fallback 保持原行为。bootstrap 明确由哪一宿主处理器注册、谁验证 Cookie/Origin/正文、在路由清单使用何种归属，以及为何不会绕过认证或误入 Settings.View 链。增加相应契约回归，不必引入通用插件框架。

## 建议栏（不立案）

- **S1：修正 Finding 引用。**方案 §8 所述 HTTP 状态/code 问题现编号为 FIND-030；`workbench/findings.md` 明确旧 FIND-022 已因重号更名。修正当前方案链接即可，不要求本期统一全局错误协议。此项不影响执行行为，不作阻塞。
- **S2：避免无必要的上游改动。**`useOnboardingChecklist({skip})` 已把 skip 传给全部查询；如果 ClientLayout 不挂载 Widget、Sidebar 正确传 skip 就已足够，可以移除该 hook 的计划修改。白名单是允许范围，不是必改清单。
- **S3：让账号切换断言覆盖完整状态所有权。**除 `baseApi` 外，`store.ts` 还有 provider/plugin/app slice；provider 和 plugin 持有选中实体。实施时复用现有清理动作或完整导航，测试验证无旧实体闪现，避免只清 Query 缓存。方案已承诺清旧缓存，这里是验收落点提示，不要求另建状态系统。
- **S4：检查脚本保持可审计。**将格式/类型/单测、EE/OSS 构建和测试二进制来源显式列入脚本输出；构建隔离注意 `npm run build` 的 copy-build 会写 transport UI，`sync.sh` 会重建 overlay。方案已要求可控生成目录，实施证据应能核对该事实。
