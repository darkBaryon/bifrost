## 给用户的摘要

现在审计页面是占位；建议第一期做成“管理操作发生后，可以查到谁操作了哪个对象、接口处理结果如何”。
先使用 M0 的 Handler 包装、数据库与 UI 覆盖层，不重新搭 infra。
首期明确为 HTTP 管理操作审计，不把请求字段冒充已提交的数据库变更。
同步处理骨架验收要求的 migrator 与 GOWORK=off 两项技术债。
待确定：是否接受首期没有完整旧值/新值；审计写入失败是否允许业务继续；鉴权关闭时是否允许查看审计。
当前为设计草案，未完成接口覆盖穷举、身份路径验证、checklist 和独立方案复核，不可直接按此实施。

## 2. 现状与约束盘点

- `ee/transports/bifrost-http/server/bootstrap.go:22`：prepare → 上游 Bootstrap → attach；当前没有替换 OSS 鉴权。
- 同文件 attach：已有 ConfigStore.DB、SyncLoadedPlugin、Router 与 Server.Handler 接入。数据库仍裸 AutoMigrate；后续审计用独立功能装配函数，attach 保留编排职责（FIND-012）。
- `transports/bifrost-http/handlers/providers.go:144`：provider/key CRUD 按方法和路由注册，可建立动作映射，不能只判断 POST/PUT 就认为是配置变更。
- `transports/bifrost-http/handlers/middlewares.go:1093`：APIMiddleware 有公开和可配置白名单；仅调用它不保证审计查询一定要求真实认证。
- 同文件 `:1163` 附近：关闭鉴权会同时设置 IsLocalAdmin 和 AuthBypassed；必须先识别 bypass，不能单凭 IsLocalAdmin 记录已登录管理员。
- `transports/bifrost-http/handlers/session.go:96`：登录创建 session，仅保存 token 与有效时间等，没有用户 ID。不能将提交的 username 或未验证的 header 当真实身份。
- `framework/configstore/store.go:947`、`rdb.go:381`：有 RunMigration 和 RefreshConnectionPool，可走上游数据库迁移连接机制。
- `framework/migrator/migrator.go:46`：支持单独的迁移记录表；ee 使用自己命名空间，不能污染上游 migration ID。
- `ee/ui/sync.sh` 和审计占位组件：复用 UI 覆盖层，业务代码写在 ee/ui，生成目录不直接编辑。
- ServerCallbacks 无法替换，外层中间件不天然掌握已提交字段差异；不复制上游 handler 或盲目使用 GORM 回调冒充语义审计。

## 3. 目标 / 非目标

**目标**：形成一条管理操作 → 安全事件构造 → 数据库保存 → 受保护查询 → 页面展示的闭环。

候选覆盖：provider/key、VK、团队/客户、预算/限流、路由及系统配置的变更，登录/退出与权限拒绝。正式范围以复核前补齐的逐路由清单为准，不把此候选清单视为已验证全覆盖。

**非目标**：推理正文审计、RBAC、多用户、外部导出、签名存证、配置文件启动变更、后台同步任务及 SDK 内部操作。首期不保证完整旧值/新值、业务事务原子性或跨实例一致性。方案必须让页面与文档表达这些边界。

## 4. 接口与数据设计

### 4.1 分层与装配（建议）

- `ee/framework/audit/`：事件类型、存储、迁移和记录服务；不依赖 transport，不做泛化仓储框架。
- `ee/transports/bifrost-http/handlers/`：动作映射、HTTP 采集与查询 handler；不把 RequestCtx 传给后台 goroutine。
- `ee/transports/bifrost-http/server/audit.go`：RegisterAudit 装配数据库、服务、路由和中间件，返回启动错误；attach 调它。
- `ee/ui/app/enterprise/components/audit-logs/`：替换占位页，增加列表、筛选、详情与失败状态；前端不承担鉴权。

RegisterAudit 只负责装配；Recorder.Record(ctx, event)、Store.List(ctx, filter)、Store.Get(ctx, id) 承担业务。精确 Go 签名在复核前锁定。

### 4.2 事件模型（草案）

表 `ee_audit_events`，字段建议：

| 字段 | 含义 |
|---|---|
| id / schema_version | 服务端事件 ID、事件格式版本 |
| started_at / completed_at / duration_ms | UTC 时间与耗时 |
| actor_kind / actor_id / actor_display / auth_method | local_admin、anonymous、auth_disabled 或 unknown；未来 B2 增加 user；不存凭据 |
| action / resource_type / resource_id | 服务端定义的动作与目标；无法确认 ID 时留空并标识，不捏造 |
| route / method / request_id | 规范化路由与服务端关联 ID，不保存完整 URL/query |
| peer_ip | 默认连接来源地址；没有可信代理配置时不信任 X-Forwarded-For |
| result / http_status | HTTP 层 succeeded/failed/denied/unknown；HTTP 成功不声称业务事务原子成功 |
| submitted_fields / summary | 可选、受限的允许字段名或服务端摘要；明确是提交信息，不是数据库差异 |

只保存经过允许清单构造的数据，长度与数量设上限。禁止保存原始 body、Authorization、Cookie、完整查询串、上游错误正文或任意 ExtraParams。路径参数可能含敏感值，逐路由决定可存字段。登录失败的账号输入不作为 actor_id。

首期针对创建操作，只有已验证的响应结构才提取资源 ID，其他情况记录资源类型和动作；不整段复制响应。默认不实现 before/after，避免并发修改、密文和缓存造成错误差异。

### 4.3 采集和身份

外层中间件先用明确路由清单匹配管理操作，再保存有限元数据；next 返回后读取状态与可信鉴权标记，构造事件并保存。匹配清单不能用宽泛 URL 前缀把推理接口纳入。

路由匹配、失败请求及身份要单独验证：外层执行前还没有路由参数，不能假定此时 RequestCtx 已有 provider/key_id；内层返回后标记是否仍在、各认证分支是否一致，也不能只靠注释假设。

actor_kind=local_admin 只在认证确实成功时赋值，显示当前配置的管理员名称也不等于识别共享账号背后的自然人；必要时由 resolver 在认证有效窗口获取身份快照。改名/注销操作、登录成功、白名单、Basic/Bearer/Cookie 分支均需明确规则。无法验证时使用 unknown/anonymous。

审计 GET 自身默认不产生日志，避免递归；查询被拒绝是否作为安全事件另行明确，并限制异常流量造成的存储放大。

### 4.4 写入失败策略（待决策）

建议首期使用带超时的同步写入：管理请求量低，避免引入内存队列和退出排空协议。写入失败暴露计数、结构化错误与最近失败时间；日志本身不带敏感事件正文。

必须明确：业务 handler 执行后，即使审计写入失败，也无法撤销已发生的操作。建议保留原业务响应并报告审计异常，不返回伪造的“修改失败”诱发重试。此方案有业务已完成但事件未保存的窗口，不能宣称不丢记录。超时数值在性能实验后确定。

如果用户要求“没有持久审计就不能修改”，需要重新设计持久意图记录、结果状态和恢复核对，或业务事务内 outbox；单纯 next 后写库不满足。数据库事前探测也不能保证事后一定可写。

### 4.5 查询 API（拟定契约，待复核）

- `GET /api/ee/audit/events`：时间区间、action、actor_kind/actor_id、resource_type/resource_id、result、cursor、limit（建议默认 50，最大 100）。
- 响应 `{items, next_cursor}`，按 started_at 与 id 稳定降序，不默认做全表 count。
- `GET /api/ee/audit/events/{id}`：单条详情；不存在 404，参数不合法 400，存储失败 500。
- 索引先覆盖时间排序及已确定的筛选组合，用 SQLite/PostgreSQL 查询计划确认，不为每个字段盲目建索引。
- 复用 APIMiddleware；建议另要求真实本地管理员身份，鉴权关闭或白名单绕过时拒绝读取审计。此行为需用户确认；不启用 IsEnterprise，不扩大成 RBAC 改造。
- 不提供修改和逐条删除接口。拟首期默认不自动删除；保留清理期限尚未确定，正式实施前必须定义容量提示与清理策略，不能擅自采用固定天数删记录。

### 4.6 两项既定技术债与探针处置

使用 RunMigration + migrator 的组合，独立 `ee_migrations` 记录表，先核实 PostgreSQL 并发迁移锁及事务边界；启动迁移失败不启动正式 API。若需刷新运行连接，必须在服务捕获 DB 句柄之前处理，避免持有旧连接。

build/test/smoke 使用 GOWORK=off，复用 ee/go.mod 本地 replace；不得只改 ee 编译而漏掉 smoke 内 OSS 对照的 go run。测试应使用临时配置、独占进程及端口，不能沿用按端口杀进程的方式影响其他会话。

FIND-012：本次拆出按功能装配。FIND-013：建议生产装配停用 ee_probe 插件与公开 ping，测试改验真实审计链路；旧 ee_probe 表先保留，不自动删历史表。标记头/meta 是否保留在复核中列为明确清单。FIND-015 因新增可复现验收需处理测试隔离。台账待方案通过后再按事实更新，不提前标已解决。

## 6. 测试策略

- 固定测试凭据放入请求后，检查数据库、查询响应与错误日志均不出现原文。
- Cookie/Basic/Bearer 登录、无凭据、过期 session、auth disabled、白名单、配置改名、登录失败分别断言 actor 与读取权限。
- 修改 Key 成功/校验失败/目标不存在/权限拒绝，确认动作、对象、状态与事件数量；普通 GET 和推理请求不误记。
- 并发修改不捏造 before/after；超长/恶意路径和字段不突破事件大小限制。
- 注入 DB 写入失败、查询失败、超时；确认响应策略、异常计数与无明文日志。
- 空库、M0 旧库、重复启动、SQLite 锁竞争和 PostgreSQL 迁移/查询；回滚二进制后上游仍能启动并读原有配置。
- 页面筛选、分页、详情、空态与错误态；两种构建环境类型检查；原 VK、预算限流及流式调用回归。

当前尚处草拟阶段，不生成声称可执行的 checklist。逐路由清单、失败策略和接口冻结后，按模板补 `checklist.yaml`，与最终测试命令一一对应，再进入独立方案复核。

## 8. 风险与禁止事项

不擅自修改上游 handler；不抓原始正文后再靠黑名单脱敏；不信任调用者自报身份；不把 HTTP 操作结果描述成不可篡改的事务审计。

最大风险：同步的事后写入仍有丢事件窗口；身份标记路径不统一可能造成误归因；中间件只覆盖 HTTP 管理入口。用户若不接受这些边界，必须修订方案，而不是在实现时隐藏差异。

## 9. 回滚口径

回退业务二进制/覆盖层，保留新增审计表和迁移记录，不自动删除事件。所有新增表使用 ee_ 前缀；不得修改上游业务表结构。迁移向后兼容、启动恢复与审计中断的告知方式纳入验收。
