## 3. 本轮修复项

**R1｜P1：用 provider 可控的错误类型识别可信错误，导致送检内容写入日志**

位置：[judge.go:132](/Users/xinyue/VSCode/ws_2026/bifrost-content-safety/ee/internal/guardrails/host/judge.go:132)，相关输出位于同文件第 112–120、76 行。

- **代码事实**：`fromProviderResponse` 仅凭 `Error.Type` 等于 `provider_connection_failed` 或 `upstream_credentials_exhausted`，就允许保留 `code` 和 `message`。但 [openai/errors.go:99](/Users/xinyue/VSCode/ws_2026/bifrost-content-safety/core/providers/openai/errors.go:99) 会直接从 provider 响应复制这些字段；类型名称不能证明错误来源。
- **触发条件与后果**：provider 返回 HTTP 502，例如：
  ```json
  {"error":{"type":"provider_connection_failed","code":"送检内容","message":"送检内容"}}
  ```
  本轮使用真实 EE 二进制和本地 provider 替身验证：两个白名单类型都把回显标记写入判官日志，每种产生 **4 条**泄露记录；普通 `server_error` 对照为 **0 条**。客户端仍返回安全的 `content_safety_check_failed`，问题发生在服务端日志。
- **测试缺口**：[host_test.go:143](/Users/xinyue/VSCode/ws_2026/bifrost-content-safety/ee/internal/guardrails/host/host_test.go:143) 的 provider 对照使用另一种类型，没有覆盖“provider 返回与网关合成错误同名类型”。
- **最小修正**：这两个分支只输出本地固定诊断，不复制可控的 `code/message`；如确需保留网关原消息，须依据不能由响应正文控制的来源信息。补充两个同名类型的回显回归，同时保留真实连接失败、key 耗尽的诊断覆盖。
