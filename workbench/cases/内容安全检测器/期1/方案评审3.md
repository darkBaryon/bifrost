## 上轮阻塞处置核对

**阻塞 A（拍板项量化口径）—— 关闭。**

- 拍板 4 改为「约 5 千汉字」。核算 16384 ÷ 3 = 5461.3，方案取「约 5 千」略保守，方向正确，不会再让用户高估可用长度。
- 摘要首段改为「单阶段最坏等于 `judge.timeout_ms`（默认 10s，含重试）」，与 §4.2 的重试预算（退避合计 1.4s，其余留给调用）一致。§8 的风险条目未同步，见放行前提 1。
- 拍板 5 补「合计 5 次」「每请求 ≤0.1 元」，并引 `core/providers/utils/utils.go:355-365` 说明被取消的调用仍计费。该引用本轮复核：该函数注释明确「does NOT truly cancel the underlying fasthttp network request」，取消只停止等待，因此按「启用项目数」计费是正确口径而非高估。拍板 5 表述准确。
- 拍板 6 补了后果句（阈值 `high` 时通用命中只记录、`medium` 则拦），与 §4.1 的 `generic-*` → medium 映射一致。

**阻塞 B（16KB 超限的失败路径）—— 关闭。** 三段链路逐段落到现有结构：

1. **检测器侧**：§4.2 超限返回 `guardrails.ErrDetectorTextTooLarge` 且不重试。检测器返回 error 是 `detector.go:23-25` 既有契约内的用法，不改接口。
2. **框架侧**：§4.3 新增 `Failure` 取值 `TextTooLarge`。`Failure` 是 `evaluation.go:20-27` 的字符串常量组（现有 `detector_error`/`detector_timeout`/`invalid_result`），加一个常量即可；分类点在 `evaluation.go:57-61` 的 switch，加一个 `errors.Is(err, ErrDetectorTextTooLarge)` 分支排在 `err != nil` 之前即可，`evaluation.go:73-75` 随后照常把它记成 `Outcome=Failed` + `Action=rule.OnError`，与拍板 4 的「按该规则 `on_error` 处置」严格一致。哨兵放业务根包，与 `checker.go:26-29` 的 `ErrInvalidInput`/`ErrTextTooLarge` 同处，命名不冲突。
3. **插件侧**：§4.3 的映射「`TextTooLarge` → `content_safety_text_too_large`，其余 `Failed` → `check_failed`，`Matched` → `content_safety_blocked`」可直接落在 `plugin/plugin.go:115-124`；错误码常量 `textTooLarge` 与文案「内容超过安全检查长度上限」`deny.go:21,38` 都已存在，无需新增常量。两种超限（`max_text_bytes` 整体超限走 `Check` 返回的 `ErrTextTooLarge` + `deny.go:53-59`，判官 16KB 超限走本链路）共用同一客户端错误码但日志可区分（`plugin.go:110-114` 输出 `failure=text_too_large`），运维区分与用户提示两个诉求都满足。

评审 2 指出的「用户看到『内容安全检查未完成』、运维无法区分故障与超限」已被消除。

## 放行前提（实施第 1 步一并订正，不另起版本）

1. **§8 第一条风险仍是旧口径。** 现写「判官延迟：每阶段最多一次调用时长（并行），两阶段叠加」，与本版摘要「单阶段最坏等于 `judge.timeout_ms`（含重试）」矛盾。风险章是实施与运维实际会读的一节，须改成同一口径。
2. **§6「插件」一条未随三分支更新。** 现写「`Blocking.Outcome` 两种取值对应两种错误码」，而 §4.3 已是三条映射（`Matched`→blocked、`Failed`+`TextTooLarge`→text_too_large、`Failed`+其余→check_failed）。断言必须覆盖三条，尤其是新增的超限分支——它是本版唯一的新增对外行为。
3. **§7 文字滞后。** 仍写「见同目录 `checklist.yaml`（v2 同步：…）」，未提本版新增的 `TextTooLarge` 必含符号与基线由 `c05dba215` 改为 `dba55b14b`。checklist 文件本身已正确更新（本轮读过 diff），只是方案正文没跟上。

## 本轮建议项（不阻塞）

1. **`ConfigStore` 为 nil 的拒启分支实际不可达，宜说明而非当作新策略。** `ee/internal/app/bootstrap.go:52-54` 在调用 `assembleGuardrails` 之前已经统一拒绝：`"ee requires the config store (database mode); config_store.enabled=false is not supported"`。所以「`ConfigStore` 为 nil 时拒启」不是本功能引入的新限制，保留防御式判断没问题，但方案里宜注明它由 bootstrap 前置保证，避免读者以为内容安全额外收紧了部署条件。
2. **两个哨兵错误必须彼此独立，不能用 `%w` 相互包裹。** 若 `ErrDetectorTextTooLarge` 被定义成包住 `ErrTextTooLarge`，`deny.go:53-59` 的 `mapCheckError` 与 `evaluation.go` 的分类会互相串（检测器超限会被误当成整体文本超限，反之亦然）。建议在方案或代码注释里写明二者无 wrap 关系，并在测试里各断言一次 `errors.Is` 的否定方向。另建议插件对 `Blocking==nil` 做一次兜底（按 `check_failed`），不变量成立时它是死代码，但可避免钩子内 panic。
3. **判官失败类别只进了框架日志，适配器日志仍只记「成功与否」。** §4.4 的 Info 日志建议带上失败类别（超时 / HTTP 错 / 解析失败 / 空响应），这是区分「提示词让模型输出了非 JSON」与「上游故障」的唯一线索，且不涉及原文。§4.2 把四类都折叠成「一次失败」后，框架侧只能看到 `detector_error`。
4. **`guardrails-file-size` 仍只扫 `ee/internal/guardrails`。** `ee/internal/app/guardrails.go` 本期要长出完整配置解析与拒启校验（§4.5 列了十余条），最可能触到 500 行红线的就是它，建议把它纳入该检查的路径。
5. **`Blocking` 的措辞「指向 `RuleEvaluations` 中的副本」略含混。** 由于 §4.3 已保证汇总发生在 `WaitGroup` 之后、切片不再追加，指向切片元素是安全的；建议直接写「指向 `RuleEvaluations` 中的对应元素（汇总后切片不再变更）」，免得实施时纠结要不要另存一份。

## 剩余风险

- **判官可用性即服务可用性**：`on_error=block` 下 DeepSeek 抖动或限流会变成全量拒服务；期 1 无运行期降级开关，只能改配置重启。
- **16KB 上限未用真实长度分布校准**：上线后可能成片出现「长对话被拒」。本版已把它变成可识别的 `content_safety_text_too_large`，可观测性足够，但阈值是否合适只能靠上线后数据。
- **密钥规则误报**：长度多来自第三方扫描器推断，止血只有 `ignored_keywords` 且改动要重启；无「先仅记录」的灰度口径。
- **提示词效果不验收**：隐晦表达、多轮铺垫、长文本的漏判本期无断言，真实准确率只进独立验证记录。
- **改动触及刚交付的框架**：`Checker` 执行模型、`CheckResult` 结构与插件错误码同时变更，回归面大于新增检测器本身；`ee-race` 与既有集成测试是主要护栏。
