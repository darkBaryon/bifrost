## 上轮阻塞处置核对

**阻塞 B —— 关闭，机制逐层核实成立。** 这是本轮的核心核对，四个环节都对上了：

1. **前置钩子的写入落到请求根 ctx。** `core/bifrost.go:7884-7886`：`pluginCtx := ctx.WithPluginScope(&pluginName)` → `PreLLMHook(pluginCtx, req)` → `pluginCtx.ReleasePluginScope()`。`WithPluginScope`（`core/schemas/context.go:862-880`）构造的作用域 ctx 把 `valueDelegate` 指向根 ctx；`SetValue`（`:474-478`）在 `valueDelegate != nil` 时直接委托根 ctx 写入。`ReleasePluginScope`（`:893-897`）只释放日志存储引用，不动已写入根 ctx 的值。所以前置钩子写的快照在本次请求内一直存在。
2. **非流式后置钩子读得到。** `core/bifrost.go:8028-8030`：同样 `ctx.WithPluginScope(&pluginName)`，`Value`（`context.go:386-388`）在 `valueDelegate != nil` 时委托根 ctx 读取，根 ctx 是同一个。
3. **流式每个 chunk 也读得到。** `core/bifrost.go:8001-8008`：流式分支把每个插件的作用域 ctx 缓存在 `p.streamScopedCtxs`，由 `ctx.WithPluginScope(&name)` 创建，`ctx` 仍是本次请求的根 ctx，于是每个 chunk 的 `PostLLMHook` 读到的还是同一份根值。**并且不会串请求**：`PluginPipeline` 取自池（`:8472`），但 `resetPluginPipeline` 在归还前释放并置空 `streamScopedCtxs`（`:8319-8322`），所以缓存不会跨请求复用。
4. **`blockRestrictedWrites` 不挡我们的 key。** 前置与后置钩子期间根 ctx 都处于 `BlockRestrictedWrites` 状态（`:7867`、`:7991`），但 `SetValue`（`context.go:479-483`）只在 `isReservedKey(key)` 为真时丢弃写入；`isReservedKey`（`:49-56`）先断言 `key.(BifrostContextKey)`，非该类型一律返回 false，而 `reservedKeys`（`:19-44`）里也没有任何插件私有 key。所以用包内私有 key 写入不会被静默丢弃。

结论：§4.4「热更新只影响 Swap 之后到达的请求，已准入的流不会中途改判」的机制可实现。两处语义细节见放行前提 1、2。

**阻塞 A —— 关闭。** §4.6 的 `app` 流程改为「无行以 nil 启动；有行则 Build，失败拒启」，§8 列出代价，§6 补了「启动时坏配置拒启（单测）」。与 §4.6 的 `update` 路径（Build 失败返回 400）方向一致，不再是同一错误两种安全默认。恢复说明的措辞需订正，见放行前提 3。

## 放行前提（实施时订正，不另起版本）

1. **把「快照缺失」和「快照为 nil」写成两种明确状态，并让后置钩子在缺失时透传而不是回读当前指针。** §4.4 现在写「`PostLLMHook` 优先读 ctx 快照，缺失时才读当前指针」。若实现时在快照为 nil（未配置）的情况下**不写 ctx**，那么一个在无规则状态下被准入的流式请求，遇到中途 `Swap` 进含输出规则的配置后，后置钩子会回读到新指针，重新落回评审 4 阻塞 B 的路径：`plugin/text.go:69` 判 `choice.ChatStreamResponseChoice != nil` → `errUnsupported` → 中途注入错误。两条都要写死：(a) 前置钩子在最早处无条件写入快照（包括 nil，以及 `plugin.go:52-55` 那条「无任何规则直接返回」的早退路径之前）；(b) 后置钩子在快照缺失时直接透传——缺失只可能是前置钩子没跑过（`RunPostLLMHooks` 的 `runFrom` 保证后置只对跑过前置的插件执行），此时本就不该检查。§6 的「Pre 后 Swap，Post 仍用旧快照」用例请加一条 nil→非 nil 的方向。
2. **前置钩子在 fallback 上会重跑，快照要「只在缺失时写入」。** `core/bifrost.go:7920` 明确「unlike PreLLMHook (which runs again on every fallback)」。按现在的措辞，回退到另一个 provider 时前置钩子会再读一次指针并覆盖快照，若期间发生 `Swap`，同一请求的后半程就换了配置，与 §4.4 承诺的「只影响 Swap 之后到达的请求」不符。写成「ctx 中已有快照则不覆盖」即可。
3. **§7 的基线文字与 §4.6 的恢复说明各有一处不准。** §7 仍写「（v4 同步：基线 `1a061b046`…）」，而 checklist 实际已是 `b9e8752ea`、§1 起点也是 `b9e8752ea`；§4.6 的「修复 provider 或调用 reset 前先删除 `ee_guardrails` 行」读起来像要先删行再调 reset，实际情况是**拒启后接口不可用、reset 根本调不到**，唯一恢复手段是修复 provider 或直接删表行。请把这句改成运维看得懂的两条路径。（顺带：§5 步骤 1 末尾「订正本方案 §6/§7/§8 口径已在 v4 完成」是历史备注，留在实施步骤里会误导；「Gate 决策结果」仍写「待 v4 复核」。）

## 本轮建议项（不阻塞）

1. **fasthttp / core/schemas 的禁留仍漏掉根包其余文件与两个子包。** 现在根包只钉了 `checker.go` 一个文件，`rule.go`、`evaluation.go`、`detector.go` 以及本期新增哨兵可能落到的新文件都没覆盖；`core/schemas` 禁留也只有 `detectors`、`config` 两处。建议改成一条必过命令，一次覆盖根包全部文件：`find ee/internal/guardrails -maxdepth 1 -name '*.go' -exec grep -l 'fasthttp\|net/http\|core/schemas' {} \;` 配 `expect_empty: true`（`preflight.py:50-55` 支持该语义，同类命令本机已验证可用）。
2. **`persistence` 与 `host` 可以各加一条 fasthttp 禁留（你问的那条成立）。** 先例 `ee/internal/branding/persistence/` 的两个文件只引 `context`/`errors`/`time`/`sqlite3`/`configstore`/`migrator`/`gorm`，不引 fasthttp；`guardrails/host` 走 bifrost client，也不该出现 fasthttp。加上这两条，能机械挡住「把 `*fasthttp.RequestCtx` 一路传进存储层或判官适配器」这类分层滑坡，代价为零。
3. **快照 key 建议用包内未导出类型。** 它写在**请求根 ctx** 上，同一请求里其他插件也能读到甚至覆盖。用 `type snapshotKey struct{}` 这类未导出零尺寸类型作 key，既避免与 `BifrostContextKey` 的保留键冲突，也让其他插件无法构造同一个 key。
4. **`get` 建议回报「当前是否生效」。** 阻塞 A 改成拒启后，「配置在库里但没生效」的窗口基本消失，但 FAKE 模式（此时 `update` 409）与 `Swap` 失败仍可能让库里的配置与运行态不一致。`{config, version}` 里加一个只读的生效标记，控制台就能自证，成本一行。
5. **锁键与行号两处顺手订正。** §4.6 的顾问锁键建议按评审 4 建议 8 在注释里与 `branding/persistence/migration.go:18-20` 互引；§2 的 `rbac/permissions.go:16,141` 改为 `:16,140-141`。

- **拒启换来的可用性代价**：判官 provider 被删或配置数据损坏会让网关起不来，而此时接口不可用，只能改库恢复。这是本版用安全默认换来的，已写进 §8，但运维手册（README）要给出明确步骤。
- **热更新窗口**：即便按放行前提 1、2 收紧，仍有「新配置对已在途请求不生效」的窗口，属设计内。
- **`Settings.Manage` 与安全开关同级**：能改缓存设置的人即可关停内容安全，已列为接受风险，期 2 随管理页面再评估。
- **64KB 送检上限的成本与延迟**：≤0.125 元/请求是按实验单价折算的估值，真实 token 与 p90 延迟要在独立验证记录里单列。
- **密钥规则误报、提示词效果不验收、改动触及刚交付的框架**：同前四轮，未变化。
