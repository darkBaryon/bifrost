## 结论

需修改。v4 因 Gate 1 裁决新增的持久化配置、读写接口与热更新，整体走的是仓内既有路子：`branding/persistence` 的迁移锁与 busy 重试、`branding/http` 的 `POST /api/x/get|update|reset` + `auth` 中间件、`rbac/host/routes.txt` 的登记格式与 `VerifyRoutes` 守卫，都被正确沿用且逐项核实可行；`Settings.View`/`Settings.Manage` 是现有目录里唯一合身的权限，不新增 RBAC 模块的决定成立；分级维持 L2 有先例支撑（品牌案同型，新增单例表、无数据迁移）。评审 3 的三处口径订正已全部落到 §6/§7/§8。

两条阻塞：**启动时构建失败以「不检测」启动**是一个未经用户签字的安全默认翻转，与本功能自己的运行期路径（update 构建失败返回 400 拒绝）和仓内既有做法（非法 `EE_GUARDRAILS_FAKE` 拒启、pricing `ErrConfig` 拒启）都相反；**热替换缺少「一次请求一份快照」的语义**，在流式请求上会把已准入的请求推进插件明确要避免的未支持路径。两条都能用一句设计决定关闭。

## 本轮阻塞项

**A. 启动时构建失败「以不检测启动」是未经裁决的安全默认翻转。**

§4.6/§8 规定：库里有配置但 `Builder.Build` 失败（provider 被删、数据损坏等）时只记 Error、以 nil 检查器启动，并称「安全上等同未配置」。三点可证伪的问题：

- **与本功能自己的运行期路径相反。** 同样是 Build 失败，`POST /api/guardrails/update` 的处置是返回 400 拒绝（§4.6）。同一种错误在两条路径上给出相反的安全默认，管理员无法形成一致预期。
- **与仓内既有做法相反。** 配置存在但不可用时，`ee/internal/app/guardrails.go:51-52` 对非法 `EE_GUARDRAILS_FAKE` 值是拒启（错误信息还提示「unset it to disable」）；`ee/internal/app/pricing.go:68-71` 对 `pricing.ErrConfig` 同样返回错误拒启。v4 在安全功能上反而比定价更宽松。
- **「安全上等同未配置」不成立。** 未配置是管理员知情的状态（他没开）；构建失败是管理员认为已开、实际全量放行的状态（他不知道），两者的知情度与需要的告警完全不同，而唯一信号是一条启动日志。`/api/guardrails/get` 此时仍会返回库里那份配置与版本号，控制台看上去是「已开启」。

这属于业务风险取舍，应由用户裁决而不是写在 §8 的「已接受风险」里——注意 v4 的「Gate 决策结果」段落列的是 6 项拍板，并不包含这条。要求 v5 二选一：(a) 改为拒启，与非法 FAKE 值、pricing `ErrConfig` 一致；(b) 保留以不检测启动，但升为拍板项交用户签字，并给出补偿：`/api/guardrails/get` 的响应增加「当前是否生效」字段（让控制台能看出防护未生效），且启动失败必须是 Error 级并在 README 写明排查路径。无论选哪个，§6 都要有对应用例。

**B. 热替换缺少「一次请求一份快照」的语义，流式请求会被推进插件明确要避免的路径。**

插件的流式准入是在 `PreLLMHook` 依据当时的 `HasRules(Output)` 决定的（`plugin/plugin.go:96-98`：有输出规则就拒绝流式请求），而 `PostLLMHook` 会在流式请求上按 chunk 被调用——`core/bifrost.go:7974,7989-7991` 的 `RunPostLLMHooks` 明确有 streaming 分支（"For streaming requests, it accumulates timing per plugin instead of creating individual spans per chunk"）。因此：

- 若在 `Pre` 通过之后、流结束之前 `Swap` 进一份**含输出规则**的配置，已被准入的流式请求会进入 `plugin.PostLLMHook` → `extractOutputTexts`，在 `plugin/text.go:69` 撞上 `choice.ChatStreamResponseChoice != nil` → `errUnsupported` → 中途向客户端注入「内容安全框架当前仅支持规范化的纯文本 Chat 内容」。这正是 Pre 阶段预先拒绝要避免的场景。
- 反向（`Swap(nil)` 或换成无输出规则的配置）则是：一个在「输出会被检查」前提下放行的请求，其回答最终不经检查返回。

v4 只说「`checker` 改为 `atomic.Pointer`，为 nil 时两个 Hook 直接透传」，没有定义同一请求的两个 Hook 是否使用同一份快照。要求 v5 明确其一：(a) `PreLLMHook` 取一次指针并把它带给 `PostLLMHook`（放进 `BifrostContext`，只是一个指针，符合架构 §6「`BifrostContext` 只保存小型句柄」），`Swap` 只影响此后开始的请求；(b) 明确接受按 Hook 各自取值，并在 §8 写明上述两种窗口行为、在 §6 增加「`Swap` 发生在 Pre 与 Post 之间」的用例。就本期只支持非流式输出检查而言，(a) 更省事也更好解释。

## 本轮建议项（不阻塞）

1. **`plugin_test.go` 的 nil 检查器断言必须列进改动范围。** `plugin_test.go:207-209` 断言 `New(nil, …)` 报错，与 §4.4 冲突；`plugin.go:31-33` 的构造校验也要重写（`checker.MaxTextBytes() <= 0` 这条在 nil 情况下不能再直接调）。请像 `checker_test.go:61-80` 那样在 §2 点名、§5 步骤 1 列入。
2. **checklist 删掉 `fasthttp` 禁留后，§2 的约束失去机械检查。** v4 §2 仍写「根包与 `detectors/` 禁止 `net/http`、`fasthttp`、`core/schemas`」，但 `禁留标记` 里的 `{grep: 'fasthttp', in: ee/internal/guardrails}` 已删除（因为新增的 `guardrails/http` 必然引 fasthttp，删得有道理）。建议按目录补回：`detectors/`、`config/` 各加一条 fasthttp 禁留；根包可用必过命令表达，例如 `find ee/internal/guardrails -maxdepth 1 -name '*.go' -exec grep -l 'core/schemas\|fasthttp\|net/http' {} \;` 配 `expect_empty: true`（`preflight.py:50-55` 支持该语义，本机已验证同类命令可用）。
3. **写明「能改缓存设置的人就能关掉内容安全」这一权限后果。** `permissions.go:141` 对 `Settings.Manage` 的定义是「修改常规配置、代理、功能开关和缓存设置」。把内容安全的开关与业务规则并入同一权限，意味着任何常规设置管理员都能停用全部检测且不需要额外授权。本期不新增 RBAC 模块是既定非目标，但这条后果应写进 §8（或拍板），而不是隐含在 routes.txt 的一行里。
4. **`update`/`reset` 建议并入已存在的分组。** `routes.txt:673` 已有 `@ managed Settings.Manage none ordinary` 组，直接在其下加两行即可；`decodeRouteManifest` 只拒绝重复路由、不拒绝重复分组头，但同头分组并存会让清单更难读。
5. **`EE_GUARDRAILS_FAKE` 的互斥只覆盖启动时刻。** §4.6 写「同时存在时拒启」，但假检测器启动后管理员调用 `update` 写入真配置会直接 `Swap` 掉假检测器，此时进程处于「日志声称在用假检测器、实际在跑真检测」的状态。建议明确：假检测器模式下 `update`/`reset` 返回 409（或明确允许并在 Swap 时补一条 Warn）。
6. **`version` 的边界要写死。** §4.6 的 `Update(config, expectedVersion)` 需写明首次写入（表中无行）时 `expectedVersion` 取 0、成功后版本自增、`Reset` 后版本回到 0 还是继续递增——这三点直接决定控制台的并发编辑体验，也是 409 用例的断言依据。
7. **`config` 包的类型定位要说明，避免与编码规范的类型分工规则冲突。** 硬规则要求「业务根包的类型不带 `json`/`gorm` 标签」。`guardrails/config` 的结构必然带 json 标签（它就是那份 JSON 文档），因此应在方案里说明：`config` 是序列化边界（接口与存储共用的 DTO），`guardrails` 根包的 `Rule`/`Level`/`Action` 才是业务类型，二者之间由 `host.Builder.Build` 转换——这样收敛评审核对该硬规则时才不会误判。
8. **迁移锁键建议写成互引注释。** `branding/persistence/migration.go:18-20` 的注释已经点明「必须与上游迁移锁键不同」；新增第三个键时，建议在三处注释里互相提一句各自的取值来源，避免以后有人复制粘贴撞键。
9. **§2 的权限引用行号略偏。** 写的是 `rbac/permissions.go:16,141`：`:16` 确为 `ModuleSettings`，但 `Settings.View` 在 `:140`、`Settings.Manage` 在 `:141`。不影响结论，顺手订正即可。

## 剩余风险

- **判官可用性即服务可用性**：`on_error=block` 下上游抖动会变成全量拒服务；现在有了接口，至少可以在线改配置而不必重启，比 v3 好转但仍无自动降级。
- **热更新窗口**：即便按阻塞 B 的方案 (a) 修好，仍存在「新配置对已在途请求不生效」的窗口，属可接受但需写明。
- **配置权限与安全开关同级**：`Settings.Manage` 覆盖面大，关停检测不需要额外授权（建议 3）。
- **16KB→64KB 上限上调后，已裁决的成本口径已略被突破**：裁决 4 把判官送检上限默认提到与总上限一致（64KB），而「每请求 ≤0.1 元」是按 16KB 算的。按同一实验单价（350 token ≈ 0.0004 元）折算，64KB 中文约 2.2 万 token ≈ 0.025 元/次，示例配置 5 次 ≈ 0.125 元/请求，已超过已裁决数字。建议在 §8 更新该数字，并在独立验证记录里单列 64KB 的实测 token 与耗时。
- **密钥规则误报、提示词效果不验收、改动触及刚交付的框架**：同前三轮，未变化。
