## 结论

需修改。检测器分工（D3 规则、D1/D4/D5 判官）、判官窄接口不依赖 `core/schemas`、每检测项一个判官实例、JSON 配置默认不启用这些方向与已确认的产品决策一致，无须再请业务批准。但判官调用的上下文构造按方案原样实现会导致**每次判官调用都取不到 provider key**（进而每个请求被拦），或**让本次用户请求的后续插件管线整体失效**；并行执行的取消语义、错误码映射与既有测试/文档契约三处不兼容且未列入改动范围；延迟与成本口径与实测依据不可比。出 v2 后复核下列 6 项阻塞。

2. **起点**：`fae2fe855` 为 develop `05db7cea2` 之后的文档提交，分支与需求记录一致。
3. **现状与约束**：引用基本准确——`plugin/plugin.go:23` 入口只持有 `*guardrails.Checker`，`plugin/plugin.go:13` 的 `Logger` 确实只有 `Info`；`ee/internal/app/guardrails.go:20-21,64-65` 读 `EE_GUARDRAILS_FAKE` 并以 `PluginPlacementPreBuiltin` 注册；`transports/bifrost-http/server/server.go:230` 为 `Client *bifrost.Bifrost`；`core/bifrost.go:801` 为 `ChatCompletionRequest`；`core/schemas/bifrost.go:349` 为 `BifrostContextKeySkipPluginPipeline`；`core/schemas/provider.go:65` 为 `MaxRetries`；`ee/internal/app/pricing.go:17-24` 确有「嵌入文件 + 环境变量指外部文件」的先例；`grep -c toml ee/go.mod` = 0，无 TOML 库、无 gitleaks 依赖。`detector.go:22`、`checker.go:66-93`、`evaluation.go:44-79` 三处行号各偏 1–3 行（实际为 `detector.go:23-25`、`checker.go:63-95`、`evaluation.go:41-78`），指向对象正确，不构成阻塞。
4. **目标/非目标**：与需求一致，未夹带管理 API、脱敏、流式等已排除项。
5. **设计**：判官检测器定义窄 `Model` 接口、app 侧适配，符合架构 §5「接口由使用方定义、构造函数注入」与 §7「模块根包只依赖标准库」；但适配器落点、请求上下文、并行语义有问题，见阻塞 1、3、4、5。`temperature`/`response_format` 可表达（`core/schemas/chatcompletions.go:220` `Temperature *float64`；`:213` `ResponseFormat *interface{}`，取值 `json_object` 见 `core/schemas/responseformat.go:25`）；但 `ChatParameters` **没有 `max_tokens` 字段**，只有 `MaxCompletionTokens *int`（`chatcompletions.go:202`），方案措辞需改。
6. **实施步骤**：步骤 1 未包含既有测试与 README 的同步修改（阻塞 4）；步骤 2 的数据转换可复现性与 §2 自相矛盾（建议 7）。
7. **测试策略**：替身判官覆盖正常/非法/超时/取消方向成立；缺「拦截错误码映射」与「错误路径上已完成评估保留」两类断言（阻塞 2、3）。

9. **风险/回滚**：回滚口径成立（不设该环境变量即与 develop 一致）。风险清单缺成本项与「Block 后其余判官调用仍会发出」的事实（阻塞 4、6）。

## 阻塞项

1. **阻塞：判官请求上下文按方案写法必然出故障。**
   方案 §4.2 只写「ctx 设 `BifrostContextKeySkipPluginPipeline=true`」，未说明在哪个上下文上设、要不要清理调用方状态。两种落法都错：
   - 若在**调用方的请求 ctx** 上设：该键不在 `reservedKeys`（`core/schemas/context.go:19-44`），写入会生效并经 `valueDelegate` 落到 root（`context.go:474-490`），于是本次用户请求后续的 `RunLLMPostHooks` 等整段被跳过（`core/bifrost.go:7977`、`8071`），**本插件自己的输出检测、日志插件、治理插件全部不再执行**。
   - 若只是派生一个 ctx 设该键、不清理：`core/utils.go:415-432` 明确说明跳过管线时继承调用方的 key 路由状态会把它套到另一个 provider 的 key 池上、「rejects every key（no keys found for provider）」。该状态由治理插件真实写入（`plugins/governance/resolver.go:128`），消费点是 `transports/bifrost-http/lib/account.go:47-66`：按 VK 允许的 key ID 过滤 → 判官请求在 deepseek 上过滤出 0 个 key → 判官恒失败 → `OnError=block` → 全量请求被拦。
   上游已给出唯一正确入口并明文禁止自行设键：`core/utils.go:480-489` `PrepareContextForInternalRequest`（注释：「Plugins should call this instead of setting BifrostContextKeySkipPluginPipeline (a reserved core key) themselves」）。同类先例是插件内发子请求的 `plugins/routing/llmclassify.go:129-141`，其中还有必须照抄的一条：`chatCtx := schemas.NewBifrostContext(ctx, deadline)` 之后 **`defer chatCtx.Cancel()`**，否则 `NewBifrostContext` 起的 `watchCancellation` goroutine 会长期引用已归还对象池的 scoped 插件 ctx（`core/schemas/context.go:98-131`）。
   要求 v2 写明：判官适配器新建 `*schemas.BifrostContext`（父为检测器收到的 ctx，携带规则 Timeout 派生的 deadline）→ `bifrost.PrepareContextForInternalRequest` → `defer Cancel()`；并在方案里点出「跳过管线 = 判官调用不计入治理预算/限流、不入日志」这一完整代价（拍板项 2 目前只写了日志与计费）。

2. **阻塞：并行后插件的拦截错误码映射失效。**
   `plugin/plugin.go:118-122` 判定拦截原因的依据是「`RuleEvaluations` 的**最后一条** `Outcome == Failed`」；串行时最后一条必定是触发 Block 的那条，所以成立。并行后方案 §4.3 规定「结果按配置顺序写回」，Block 来源不再必然是最后一条：例如配置顺序 [judge(失败,OnError=block), secrets(命中 block)]，两条都完成，最后一条是 `Matched`，用户拿到的是 `content_safety_blocked` + 管理员配置的拦截文案；把两条对调则变成 `content_safety_check_failed` + 「内容安全检查未完成」（`deny.go:16-41`）。同一事实、不同配置顺序给出不同错误码与文案。v2 需改判定依据（例如按 `Outcome` 聚合：只要存在 `Failed` 且其 `Action==Block` 就算检查失败），并把该用例写进测试。

3. **阻塞：Block 取消与框架错误没有区分机制，按现有实现会把拦截变成「取消」错误。**
   `evaluation.go:47-56` 在调用前后都用 `ctx.Err()` 判父取消并直接 `return ruleEvaluation, parentErr`；`checker.go:83-87` 一旦 `evaluateRule` 返回 err 就整体返回 error，`plugin/deny.go:53-56` 再把 `context.Canceled` 映射成 `content_safety_canceled`。若把「Block 时取消其余规则」的子 ctx 直接当作 `evaluateRule` 的 ctx，被取消的规则会让整次 `Check` 返回 `context.Canceled`，拦截结果被错误码覆盖。方案 §4.3 只说「被取消的规则不写入结果」「父 ctx 取消仍作为框架错误返回」，没给出区分办法。
   同时 `checker.go:60-62` 的公开契约写着「返回 error 时 `RuleEvaluations` 保留出错前已完成规则的执行结果」，`checker_test.go:243-271` 正在断言这点（父 ctx 取消时仍保留已完成的 Observe 评估）。v2 需明确：用什么机制区分「内部 Block 取消」与「父 ctx 取消/超时」（如 `context.WithCancelCause` + `context.Cause`，或单独检查父 ctx），以及错误路径上已完成规则的评估是否仍保留（保留则契约不变，不保留则要同步改注释和该测试并说明理由）。

4. **阻塞：并行是对外可观察的行为变更，既有测试/注释/README 未列入改动范围。**
   - `checker_test.go:61-80` `TestOrderShortCircuitAndStages` 断言 `calls == "observe,block"`，即 Block 之后的 `never` 规则**不得被调用**；并行后必然被调用，且该测试用无锁 slice 追加，`go test -race`（checklist 必过项 `ee-race`）会直接报数据竞争。
   - `checker.go:19-23`（`CheckResult` 注释「阻断之后的规则不执行」）、`ee/internal/guardrails/README.md`（「遇到拦截就停止」「依次调用检测器」「后续规则仍可拦截」）都要改。
   - 更重要的是语义本身变了：**Block 不再阻止其余规则被发起**，只是尽快取消。按 §4.4 的示例配置，输入阶段会同时发出 harmful、prompt_attack、business_rules 三个判官请求（即使密钥规则 0.3ms 就判定拦截），输出阶段再发两个。这既是成本事实也是「不得把用户文本多余地发给 DeepSeek」的隐私面事实，必须写进方案 §8 并让用户知情。
   v2 的步骤 1 需显式列出：改 `checker_test.go` 的顺序断言与并发安全、改 `checker.go` 注释、改 README。

5. **阻塞：判官适配器落在 `app` 违反架构硬规则。**
   方案 §4.2 把运行期适配器放 `ee/internal/app/guardrails_judge.go`，checklist 的 `必含符号` 也写死 `{grep: 'BifrostContextKeySkipPluginPipeline', in: ee/internal/app}`。但编码规范「架构符合性」明确「应用装配集中在 `app`，只负责依赖装配与生命周期，**不承载运行期业务编排**」，架构 §7「适配归位判定」规定「只服务某项业务的宿主接入放在 `<模块>/host/`」，仓内先例为 `ee/internal/rbac/host/`（`authorization.go`、`request.go` 等运行期适配）。判官适配器每次检测都会调用 `host.Client.ChatCompletionRequest`，属运行期适配，应放 `ee/internal/guardrails/host/`（或同等的模块内适配子包），由 `app` 注入 `*bifrost.Bifrost`。checklist 的 `必含符号` 作用域需同步改。

6. **阻塞：延迟与成本口径不成立，依据不可比。**
   - 摘要称「一次请求最多多等一次判官调用的时间」。事实：输入、输出是两次独立的 `Check`（`plugin/plugin.go:62-70`、`75-88`），各自并行；叠加 §4.2 的应用层重试（3 次、退避 200ms×2ⁿ），单阶段最坏等于规则 `Timeout`（方案 §8 写默认 10s），一次请求最坏约 2×Timeout。
   - 送检文本量无界到 64KB：`plugin/text.go:41-57` 把**全部历史消息**拼成一段，上限即配置的 `max_text_bytes: 65536`；判官请求把这段整体作为 user 内容发出。而成本/延迟依据来自 `product/需求/内容安全/检测器实现调研.md` 第三节的小样本实验（每次约 350 token、p50 670ms、p90 890ms、约 0.0004 元/次），两者不可比。
   - 并发实例数放大：示例配置下输入阶段 3 个判官实例、输出阶段 2 个，单请求最多 5 次判官调用，每次可携带 64KB 文本。
   v2 需给出判官送检文本的上限或截断口径（例如判官专用字节上限，或只送最近 N 轮），修正摘要的延迟口径，并把「每请求判官调用次数 × token 量」的成本量级写成拍板项交用户确认。

## 建议项（不阻塞，但需在 v2 回应）

1. **规则 `Timeout` 的来源没写。** `Rule.Timeout` 必填且必须 > 0（`rule.go:59`），但 §4.4 的 JSON 里 `harmful`/`prompt_attack`/`business_rules` 都没有 `timeout_ms`，只有 `judge.timeout_ms` 与 `secrets.timeout_ms`，§8 又说「规则 `Timeout` 默认 10s」。请写明判官规则的 `Timeout = judge.timeout_ms`，并明确每条 D5 是否允许单独配超时（属产品选择，宜列拍板）。同样没写的还有 `Category` 映射（secrets→`credentials`、harmful→`harmful_content`、prompt_attack→`prompt_attack`、business_rules→`business_rule`）。
2. **重试次数范围与产品结论不一致。** `product/需求/内容安全/调研总结.md`「判官调用失败」写的是「重试 3–5 次，仍失败则拦截」；方案 §4.2 允许 `Retries` 取 0–5，0 即不重试。要么收敛到 3–5，要么把放宽写成拍板项。
3. **应用层重试与 provider 自身重试叠加未算账。** 方案 §2 说重试退避「复用上游 provider 配置」（`core/schemas/provider.go:63-65` 的 `MaxRetries`、`RetryBackoffInitial/Max`、`DefaultRequestTimeoutInSeconds`），检测器再叠一层 3 次 + 200ms×2ⁿ 退避。10s 预算下实际可能跑不满 3 次应用层重试。请写清预算如何分配（例如判官单次调用的 deadline = Timeout/(Retries+1)）。
4. **非法配置拒启清单不完整，且建议拒绝未知字段。** §4.4 只列了「阈值/动作/阶段非法、judge 缺 provider、business_rules ID 重复或 rule 为空」。缺 `judge.model` 为空、`timeout_ms <= 0`、`retries` 越界、`stages` 为空数组、`max_text_bytes <= 0`（虽会被 `checker.New` 拒，但错误信息不指向配置）。另建议 `json.Decoder.DisallowUnknownFields`：否则 `"enalbed": true` 这类拼写错误会静默地让某个检测项不启用，属于配置层的 fail-open。
5. **密钥检测器的两个「忽略词」概念命名冲突。** Options 字段叫 `ExtraStopWords`（Gitleaks 语义：作用于命中到的 secret 值），配置字段叫 `ignored_keywords`（字面语义：作用于关键词预筛）。请统一并写明作用对象，否则管理员配了不生效。
6. **Level 映射属产品取舍，宜列拍板。** §4.1 自行决定「专用规则 High、`generic-*` Medium」，而 §4.4 默认阈值 `medium` ⇒ 任何 `generic-api-key` 命中即拦截；`product/需求/内容安全/密钥格式核实.md` 第三节明确这类规则「误报风险高」。建议要么 generic 归 Low，要么把默认阈值/动作的组合交用户拍板，并说明除 `ignored_keywords` 外的止血手段（例如先按 `observe` 上线一段时间）。
7. **密钥规则数据的可复现性两处自相矛盾。** §2 写「转换在仓外一次性完成，仓内只放 JSON」，§5 步骤 2 又写「结果与转换记录入 `data/`」。Gitleaks 升级时无法复现转换。建议把转换脚本（或可复现的命令 + 源版本标识：`v8.30.1`，核对基线 commit `b58d3f1` 见 `检测器实现调研.md` 第四节）入库，并在 checklist 的 `必存产物` 里加上该记录。
8. **Observe 规则在有 Block 并发时的统计会系统性偏低。** §4.3 规定被取消的规则不写入 `RuleEvaluations`，意味着「仅记录」类规则只要慢于拦截规则就没有记录。这与 README「仅记录命中，继续执行后续规则」的承诺不同，请在方案与 README 中写明新语义。
9. **命名常量。** 「每 32 条规则检查一次 `ctx.Err()`」「退避 200ms」「`max_tokens=200`」这类数值按编码规范硬规则「业务限制要命名」须定义命名常量并注明来源；另 `max_tokens` 应改称 `MaxCompletionTokens`（`core/schemas/chatcompletions.go:202`，无 `MaxTokens` 字段）。
10. **checklist 覆盖面。** `guardrails-file-size` 只扫 `ee/internal/guardrails`，不覆盖新增在 `app`（或按阻塞 5 迁到 `guardrails/host`）的文件；`必含符号` 建议补「判官适配器使用 `PrepareContextForInternalRequest`」一条，把阻塞 1 的正确写法固化成机械检查。
