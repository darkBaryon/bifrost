### 本轮修复项

**R1 · `judgeError` 的注释把 gateway 分支的文本无条件断言为 Bifrost 常量，而该分支的判定依据是 provider 可控字段**

位置：`/Users/xinyue/VSCode/ws_2026/bifrost-content-safety/ee/internal/guardrails/host/judge.go:98-101`（对应判别式 `:128-139`、gateway 分支 `:111-122`）。

代码事实：`:100-101` 写「**其余都是**网关或传输层自造（取消、超时、key 池没有支持判官模型的 key、连不上 provider、key 全部失效），**文本为 Bifrost 常量**，保留类型、代码与截断后的消息用于排障」。这个"其余"由 `fromProviderResponse` 划定，而它在 `:132-136` 用 `*bErr.Error.Type` 与两个上游类型名比对来把错误踢出 provider 分支。`Error.Type` 在 provider 响应路径上不是网关产物：`core/providers/openai/errors.go:99` 的 `bifrostErr.Error.Type = errorResp.Error.Type` 把 provider JSON 正文里的 `error.type` 原样搬入，判官所用的 DeepSeek 非流式 Chat 走的正是这条路径（`core/providers/deepseek/deepseek.go:247` → `openai.HandleOpenAIChatCompletionRequest` → `ParseOpenAIError`）。同一个测试文件把这一点写得很清楚：`host_test.go:114` 构造 `Type: schemas.Ptr("bad " + echo)`、`:144` 构造 `Type: schemas.Ptr("server_error " + echo)`，就是在断言 `Error.Type` 可能携带送检内容。因此只要 provider 的错误正文里 `type` 恰为 `provider_connection_failed` 或 `upstream_credentials_exhausted`，这条错误就会被判成"网关自造"，其 `message`（`judge.go:119-121`，截断到 200 字节）进入日志与错误链——而这正是本模块承诺绝不发生的事。

维护影响：`:100-101` 这句是 gateway 分支敢于打印自由文本的全部理由。它被写成无条件保证，而代码只能做到"按上游类型排除"。代价有两层：一是读注释的人会把"gateway 分支的文本一定安全"当成不变量，日后放宽 200 字节上限、把该消息并入接口响应或审计记录时不会再核对来源，那时泄露才真正生效；二是编码规范把"与实际行为不一致的注释视为缺陷"，而这句恰好是本模块唯一一处安全性承诺。判别式方向本身没有问题（比上一轮更贴近上游事实），需要改的只是那句保证。

最小修正（本评审范围内，只改文本）：把 `:100-101` 改成陈述实际规则——"其余归 gateway 分支：包括取消、超时、key 池没有支持判官模型的 key，以及按 `Error.Type` 从上游合成错误清单中识别出的连接失败与 key 耗尽。后者的识别依据是上游写入的类型名，而 `Error.Type` 在 provider 响应路径上来自 provider 正文（见 `core/providers/openai/errors.go`），因此这是尽力而为的排除，不是文本必为 Bifrost 常量的保证"。`README.md:101` 已写明 provider 的 `type` 可能回显并指向判别函数，口径不冲突，无需改动。若倾向于把排除条件收紧（例如同时要求 `Error.Message` 等于 `schemas.ErrProviderDoRequest` / `ErrProviderNetworkError` 或 `errAllKeysDead` 的哨兵文本），那是行为变更，取舍与回归归代码评审，本轮已在「转代码评审」记一行；两条路任选其一都能关闭本项，但不能让这句保证原样留下。
