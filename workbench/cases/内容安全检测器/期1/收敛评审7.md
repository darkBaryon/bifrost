### 本轮修复项

**R1 · README 把"没有可用 key"整类许诺成保留错误消息，而三种形状里有两种本轮起不再有消息**

位置：`/Users/xinyue/VSCode/ws_2026/bifrost-content-safety/ee/internal/guardrails/README.md:101`（对应实现 `/Users/xinyue/VSCode/ws_2026/bifrost-content-safety/ee/internal/guardrails/host/judge.go:110-135`）。

代码事实：README 这一句写「判官失败时……能看到的是状态码和一个固定类别；**网关自身产生的错误（取消、超时、没有可用 key）额外保留类型、代码与前 200 字节消息**」。`judge.go:115` 划定"保留消息"分支的条件是 `bErr.IsBifrostError || bErr.StatusCode == nil`。"没有可用 key"在上游有三种形状，只有一种满足该条件：

- key 池没有支持判官模型的 key → `core/bifrost.go:8987-8988` 产生纯文本错误，经 `:6233` `newBifrostErrorFromMsg`（`core/utils.go:324-331`）包装，**无 StatusCode** → 进 `gateway_internal` 分支，保留消息。README 描述成立。
- key 全部失效 → `core/bifrost.go:6220-6231` `errAllKeysDead`，`IsBifrostError: false` + **502** → 进 `judge.go:130` 分支，输出 `category=provider_unavailable known_type=upstream_credentials_exhausted`，**没有 type/code/message**。
- key 全被过滤 → `core/bifrost.go:6207-6218` `errAllKeysFiltered`，`IsBifrostError: false` + **503** → 同上，`known_type=no_eligible_keys`，同样没有消息。

同一句的前半"能看到的是状态码和一个固定类别"也已不完整：本轮新增的 `known_type=` 是错误链里的第三个可见 token（`judge.go:131-132`），README 全文未出现该词。

维护影响：编码规范把包 README 的读者设定为"第一次接手、准备改它的人"，而这段是本模块唯一的脱敏承诺。判官最典型的线上故障就是 key 配错或全部失效——正是 README 说错的那两种。接手的人按 README 预期在日志里找消息，找不到时会先怀疑截断逻辑或日志注入坏了，而不是去读 `:115` 的分支条件；反过来，若他信了"没有可用 key 一律有消息"而据此写排障手册，手册在最需要的场景下失效。编码规范两条明文同时被触及：「修改代码时必须同步检查并更新相关注释，已失效的说明及时删除」与「包的功能、文件或约束发生变化时同步更新」。

最小修正：把括号里的"没有可用 key"收窄成实际落到该分支的那一种，例如「网关自身产生、且没有 provider 状态码的错误（取消、超时、key 池没有支持判官模型的 key）」；并补一句半行说明第三个 token，例如「错误类型属于上游合成错误清单时，另附一个本地常量名」。**不要**借此把三个类型名重新列回 README——那会撤销上一轮 R1/S2 刚完成的简化。只改文字，不涉及行为。

**R2 · `providerFailureCategory` 的注释仍称状态码来自 provider，而本轮第一次让网关自造的状态码走进它；同处 `judgeError` 的"不断言来源"与其输出的 `provider_*` 自相矛盾**

位置：`/Users/xinyue/VSCode/ws_2026/bifrost-content-safety/ee/internal/guardrails/host/judge.go:137-138`（`providerFailureCategory` 注释）与 `:104`（`judgeError` 注释首句）。

代码事实：两条都是本轮改动直接造成的失效。

- `:137` 写「`providerFailureCategory` **只按 provider 返回的** HTTP 状态码给出固定类别」。上一轮该函数确实只对 provider HTTP 响应可达——旧代码在 `:130` 之前就对命中 `synthesizedGatewayTypes` 的错误 `return` 了。本轮把那个提前 return 删掉（`judge.go:130-133`），于是 `core/bifrost.go:6208` 的 503、`:6221` 的 502 和 `core/providers/utils/utils.go:2724` 的 502 这三个**由网关自己写死**的状态码，现在全都从这个函数取类别。注释的限定词"provider 返回的"在本轮新增的这条路径上是假的。
- `:104` 写「类别名**只陈述可验证的事实，不断言来源**」，紧接着 `:107` 说"带状态码：按状态码归入 `provider_*` 类别"。`provider_unavailable` / `provider_auth` / `provider_rejected` 这组名字本身就是在断言来源是 provider，而对上述三种形状而言 provider 可能根本没被联系上（`no_eligible_keys` 是 key 被本地过滤器滤空，`upstream_credentials_exhausted` 是本地 key 全部标死）。这不是要求推翻上一轮 S1 已采纳的取舍（那条取舍的正文就是"按状态码派生 + `known_type`"，`known_type` 正是用来补回真实来源的），问题只在注释把这个取舍描述成了一个它做不到的绝对承诺。

维护影响：`judgeError` 是本模块最容易被误改的函数——五轮评审里改了四次，每次都是因为"哪些字段可信"判断错了。它的注释是下一个人唯一的判断依据。`:137` 的"provider 返回的"会让人以为凡是走到这里的都来自 provider 响应，从而在扩展时把某个"只对 provider 响应安全"的处理（例如把状态码原样透出给调用方、或按状态码决定是否重试）加进来，而实际上这里也承载着网关自造的 502/503；`:104` 的绝对句式则会让下一个人误以为类别名已经通过了"可验证"检验，不必再核。同为编码规范「与代码不一致的注释视为缺陷」的直击点。

最小修正：两处各改一句。`:137` 改成陈述实际输入，例如「按错误携带的 HTTP 状态码给出固定类别，不引用任何自由文本；状态码可能来自 provider 响应，也可能由网关合成（见 `synthesizedGatewayTypes`）」。`:104` 首句去掉绝对承诺，改成描述取值口径，例如「类别名只由状态码派生、不使用自由文本；来源由 `known_type` 单独标注」。只改注释，不涉及行为。
