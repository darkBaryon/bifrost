**代码事实：** `proxyUpdate` 判断保留原 Password 后，只比较 `Type`、`URL`。`SkipTLSVerify` 没有进入比较。

**触发条件与后果（静态推断）：** 已有代理配置保留原密码，管理者保持 Type/URL，仅改变 `SkipTLSVerify`，不会要求新增敏感权限。该字段确实参与运行时 TLS 配置，见 [http.go:272](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/core/network/http.go:272) 和 [http.go:407](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/core/network/http.go:407)。因此沿用凭据改变 TLS 信任的规则未生效。

**最小修正：** 将有效 TLS 信任配置纳入全局代理比较；补充保留密码时 TLS 改动拒绝、授权后允许、普通参数更新允许的测试。修复时同时对照全局代理的实际路由配置字段，避免比较模型继续少于运行时模型。

**验证边界：** 未建立代理或 TLS 连接；本项依据配置处理与运行时赋值链判断。

### R4：OTEL 按 profile 合并凭据集合，遗漏实际信号目标变化

**位置：** [plugin_credentials.go:61](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/ee/internal/rbac/host/plugin_credentials.go:61)

**代码事实：** 检查将 `Headers`、`TraceHeaders`、`MetricsHeaders` 的值合为一个集合，再比较包含两个地址的整个 profile 元组，未保留凭据与 trace/metrics 实际发送目标的对应关系。

运行时分别合并共享头和信号专用头，专用头覆盖同名共享头，见 [main.go:557](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/plugins/otel/main.go:557)、[main.go:653](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/plugins/otel/main.go:653)，随后分别配置 trace client 与 metrics exporter。

**触发条件与后果（静态推断）：** 同一个 profile 的 trace、metrics 地址不同；共享认证头原先被 metrics 的同名专用头覆盖。更新保留共享头而移除该覆盖，两个地址均不变。检查会认为旧凭据仍匹配原 profile，运行时却会把原先只用于 trace 的共享凭据新增用于 metrics 地址，未要求敏感权限。此条件不需要修改凭据明文，原路径的保留标记即可沿用共享头。

**最小修正：** 根据运行时相同的覆盖规则，分别构造 trace 和 metrics 的有效头，再建立“凭据—实际目标—TLS/协议”对应关系。任何旧凭据新增目标都检查敏感权限；保留原有多目标使用、profile 重排和原样保存的兼容性。

**验证边界：** 未执行 exporter 或发送凭据。现有插件测试覆盖地址变化和多 profile 原样保存，没有覆盖共享头与专用头覆盖关系变化。

### R5：Key 别名名称与字段名碰撞，会漏掉别名 endpoint

**位置：** [credentials.go:72](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/ee/internal/rbac/host/credentials.go:72)

**代码事实：** `keyConnection` 在任意 map 层级按裸键名分类。遇到 `value`、`client_secret` 等凭据字段名即停止向下遍历，将子对象整体交给 `configSecretText`。但 `Key.Aliases` 的 map 键是用户模型名，合法名称可以与这些字段同名。

`KeyAliases.Validate` 不禁止这些名称，见 [account.go:302](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/core/schemas/account.go:302)；`SecretVar.UnmarshalJSON` 对非 SecretVar 形状的对象可以退为字符串，见 [secretvar.go:313](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/core/schemas/secretvar.go:313)。

**触发条件与后果（静态推断）：** 已有 Azure Key 使用上述合法名称的富别名，更新保留 Key 主凭据，仅改变该别名 endpoint。别名对象被归入凭据集合，其 endpoint 未进入 targets，目标比较不变，敏感权限检查漏过。Azure 运行时实际优先采用别名 endpoint，见 [utils.go:57](/Users/xinyue/VSCode/ws_2026/bifrost-permissions/core/providers/azure/utils.go:57)。

**最小修正：** 区分配置结构字段与 `Aliases` 的动态模型名，按实际 Key/AliasConfig 类型或明确路径读取目标字段。不要通过禁止合法模型名补洞。增加模型名与字段名碰撞的纯配置测试，并验证保留凭据时拒绝、授权后允许。

**验证边界：** 未调用 Azure 或任何厂商服务；结论来自类型、校验、比较与端点选择链。
