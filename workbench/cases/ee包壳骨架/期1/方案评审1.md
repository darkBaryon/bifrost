## 结论

**需修改**。Go 侧的核心断言(Bootstrap 后可挂路由/换 Handler、SyncLoadedPlugin、ConfigStore.DB()、独立 replace 构建)全部亲核成立,方向可行;但 UI 覆盖层会把上游 UI 编成企业模式(`IS_ENTERPRISE=true`),方案没有识别这一副作用,与需求目标 1「同样的页面」和非目标「不设 IsEnterprise」直接冲突;另外 checklist 有两条在任何状态下都过不了。

阻塞项:

1. **B1 覆盖层触发 UI `IS_ENTERPRISE=true`,方案未识别、未拍板**。`ui/vite.config.mts:10` 仅凭 `app/enterprise` 目录存在判定 `isEnterpriseBuild`,`:48` 注入 `BIFROST_IS_ENTERPRISE`,`ui/lib/constants/config.ts:267` 得出 `IS_ENTERPRISE`。覆盖层一旦存在,ee 的 UI 与 OSS 至少有这些差异:侧栏多出 Proxy / Branding 菜单(`ui/components/sidebar.tsx:1022,1054`),License / Branding 页面可进入(`config/license/page.tsx:10-15`、`config/branding/page.tsx:12-17`),`useBranding` 每次加载请求 `/api/branding`(`ui/lib/hooks/useBranding.ts:165`,OSS 后端无此路由,handlers 目录 grep 无命中),Security 页多出「Dual Credential Conflict Behavior」区块且标签改为「Enable Auth on Inference」(`securityView.tsx:349,376`),`enforce_auth_on_inference` 的脏检测逻辑改变(`:144`),新版本横幅被隐藏(`sidebar.tsx:1154`),onboarding 增加企业步骤(`useOnboardingChecklist.ts:111`)。方案 v2 须:列出这份差异、明确是否接受(拍板项)、把验收口径从「同样的页面」改成可核的描述,并在冒烟/人工检查里覆盖至少一处(如 Security 页)。若不接受,要说明替代路线(上游 vite 配置不可改,目前看无法既用 `@enterprise` 覆盖又保持 OSS 模式)。
2. **B2 checklist `no-is-enterprise-in-ee` 永远失败**。`tools/preflight.py:47-49` 要求 `rc == 0` 且(expect_empty 时)stdout 为空;`grep` 无命中时退出码为 1。我用同一语义模拟:基线(无 ee)rc=1,含干净 `.go` 文件的 ee 目录 rc=1、out 为空,两种情况 green 都是 False。应改为 `! grep ...`(不带 expect_empty)或挪到「禁留标记」节。
3. **B3 checklist `upstream-untouched` 在基线上已经是红的,且比较对象是工作树**。基线执行该命令输出 `plugins/routing/go.mod`(工作树改动,`git diff upstream/dev HEAD` 对该文件为空,即未提交的 go 工具链 tidy 痕迹)。方案/checklist 须规定预飞前如何处理这类 go.mod 漂移(`git checkout` 还原、或改为比较 `HEAD`、或补排除项),否则合同在起点上就不成立。

### §4 设计

- 4.1 目录与命名:镜像上游、`ee_` 前缀、包名一致,无异议。`lib/tables.go` 的 `Probe` 结构若不实现 `TableName()`,gorm 默认表名是 `probes`(configstore 无 NamingStrategy/TablePrefix,grep 无命中),T3 会失败——见 S4。
- 4.2 Bootstrap 契约:`NewBifrostHTTPServer` 返回后 `Router`/`AuthMiddleware`/`Config` 均为 nil(实测打印 `true true true`),attach 必须在 `s.Bootstrap` 之后——方案顺序正确。`s.Server.Handler` 整体包裹,`X-Bifrost-EE` 可覆盖所有响应 ✓。`/api/ee/ping` 不挂 `APIMiddleware` 意味着它是一条无鉴权的公开路由(Handler 级别没有鉴权,鉴权只在每条路由的 middlewares 里),骨架期可接受,文档要写明。
- 4.3 go.mod:replace 清单充分(实测)。`go work use ./ee` 的持久性问题见 S1。
- 4.4 sync.sh:在与方案完全相同的脚本上做了 tsc 实验——上游 tsconfig 没开 `preserveSymlinks`,但对逐文件符号链接的覆盖文件,`@/` 别名与 `./sibling` 相对 import 都解析到覆盖层目录,`tsc --noEmit` 通过;把相对 import 改成不存在的模块能正确报错(负例有效)。vite 侧 `preserveSymlinks: true` 同样以链接路径为准,两者口径一致,不存在方案担心的漂移。「dev 热更新可用」未验证(需起 vite dev),记为待实施确认。脚本用相对路径,只在仓库根目录下正确;`make -C ee` 的 cwd 是 ee/,需在脚本内 `cd "$(dirname "$0")/../.."`(S6)。
- 4.5 构建:`UI_DIST` 参数化合理。`make -C ee build` 的产物路径 `ee/tmp/bifrost-http` 需 ee/.gitignore 含 `tmp/`(4.1 已列)✓。
