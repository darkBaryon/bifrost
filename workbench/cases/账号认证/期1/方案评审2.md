## 可证伪质疑

### B1：宿主身份上下文——已关闭

v2 4.5 明确只对已验证、非受限 chief 设置 `schemas.IsLocalAdminContextKey=true`，普通成员、公开入口和 TempToken 不获此标记，WS 每次写仍重新验证。亲核 `handlers/notifications.go:161/207` 对该标记的发布和可见性判断，契约能满足现有调用方。第 6 节加入创建、查询、角色限定通知推送及失效校验，覆盖首轮反例。

### B2：真实配置字段及现有页面回送——已关闭

v2 使用实际 HTTP 字段 `client_config.whitelisted_routes`；GET 返回固定只读 EE 认证投影，PUT 接受按字段语义相同的投影、在原 handler 前移除 auth_config，实际认证变化和非空白名单整请求拒绝。亲核宿主 config DTO、GET 的旧认证输出，以及首轮已核实的页面整包回送路径。该设计使普通设置可继续沿原 handler 更新，同时不触发旧认证写入。

拒绝重复键、未知认证字段和凭据引用，以及只对已通过预检的请求作局部删除，已写明，未把“同值”定义为仅忽略敏感字段。真实 HTTP 的成功/拒绝与无部分写入断言已加入第 6 节。

### B3：嵌入 UI 的可复现验收——已关闭

checklist 增加 `cd ui && npm ci` 及 `make -C ee build-ui`，之后才构建 smoke 使用的二进制。亲核 ui/package-lock.json 存在，EE Makefile 的 build-ui 依赖 ui-sync、执行 vite build、要求 index.html 并复制至 embed 目录；它不依赖会生成 go.work 的 workspace 目标。既有 HTML 断言得以保留。

### 首轮建议与新增兼容行为——已收口

- 独立 `/debug/pprof/` 明确保留现有运维鉴权；主 Router 的 `/api/dev/pprof` 仍归 EE 管理认证，未混淆两个监听入口。
- 文件密码哈希失败时接受宿主有效旧 DB 回退的规则已明确，新增超 72 字节文件密码用例；快照自身残缺或不支持仍拒绝启动。
- 品牌 `POST /api/branding/get` 明确公开且无需 Origin；update/reset 仍要求同源及 chief，符合现有路由职责。
- TempToken 特殊优先级仅作用于 `handlers/temptokens.go` 声明的六组 method/route，并保留 scope、resource_id、开关及 handler 验证；成功后清 EE 身份，不能转为一般管理权限。允许过期/非 chief Cookie 不遮蔽专用令牌，是明示的兼容选择。
- 旧 logout/ws-ticket 空体映射为 `{}`，来源检查保留。亲核 sessionApi 的 logout 确为无 body POST，而 baseApi 默认设置 application/json；v2 修复的是空体解析兼容，没有误把该调用断言为一定缺 Content-Type。原成功 message 形状保留。
