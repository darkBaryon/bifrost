### 架构符合性

- 对照 §4：`OperationContext` 处理 HTTP 关联头，`WithDiagnosticOperation` 只在标准 context 内附操作名与 ID。业务没有输出日志、识别 PG/SQLite 或处理 HTTP 对象；`databaseFailure` 在存储读取和事务最终出口提取安全字段。新增 `diagnostics.go` 将驱动识别集中，调用方仍可直接理解失败路径，未把紧密相关业务拆散。
- 对照 §5 的事务边界：`MigrateIdentity` 每次调用 `migrateIdentityOnce`，后者仍持有原完整迁移事务、PG advisory lock 和 `RunSingleMigration`；运行期 Transaction 保留 state 写锁与业务 callback。重试识别共用 `sqliteBusy`，没有把数据库特例推到 HTTP/service。迁移与运行事务的阶段和最终错误处理不同，当前重复的短循环不构成需要维护公共重试框架的成本。
- 对照 §7：日志改变发生在 CORS defer 中生成 `http.target` 的位置，EE adapter 不再修改 URI/query 缓存来影响另一层输出；`requestLogTarget` 不改变请求。根据 `server.go:2935`，CORS 位于解压和 Router 外；该层次选择能独立解释为何覆盖认证前返回。是否覆盖所有泄露路径及实际握手行为交代码评审，不由架构结论推出安全通过。
- `app/recovery.go` 仅补入口操作上下文，恢复密码及会话撤销仍由 identity service 处理。Node 的默认目录测试复用已有启动能力，通过可选参数装配自有 HOME/APPDATA/cwd，没有建立第二套进程管理器。

### 依赖关系

- identity 根包 import 仍为标准库；诊断值是自身字符串结构和私有 context key。HTTP、宿主适配、persistence 向根包依赖，Repository/Tx/AccountPolicy 的使用方窄接口保持，不反向引用 HTTP 或 GORM。
- `pgconn.PgError` 与 `sqlite3.Error` 仅出现在 persistence；`ee/go.mod:7` 将已存在的 pgx v5.9.2 改为直接依赖，匹配新增 import，并非引入新的数据库系统或认证服务。SQL 日志静默与固定诊断出口继续由适配负责；现阶段标准日志输出不需要增加全局服务容器或日志框架。
- HTTP 上下文仅沿同步调用进入 service/store；WS 再验证用回调收到的 context 生成新操作关联，闭包捕获 session ID，不为诊断捕获原 RequestCtx。连接生命周期行为由代码评审复核。
- 宿主共享数据库所有权不变，Store 不 Close；离线入口关闭自身建立的连接，脚本管理自己创建的进程和数据库。`database_created` 与 `succeeded` 分别表示资源实际存在和整轮成功，保留二者使失败现场的处置意图清楚，不属于重复状态。
- 对照同类请求 ID 实现后核实 TracingMiddleware 仅被装到推理链（`server.go:2836`），新增 OperationContext 用于管理链。没有凭表面都处理 `x-request-id` 就合并两条不同入口；不声称本次改动建立了全系统统一追踪 API。
