**R1｜`ResetPassword` 先 bcrypt 后鉴权 —— 已关闭**

- 改动事实：`/Users/xinyue/VSCode/ws_2026/bifrost-auth/ee/internal/identity/passwords.go:74-84` 用 `if allowed := s.RequireAccountManager(ctx, p); allowed == nil` 包住 `s.hash`，与 `accounts.go:76` 的 `CreateAccount` 同形；`:125-129` 新增 `hash == "" → ErrConflict` 的竞态兜底；`:121-123` 的失败事件写入路径原样保留在预检之后。
- **失败事件契约仍然成立**（我最关心的一点，实跑验证）。自写探针 `reset-contract-probe.py`（scratchpad，自行拉起并回收一个 EE 进程与临时 SQLite）对新二进制逐项断言，全部通过：
  - (a) **受限会话成员**（仍持默认密码）重置他人 → 403，chief 查得到该 `operation_id` 的事件，`result=failure`、`reason_code=forbidden`、`actor_id`/`target_id` 正确；
  - (b) **正常成员**（已改密、无权限）重置他人 → 403 + 失败事件；
  - (c) 同一未授权成员用**同一 operation_id 重试** → 仍 403，事件数仍为 1 且 `id` 未变（幂等，未重复写）；
  - (d) chief **自我重置** → 403 + 失败事件（此路径预检通过、仍会算哈希，行为与修复前一致）；
  - (e) **目标不存在** → 404 + `reason_code=not_found` 的失败事件；
  - (f) 正常重置 200、同 ID 重试返回原 `event_id`、被重置账号可用初始密码登录。
  即预检只决定"算不算哈希"，不决定"写不写事件"，方案 4.2「权限/状态/目标错误记录失败事件」未被削弱。
- **饥饿路径确已关闭**（实测，非静态推断）。自写 `slot-probe.py`：8 个线程持续 6 秒以未授权成员身份轰炸 `/api/accounts/reset-password`，同时一个合法账号并发做 change-password + 重新登录。结果：轰炸方 **2675 次全部 403，零 429**；合法方 3 轮 change-password 全部 200，3 次登录全部 200 且耗时 66/85/101ms（单次 bcrypt 的正常量级），无一次被限流。446 次/秒的应答速率在 cost=10、4 槽位的约束下（理论上限约 57 次/秒）物理上不可能包含 bcrypt 计算，可直接证明被拒路径不再进入哈希槽。
- **新增竞态分支未引入新问题**。逐条核对：①`hash == ""` 与"预检失败"严格等价——`encrypt.Hash` 不会返回 `("", nil)`，返回错误时函数已在 `:80-82` 提前退出，故该判据无歧义。②该分支 `return ErrConflict` 使整笔事务回滚，**不写任何事件、不改密码、不升版本、不撤销会话**，无副作用残留，调用方用同一 operation_id 重试必然成功（重置本身幂等）。③触发需要"预检判否而同一请求的事务内判是"，本期无提升/更换 chief 的接口，现实中只剩预检两次读取遭遇瞬时存储故障这一种情形；方案 4.3 明令管理鉴权不查只读副本，故不存在复制延迟导致的稳定误触发。④实测未见误触发：探针 (g) 连续 12 次授权重置全部 200 无 409；上述 2675 次未授权调用的响应码集合是 `{403}`，说明"预检否 + 事务内否"这条主路径 2675 次全部正确收敛到失败事件，没有一次漏进竞态分支。
- 回归：SQLite 与双节点 PostgreSQL 身份冒烟中原有的重置幂等、跨节点撤销、事件回滚断言（`identity-smoke.py:196-216`）与 `service_test.go:168-192,246-260` 的失败事件用例全部通过。
