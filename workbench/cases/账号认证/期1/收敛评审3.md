### 架构符合性

- 对照 §4：数据库锁错误由 persistence 判断，Handler 和品牌业务服务没有新增等待、循环或驱动知识。`migrateBrandingOnce` 的命名表明它只执行一次完整迁移，与外层重复尝试的职责相邻；没有为重试新增包或拆出通用执行器。
- 对照 §5：表创建、单例初始化、版本记录仍在同一外层 GORM 事务，`opts.UseTransaction=false` 的内层迁移配置保持；PG 的 lock_timeout/advisory lock 仍位于该事务内。外层重试调用原子操作，不将单表步骤散开。是否在真实驱动失败时完整回滚由代码侧证明。
- 对照 §7：`app.attach` 继续通过宿主 ConfigStore.RunMigration 进入品牌迁移，失败仍返回原有 `ee: migrate branding` 包装错误。共享连接没有被品牌新建、关闭或重配；未为该故障修改宿主启动顺序、另起数据库或复制整条应用初始化链。
- 本次故障发生在认证候选的必经启动路径，对现有品牌迁移作局部可靠性修正与本期交付有直接关联；方案已登记偏差，没有顺势新增品牌功能。无需重开默认密码、重置权限、无 Redis 或后端先行等已批准范围。

### 依赖关系

- 新增 import 是标准库 `errors`/`time` 和已有直接依赖 `go-sqlite3`；具体驱动类型限于品牌存储适配，根包、Repository 和 HTTP 接口没有泄露 SQLite 类型。
- 品牌没有导入 identity，未形成跨业务或反向依赖。identity 的错误诊断出口与品牌直接返回原错误不同；为共用几行 typed busy 判断而抽跨模块框架会增加阅读与装配成本，目前没有维护收益。
- RunMigration 的 SQLite hook 复用当前 DB，PG 由宿主提供迁移连接；品牌只使用传入连接。现有 testDB 仍提供隔离 SQLite 文件/PG schema 并负责清理，本次测试复用它，未建立另一套夹具生命周期。
