## 给用户的摘要

从功能前基线重新开发，旧实现只留作历史，不提取旧提交。
每期生产代码和测试合计约 1,000 行；不再以全部后端为一期。
先验证复用边界，再做一期模板管理；后续方案随已验收结果细化。
整体业务范围沿用 [产品讨论](../../../product/需求/资源治理/方案讨论.md)，不以缩小单期为由删掉最终需要的调用方式。
本蓝图及期1方案已完成独立方案复核（见期1方案评审1/2），待用户审阅新的分期和首期边界；本轮没有功能实现。

## 1. 起点与整体边界

- 精确基线：`d93fa8ad2082c716f76c55720b2272e718a7f649`（当前本地 `develop`）。新分支：`codex/user-usage-rebuild`。
- 旧候选：`feat/user-usage` / `9fef9a26980e5937571391934d6067e53066c7fa`，未合入、推送或部署；原工作区未提交内容继续留在原处。
- 本分支不引入旧账本、重试器、Batch/实时适配和上游改写。已有业务规则继续有效，旧工程细节重新论证。
- 不承诺整个功能只有1,000行。每期先列预算，预计超量就先拆边界；修复和测试也计入，不压行、删测试或用净增抵消重写。

## 2. 复用先于扩展

已有身份、角色、配置数据库、迁移、价格目录和治理限额能力继续复用。模块按 [EE架构](../../../product/架构/EE后端架构.md) 组织；简单配置允许 HTTP 调用本模块具体存储，不为转发而建立全功能 Service/Repository。

[局部实测](../../evidence/按人用量与额度-重新开发复用验证.md) 已确认既有计数器支持同预算累计、调额保留用量，但稳定预算ID不会固定旧周期，缺失预算也不会主动拒绝。不能直接据此把员工映射为一个预算并声称全部规则已实现；也不能据此立即决定重建完整记账系统。

运行时方案必须回答三个问题后才能编码：个人归属与周期由谁持有；最终金额从哪个现有出口获取；故障和重复终态怎样处理。仅为已证明的缺口增加 EE 状态或可选上游扩展。不能用虚拟 Team/Customer 占用现有业务归属关系。

## 3. 当前分期与后续候选

只有期1细化到实施边界。后续各行是待细化的交付目标，不是允许一次写完的标准级任务；到期先形成约1,000行方案，必要时继续拆期。

| 次序 | 行为出口 | 约束与依赖 |
|---|---|---|
| 期1：模板管理 | 有权限的账号创建、查询、修改、删除额度模板，重启后保留；无权限和版本冲突明确拒绝 | 生产约550行、测试约350行，加复用实验101行，合计约1,000行；上游0行。见[期1方案](期1/方案v2.md) |
| 后续：个人配置 | 选择员工、单人及批量套用模板、查询与调整；覆盖配置保持用量 | 先验证模板复制与账号权限；不预建运行时用不到的类型 |
| 后续：密钥归属 | 明确绑定、同人多密钥、禁止跨人重复绑定、账号生命周期联动 | 沿用真实VK验证，不使用创建者冒充属主 |
| 后续：标准调用闭环 | 明确价格的调用归人、金额累计、当前月软额度执行、缺价拒绝 | 在这一阶段方案内按实际预算再分期；未闭环不得宣称额度生效 |
| 后续：统计与各调用链 | 个人/管理员统计、流式/异步、MCP、已知透传、实时、Batch | 每种计量生命周期单独立期，不合成“其余协议一期”；每期有真实链路证据 |
| 后续：页面 | 模板、分配、绑定、个人查看与管理员查询 | 后端验收后按页面行为分期 |

## 4. 接口与数据边界

仅期1确定模板接口和一张模板表，方案已细化待复核。个人分配、归属、计量结构在对应方案复核后确定；不照抄旧方案的13个接口或7张表。HTTP DTO、业务值和行模型分开，但不要求每个概念各建文件。

上游默认修改预算为0。运行时确有缺口时，先单列函数签名、执行时点、默认行为及预计增删量，再作为当期方案审阅；不顺便修算价算法或整理既有代码。

## 5. 审阅出口与回退

每期提供基线、候选、生产/测试/上游的新增与删除、阅读顺序、实际验证及缺口。上一期用户验收前不实施下一期。方案复核与代码/收敛评审遵循工作台规则；旧评审不能证明新分支通过。

每期使用可独立回退的提交；迁移只随使用方加入。新分支尚无生产数据，不设计迁移旧候选账本的兼容层。用户没有授权推送、合并或部署。
