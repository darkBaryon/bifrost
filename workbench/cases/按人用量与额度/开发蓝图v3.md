**页面、前端代码和浏览器验收不属于本次需求，由前端独立负责。**
完整划分为18期，下面逐期列出交付、依赖、验收和代码预算，不再把剩余调用链留成“后续再拆”。

前9期完成标准非流式文本/Embedding等模型后端闭环，期10—18接入其余已确认调用链。
本轮只补全规划，没有开始功能实现。[期1方案v2](期1/方案v2.md)保持模板管理边界。
本版本补齐[蓝图v2](开发蓝图v2.md)复核发现的调用边界与Batch结算职责；[评审3](期1/方案评审3.md)原文保留。v1的页面安排已由用户最新要求替代。

## 1. 整体目标 / 非目标

业务来源：[产品讨论](../../../product/需求/资源治理/方案讨论.md)。完整后端终态为：管理员维护模板、给员工分配副本并绑定VK；调用共享员工额度、按实际用量记账；本人和管理员通过授权接口核对统计及待核对事实。

- 精确起点：`d93fa8ad2082c716f76c55720b2272e718a7f649`（本地`develop`）；分支`codex/user-usage-rebuild`。
- 旧候选`feat/user-usage` / `9fef9a26980e5937571391934d6067e53066c7fa`保留，不提取旧提交。各期从上期验收提交继续，并在本期方案写明精确SHA。
- 单实例软额度：请求前查、结束后结算，接受在途超额。默认UTC自然月。停账号或暂停后拒新调用，在途费用仍归原员工。
- 完整范围包含标准/流式、普通后台异步、明确计价MCP、已知透传、网关代理实时与Provider Batch。未知透传、绕过网关计量的直连凭据不得假装已支持。
- 不含页面、导航、前端状态管理、前端自动化测试；不含新账号体系、按角色自动分配、换绑/解除纳管、分布式账本、预占余额、支付级零丢失承诺。
- 不扩充网关尚不支持的厂商或协议，不借本需求重构价格公式、日志系统或通用任务框架。

## 2. 模块边界与依赖方向

遵循[EE后端架构](../../../product/架构/EE后端架构.md)：入口与装配在`ee/internal/app`，业务位于`ee/internal/usage`，业务内部按需分HTTP与持久化。简单模板CRUD允许HTTP调用本模块具体存储，不预建空转的全套Service/Repository。

| 既有能力 | 本次如何复用 | 本次新增的责任 |
|---|---|---|
| identity / rbac / EE host | 复用本地账号、事务内授权、路由与会话保护 | 额度管理/查看权限及本人查询边界 |
| configstore / VK / governance | 沿用真实VK、原治理检查和计数原语 | VK与员工绑定；员工配置；各VK共享的个人检查 |
| pricing / modelcatalog / 工具价格 | 复用价格维护与网关公式 | 区分缺价和零价，实际执行前校验适用价格 |
| 既有模型、流式、实时入口 | 复用请求与用量转换、逐轮管线 | 小型归属快照与结算适配，不复制协议实现 |
| jobaccounting | 复用Provider任务持久化、轮询、结果定价与报告 | 原员工/周期归属，以及个人记录的幂等接入 |

依赖方向为EE装配 → EE业务及现有能力；上游只认识可选接口/回调，不导入EE业务。已有业务检查继续生效，不以个人额度取代VK自身限制或MCP权限。

[局部实测](../../evidence/按人用量与额度-重新开发复用验证.md)只证明：同预算累计可复用；修改额度保留用量；既有计数器不能固定迟到费用的旧周期，缺失预算也不会自动拒绝。不能因此宣称整条链已经打通，也不能因此直接照搬旧候选的账本、缓存和重试器。

## 3. 跨期接口契约草案

这里固定业务语义和跨期交接，具体函数签名与物理表结构在所属期细化，不提前生成未使用的代码。

| 契约 | 固定语义 | 首次落实 |
|---|---|---|
| 模板 | 配置与版本；复制给员工，模板后改不传播；删除不影响已分配副本 | 期1，四个模板接口以方案v2为准 |
| 个人配置 | 一个账号一份当前配置；重套/调额/恢复保留用量；批量操作返回明确成功或冲突，不留下部分成功 | 期2 |
| 归属 | 服务端验证的员工ID、VK ID和调用开始时间；不得用创建者或客户端request_id代替可信归属 | 期3—4 |
| 调用事实 | 服务端事件身份、尝试/轮次身份、用量、费用状态和原归属；已发生事实不随配置修改迁移；去重不能吞掉真实重试费用 | 期4—5 |
| 费用状态 | 已定价（包括明确零）、缺价、缺用量分开；未定价金额不可冒充0；所有协议使用同一事实写入规则和网关算价口径 | 期5—6 |
| 周期 | 原开始时间和生效配置可追溯；默认UTC自然月；跨月迟到费用归原周期；自然换期与“调配置清零”是不同操作 | 期5、7 |
| 准入 | 新调用重新检查账号、分配、模型和限额；缺绑定数据/数据库失败不得降级成普通VK；在途请求仍结算 | 期7—8 |
| 查询 | 本人身份来自会话，不能参数指定他人；管理员按权限查询；总数、密钥分项、待核对列表采用相同时间/费用口径 | 期9 |
| 长生命周期调用 | 异步提交/实时轮次/Batch提交固定归属；执行前或下一轮重查准入；结果迟到不改变原归属 | 期10、14—18 |

权限检查应覆盖额度接口及可能绕过它们的既有写入入口。普通VK保持原行为；受管VK的归属和额度不能由使用人通过旧接口或配置同步绕过。后台新增接口沿用EE会话、同源和JSON校验规范。

归属句柄可放请求上下文，流式内容不得放入上下文；读取对象池对象必须在释放前复制所需小型事实。统计、治理与协议适配共用个人事实口径，不能各自维护一套互不校验的余额。

每期涉及API时同时交付字段、权限、错误码、请求/响应示例和兼容说明；期9汇总给前端联调用。**这些是后端交付，不包含页面实现或前端验收。**

### 启用与验收顺序

- 期1—3：模板、分配、绑定API在隔离环境验收；绑定接口的生产开放随期9完整闭环推进。期3不向生产启用绑定，避免期4尚未装配时将绑定密钥当普通VK放行。
- 期4—8：在隔离环境对真实钩子、持久化、价格和拒绝链路分别验收，复用同一测试调用入口逐期扩展；不新建一套仅供演示的模拟业务。
- 期9：联合验收期1—9。两人各100美元，甲两把VK消耗10+15后合计25，乙不受影响；重套仍为25；验证超额、停用、恢复、重启、跨月、权限和待核对记录。通过后标准非流式文本/Embedding及Rerank、OCR、Compact才具备完整启用条件。
- 期10—15：每种调用链通过当期真实路径验证后，再进入受管支持范围；未完成的受管路径明确拒绝。阶段性拒绝不代表从完整需求删除该能力。
- 期16验收提交组件与持久归属，期17验收独立结算与待核对，均保持受管Batch生产入口关闭；期18完成重启/补价恢复和联合验收后再具备启用条件。
- 每期均复测未纳管VK及未注入扩展时原行为。收口时汇总全部后端验收矩阵；不另设一个不受行数约束的“大联调修复期”。

### 调用类别边界

“普通后台异步”沿用此前确认的网关异步队列含义，不等同于所有Provider任务。本次对未点名的生命周期作显式边界解释，不把它们临时塞进后期；若用户另要求纳入，需先修订需求与分期。

|---|---|
| Chat/Text/Responses普通前台、Embedding | 期4—9；对应流式与网关`/v1/async/*`在期10，异步不能绕过其内部操作的支持范围 |

### Batch适配职责（期16—18）

源码核查显示现有宿主从日志插件启动轮询，`AccountJob`要求非空`AggregateLogStore`，未定价结果不经过`UsageReporter`，且默认待处理扫描排除`unpriceable`。因此不能只连接`ReportUsage`便宣称关日志和补价恢复均可用。

| 缺口 | 责任、实现方向与期次 |
|---|---|
| 关普通日志后没有轮询 | 期17由EE app持有受管Batch结算生命周期，复用`jobaccounting.Sweeper`与既有厂商结果获取能力；隔离受管作业范围并协调既有作业claim，避免与日志插件竞争后漏报个人费用 |
| 必需的聚合记录存储 | 期17由EE usage持久化层提供`AggregateLogStore`兼容适配，复用既有存储能力并保留结算必需记录；其生命周期不依赖日志插件开关，不新建请求日志系统 |
| 全缺价/部分缺价未上报 | 期17由EE结算适配将已定价、未定价及部分未定价结果送入期5统一事实与期9查询；不能只监听成功`UsageReporter`。优先包装已有Settler/JobStore接口；如无法完整观察终态，使用当期预算内的可选结果出口，并在细案论证签名与默认不变行为 |
| 补价后默认不会再跑 | 期18由EE明确选择待核对作业并经现有claim/结算入口重驱，设置允许重新结算未定价作业的条件；不假设普通扫描自动覆盖。先提供有权限的手动重算入口，不新增通用调度平台 |
| 重启/重放/前台取结果 | 期18以期16持久归属和期17统一事实身份去重；按模型/计费分项补齐缺失金额，已定价部分不重复增加；关普通日志时同样成立 |

期17/18分别预留80/40行上游可选扩展预算（已含在生产列），并非事先决定必须修改。普通VK沿用现有结算；两条装配同时存在时的claim、聚合记录与个人报告完整性是期17必须验证的场景。
