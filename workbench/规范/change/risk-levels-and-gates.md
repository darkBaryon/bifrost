# 风险分级与条件 Gate

[← 返回 Change 模型](README.md)

两个原则，分别解决"流程太重"的两个来源：

1. **流程重量与风险匹配**——不是所有任务同重量；
2. **Gate 条件触发**——只在存在真正的人类决策时打断，没有拍板项就自动继续。

## 三级分级（判据只看风险，不看感觉）

| 级别 | 判据 | 必需产物 | 流程 |
|---|---|---|---|
| **L1 快速** | 局部修改、小 bug、小功能；不动公共接口、不动数据、错了看 diff 就能回滚 | 需求摘要（几句话）＋ 交付摘要（一页内） | 摘要 → 实施 → 机械检查 → 独立复核（含收敛评审一段话版）→ 用户看摘要/diff 点头 |
| **L2 标准** | 多模块；API / Schema / 状态变化；普通复杂度业务 | ＋ 正式方案、方案复核、收敛评审记录 | L1 基础上：方案 → 方案复核 → [Gate 1]* → 实施 → 收敛评审 → Gate 2 |
| **L3 严格** | 支付、权限、Migration、高风险数据写入、大规模重构、跨系统 | ＋ 完整影响预估、独立测试、逐维收敛评审、回滚预案 | 完整流程，所有 Gate 必现，实测验收 |

*[Gate 1] 条件触发，见下。

### 与三套规范内档位的关系

Change 级别是**跨流程类型的统一级别**；开发/重构规范内原有的"轻量级 / 标准级 / 蓝图级"是各流程类型内部的实现细节，继续适用。对应关系：

- L1 ≈ 轻量级；L2 ≈ 标准级；L3 ⊇ 蓝图级。
- 差别在 L3：它除了结构尺度（跨子系统、多期交付），还包含**风险域**——支付、权限、Migration、高风险数据写入即使只动一个模块，也按 L3 走。结构不大但风险高的 Change，取 L3 的证据要求（影响预估、独立测试、回滚预案），流程步骤可按标准级执行。

### 两根保险丝（沿用，不变）

- **就高不就低**：判据落在两级之间取高级；未知情况不得按低风险处理。
- **升级不降级**：实施中发现实际风险超出定级（碰到了公共接口、动到了数据），立即停、登记偏差、重新定级；不允许"悄悄按低级做完"。多个相关小改动不得拆开分别走 L1 来规避整体风险。

## Gate 条件触发

Gate 存在的唯一理由是**用户不可替代的决策**。拍板项清单（判断"要不要出 Gate"只看这张表）：

- 多种方案需要取舍；
- 业务规则的解释或取舍；
- 架构方向选择；
- 对外公共接口 / 契约变化；
- 花钱、引入外部依赖或服务；
- 接受某项风险；
- 范围扩大 / 定级变更；
- 高风险操作（删数据、不可逆迁移、对外发布）。

规则：

- **有拍板项 → 出 Gate 卡片**（[模板](../templates/common/gate-card.md)：结论一句话 + 拍板项 + 抽查菜单 + 风险提示），等用户裁决；
- **无拍板项 → 自动继续**，在 Change 文档留一行痕：`Gate 1 自动通过：无拍板项`。事后任何人可以质疑这个判断——错判"无拍板项"与漏登记偏差同罪；
- **Gate 2（最终交付）不可省略**，但重量分级：L1 = 看交付摘要 / diff 点头；L2 = 摘要 + 抽查菜单任选；L3 = 完整验收，涉及对外行为或数据落库时推荐实测。

## 交付摘要（所有级别的统一出口）

无论哪级，Change 结束时用户拿到一页内的交付摘要：做了什么、证据在哪（测试/预飞/评审链接）、收敛评审结论、遗留项（REF / Finding）。用户的日常体验应该是**读摘要，而不是读流程**。
