# 收敛评审

[← 返回规范主页](../../规范.md) · [流程](../流程.md)

代码评审管**对不对**：对照方案、行为正确、失败可观测、测试可信、无残留（见 [交付.md](交付.md)）。收敛评审管**像不像、乱不乱**：以项目长期维护者的工程判断，检查新增代码是否融入现有项目、实现是否清楚简洁、以后是否便于维护——既审整体架构，也审局部实现；功能正确和测试通过不能代替这个判断。两者读同一份 diff、互相独立、可并行，**范围分开不重叠**；看到对方范围的问题，写进出口清单的「转代码评审」栏，不出结论、不重复处理；转交条目由实施者交给代码评审的差量复核，处置结果进 Gate 2 请求。每个 Change 必经收敛评审，重量随[风险分级](../风险分级.md)。

操作步骤、各维度的具体信号与查法、意见写法见 [收敛评审审查方向.md](收敛评审审查方向.md)；本项目的"同类实现约定"以 [项目/编码规范.md](../项目/编码规范.md) 为参照，上游风格不是 ee 的契约。

涉及 EE 后端时，以 [EE 后端架构](../../../product/架构/EE后端架构.md) 为架构与依赖关系的依据。「架构与项目一致性」维度必须分别核对架构符合性和依赖关系，具体信号见审查方向页；历史布局不覆盖已确认的目标约定，也不因此要求本次全量迁移旧代码。

通读实际代码及相关既有实现，检查架构和组织方式是否一致、职责是否清晰、抽象是否必要；同时关注命名能否表达含义、业务限制是否有合适的命名常量、控制流与状态是否多余、转换及错误处理是否重复。对有维护影响的偏离提出最小改进方向；既有代码有明确问题时，说明合理偏离的依据，不机械复制旧问题。

## 第一原则

**机械检查产事实，判断只属于评审 agent，任何指标不得直接构成结论。**

- 脚本与命令（依赖 diff、文件增长、契约 diff、重复搜索）只产出事实，作为证据喂给评审；
- "文件超过 N 行""重复率超过 N%"这类指标**永远不允许**直接判定结论——指标只指路，判断靠读代码；
- 每条意见给出具体位置、维护影响及最小改进方向；需要取舍的结构建议另给**反证条件**——一个能推翻该提议的具体事实。局部修整可用一句话说明，不为凑意见而要求改名、抽象或搬文件。

## 重量分级（成本与改动规模成比例）

四维是**责任清单，不是操作步骤**，不能代替完整阅读和工程判断，也不要求四次独立扫描。按风险和相关性确定阅读深度；不以耗时、发现数量或报告篇幅判断评审是否充分。

| 级别 | 执行方式 | 产物 |
|---|---|---|
| **L1** | 由独立复核者在复核时顺带完成，一次通读 | 交付摘要里一两句话，依据复核结果给结论，**不建单独文档** |
| **L2** | 可与代码评审同一独立 agent：先评正确性，再评架构一致性与实现质量 | 单独收敛评审记录，四维表可收束为段落 |
| **L3** | 必须独立于代码评审的干净上下文 agent，高配模型 | 逐维留痕的完整记录 |

## 独立性

不变量只有一条：**评审者与本 Change 的实施上下文隔离**——不能是写代码的那个会话自评。是否再与代码评审分开，按上表级别决定；L3 的架构与实现质量判断没有事实表托底，不降档。

上下文隔离还不够：由实施方撰写提示词、划定范围或在评审途中发消息，同样会影响评审。因此收敛评审统一由 [启动脚本](../../tools/convergence_review.py) 在新的 Claude Code 会话中执行（`claude-opus-5`，effort high）：

- 实施方在预飞全绿、提交候选后运行脚本并在后台监控，不依赖用户手动开会话；
- 提示词由脚本按 [提示词模板](../../templates/收敛评审提示词.md) 与 checklist.yaml 机械生成，文件清单取 git diff；实施方不撰写、增删或改写提示词，不限定范围，评审期间不与评审者通信；
- 首轮整包，后续轮次对上一轮候选做差量复核，每轮都是新会话；
- 评审原文由脚本落盘为 `收敛评审<R>.md`，实施方不改写，有异议在下一轮或交用户裁决。

## 输入

1. 基线到实际交付物的完整 diff（交付物含未提交工作树时，纳入未暂存及新增文件，不能只看基线..HEAD）；
2. 存量代码（读被改文件的**完整现状**和相关同类实现，不只读 diff 行；将同类实现作为判断惯例与复用的依据，必要时用 `git log` 追溯演化原因）；
3. [Finding 台账](finding台账.md)与豁免记录（不重提已裁决的问题）。

## 四个必看维度

这是**注意力清单，不是打分表**——保证每个维度被看过，不规定每个维度必须有产出，也不规定分维度调查（见"重量分级"）。测试是否可信、非功能（性能、并发、安全、可观测性、数据一致性、部署与运维成本）属于代码评审，本评审不审；测试代码作为代码，其重复与组织仍按四维看。

| 维度 | 核心问题 |
|---|---|
| **重复** | 新代码是否已有等价实现？是否出现第二套业务规则、重复转换 / 错误处理 / 工具类、同概念不同命名？ |
| **职责与实现质量** | 职责、函数和依赖是否清晰且必要？命名、常量、控制流是否表达业务含义？是否存在多余状态、防御或兼容分支？文件与包的组织是否符合[编码规范](../项目/编码规范.md)，是否因过度拆分让简单操作难以完整阅读？ |
| **架构与项目一致性** | 是否遵循同类实现的合理约定、复用既有能力？是否另起一套架构、放错职责、绕过接口或引入反向依赖？ |
| **契约一致性** | 前端类型、后端 Schema、SDK、OpenAPI、Enum、Error Code、开发指南是否同步？ |

## 结论与四个出口

**发现问题与请求用户裁决分开。** 当前授权范围内可解决的质量问题列为「本轮修复项」，交实施者修复后定向复核；评审者只出意见，不顺手改代码。只有涉及范围、契约、风险接受或显著方案取舍时，才按流程请求用户裁决；不为每个小修建立 REF/Finding。这里不新增 frontmatter 状态。

**意见按阻塞性分栏，只有阻塞项才用 `有Blocking`：**

| 栏目 | 判据 | 后果 |
|---|---|---|
| **本轮修复项**（阻塞） | 结构或契约损伤会让后续开发付出实际代价：第二套业务规则、职责错位、反向依赖、对外契约不同步、命名或常量会误导修改者 | 修复并定向复核，未关闭时 `有Blocking` |
| **建议（nit）**（不阻塞） | 只涉及注释措辞、文档表述、局部命名、组织偏好，不改变执行路径，也不影响对契约的理解 | `无碍` 或 `仅立债挂账`，**不阻塞交付**；实施者自行决定当轮改还是挂账 |

判断标准是**维护者会不会因此改错东西**：会 → 本轮修复项；只是读着不够顺 → 建议。一份记录里只有建议时，出口取 `无碍`（有挂账条目则 `仅立债挂账`），不得因"还有话说"而给 `有Blocking`。

**差量轮的职责是收敛**：核对上轮本轮修复项的关闭情况、检查修复是否带来新的结构损伤；对本轮只改了注释、文档或命名的部分不开新的本轮修复项——上一轮要求的文字修改本身不应成为下一轮的审查对象，否则轮次无法终止。

| 出口 | 判据 | 去向 |
|---|---|---|
| **无碍** | 本轮修复项为空或已关闭/有依据撤回，无未处置的已确认损伤；建议栏有条目不影响本出口 | 正常走 Gate 2 |
| **Blocking** | 本轮必须解决的代码质量问题尚未关闭，或存在必须先处理的结构 / 契约风险 | 阻塞 Gate 2；范围内修复直接推进，需取舍的交用户裁决 |
| **REF Case** | 变差了，但事后治理不比现在贵 | 照常交付；立 REF 需求（`triggered_by: [<本case>]`）进队列 |
| **Finding** | 问题可能存在，证据还不足 | 记入 [Finding 台账](finding台账.md)，达到触发条件再转 Case |

记录模板：[`templates/收敛评审.md`](../../templates/收敛评审.md)。

## 校准（防噪音，最重要）

1. **维护影响是提出问题的依据，用户裁决门槛不是发现门槛**。能说明理解、修改或保持一致性成本的问题应提出；无维护收益的个人偏好不要求修改。
2. **修复优先局部调整和既有能力**。不机械消灭所有数字或近邻重复，不为降低行数牺牲清晰度，不为假设的未来需求添加通用框架。不强求发现问题；可延期的问题按实际影响立债或挂账，不能因无需用户拍板而消失。
3. **不重提已豁免的问题**，除非本次改动使其显著恶化。
4. **范围外的发现只转交，不裁决**：正确性、测试、非功能问题写进出口清单「转代码评审」，一行一条，不出修复意见；不借局部整理擅自改变 Gate 1 已确认的目标和契约。

## 闭环

结构改善的唯一诚实证据是后续开发不再被绊住：REF Case 完成后，其效果由**后续 Change 的收敛评审**验证（同一双眼睛再看一遍），不用指标断言验证。
