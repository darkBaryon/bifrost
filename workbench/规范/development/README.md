# 开发规范

[← 返回仓库首页](../README.md)

开发规范用于把新需求或缺陷修复变成可交付的代码变化。它回答四件事：做什么、怎么做、怎样证明做对、什么时候可以集成。

如果任务的主要目标是改善既有结构而不是改变能力，使用[重构规范](../refactoring/README.md)；如果只需要验证一个已经固定的版本，使用[测试规范](../testing/README.md)。

## 完整流程

```text
1. 立案与定档
   明确需求、非目标、基线和风险档位
        ↓
2. 方案与方案复核
   设计接口、数据、步骤和验收口径
        ↓
3. Gate 1
   用户确认范围、业务取舍和实施方向
        ↓
4. 隔离实施
   在项目规定的分支/Worktree 中小步开发
        ↓
5. 预飞与代码复核
   机械检查全绿，独立核对方案、commit 和 diff
        ↓
6. Gate 2
   用户基于测试、证据和剩余风险确认交付
        ↓
7. 按项目规则集成、清理和归档
```

轻量任务可以简化文档，但不能省略四个事实：目标、精确基线、验证证据和用户放行。

## 最小清单

- [ ] 需求来源、目标和非目标已经写清；
- [ ] 已确认基线、当前分支和工作目录；
- [ ] 已按风险定档，未知情况没有被当成低风险；
- [ ] 实施前已确认接口、数据、步骤和验收标准；
- [ ] 代码只落在已确认范围内，偏差已经显式处理；
- [ ] 静态检查、相关测试、构建或演示已形成事实证据；
- [ ] 独立复核已经对照方案检查实际 diff；
- [ ] 用户明确通过 Gate 2 后，才按项目规则集成；
- [ ] 临时日志、本机配置、无用代码和工作资源已经清理。

## 状态参考

需求可以使用：`观察中 → 待计划 → 开发中 → 已交付`，另有 `已作废`。

方案可以使用：`草拟中 → 待评审 → 需修改 → 已通过 → 已实施 → 已归档`。

状态只表示已经发生的事实。不能因为“看起来快完成了”提前流转，也不能用聊天中的口头表达代替 Gate 决策。
