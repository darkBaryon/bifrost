# 1. 立案、职责与分级

[← 开发规范](README.md) · [下一章：方案与 Gate 1 →](02-plan-and-review.md)

## 先确认这是开发任务

开发任务的起点是希望新增或改变的可观察行为，包括新功能、普通功能调整和缺陷修复。立案时先查重，确认它不是已有任务、纯结构治理或只需执行测试。

立案记录至少包含：

- 来源和一句话目标；
- 当前为什么做不到；
- 做完后用户能观察到什么变化；
- 明确的非目标；
- 初步验收结果；
- 已知期限、依赖和风险。

使用 [`templates/development/requirement.md`](../templates/development/requirement.md) 可以快速建立记录。

## 固定起点

写方案前必须确认实际工作对象：

- Git 项目记录完整基线 commit SHA、当前分支和工作目录；
- 非 Git 工作记录明确的文件清单、版本或时间戳；
- 现有未提交修改逐项确认归属，不能覆盖或夹带他人工作；
- 构建、环境、设备会影响结果时，先读取业务项目的落地规则。

所有后续 diff、评审和验收都以该起点为参照。基线变化时，必须重新判断方案和验证范围是否仍然成立。

## 职责

| 职责 | 在开发流程中的责任 |
|---|---|
| 设计职责 | 查重、提出档位、定义目标和非目标、写方案、整理 Gate 信息 |
| 实施职责 | 按确认范围小步开发、自检、记录实际实施和偏差 |
| 复核职责 | 独立读取基线、方案和产物，验证方案或代码并给出证据化结论 |
| 决策职责 | 用户确认档位、业务取舍、风险接受和 Gate 放行 |

设计和实施可以由同一人或同一会话承担。正式复核必须重新读取事实，不能直接采信实施者的自我结论；复核发现问题后交回实施职责修改，不在复核过程中顺手改代码。

## 开发分级

| 档位 | 判据 | 最低流程 |
|---|---|---|
| 轻量级 | 少量相邻文件，无新公共接口和数据结构变化，完整 diff 可直接理解 | 需求简记 → 实施 → 相关检查和 diff 复核 → 用户 Gate |
| 标准级 | 单项目内涉及多个模块，存在明确接口、状态或交付行为变化 | 完整方案 → 方案复核 → Gate 1 → 实施 → 代码复核 → Gate 2 |
| 蓝图级 | 跨子系统、重设计公共契约或需要多期交付 | 开发蓝图 → 蓝图复核 → Gate 1 → 各期按标准级执行 |

定档程序：

1. 设计职责提出档位；
2. 用一句话说明命中的风险判据；
3. 用户确认或调高档位；
4. 将裁决和理由写回任务记录。

行数和文件数只能作为经验锚点。信息不足或同时命中多个档位时按较高档准备；降档必须说明哪项风险已经被事实排除并由用户确认；执行中发现接口、范围、失败后果或验证难度超出原判断时立即停下升档。多个相关小改动不得拆开后分别走轻量流程来规避整体风险。

## 蓝图级任务

蓝图只定义整体目标、非目标、模块边界、公共契约、分期、依赖、终态验收和回滚策略，不提前猜完后期实现细节。

- 第一期应是能证伪关键假设的垂直切片；
- 每期独立走标准级流程；
- 上一期未验收，不开始下一期实施；
- 后续期方案在前期结论稳定后再细化；
- 关键假设被证伪时，修订蓝图并重新复核和 Gate。

## 项目落地边界

具体的主线、集成分支、功能分支命名、Worktree、本机 SDK、测试环境、构建命令、共享设备和发布审批都由业务项目规定。通用规范要求的是“必须证明什么”，业务项目决定“使用什么命令和资源证明”。项目规则可以细化或收紧本规范；需要放宽时必须登记偏差并由用户确认，不能静默覆盖。

发生冲突时按以下顺序处理：用户明确裁决和安全约束 → 本开发规范 → 业务项目规则 → 单次任务方案。
