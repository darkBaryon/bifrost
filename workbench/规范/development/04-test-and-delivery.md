# 4. 测试、代码复核与交付

[← 上一章：实施与预飞](03-implementation.md) · [开发规范](README.md)

## 开发自测与独立测试

实施职责先完成与风险相称的开发自测。标准级和高风险行为通常还需要按[测试规范](../testing/README.md)对精确 commit 或产物进行独立测试。

开发自测、推送供打包和独立测试通过是三个不同事实：

- 开发自测说明实现者认为可以交测；
- 推送分支只说明测试对象可以被获取；
- 独立测试通过说明规定范围在指定版本和环境中得到验证。

测试发现缺陷后，记录失败版本和证据，修复形成新 commit，再对新版本复测；不得把旧版本的通过结论沿用到新版本。

## 代码复核

复核职责对照需求、最终方案、基线和 commit 亲自检查：

- 实际功能是否满足验收标准；
- 方案声明、实施记录、偏差记录和 diff 是否一致；
- 多出的功能、公共接口、抽象或依赖是否构成范围偏差；
- 失败、空值、取消、重复触发和兼容路径是否正确；
- 自动化测试是否验证业务行为，而非碰巧的实现形态；
- 是否存在调试残留、本机配置、未使用代码或无关改动。

首轮覆盖完整范围。修改后进行差量复核；无法证明未修改区域不受影响时恢复全量复核。复核者不能以实施者提供的“已测过”代替亲核。

## Gate 2：交付验收

请求 Gate 2 时提供：

- 本次验收的精确 commit 或产物；
- 需求和验收标准覆盖情况；
- 自动化、构建、运行态和独立测试结论；
- 未执行、阻塞和遗留风险；
- 需要用户决定的事项；
- 通过后如何集成，不通过后回到哪个阶段。

用户可以按风险选择查看事实表、抽查一个入口或亲自操作关键路径。没有明确通过 Gate 2，不得把“代码已完成”“分支已推送”或“合并请求已创建”解释为获准集成。

## 集成和清理

Gate 2 通过后，严格按业务项目规则创建或更新合并请求、进入集成分支并执行最小冒烟。通用规范不预设直接推送、MR、squash 或发布分支名称。

收口时：

- 确认集成对象仍是已验收版本；
- 清理临时日志、测试后门和不再使用的代码；
- 保留方案、评审、事实表、测试和验收记录；
- 按项目规则删除已完成的功能分支和 Worktree；
- 将长期有效的接口、运行或维护口径回填到业务项目文档；
- 状态流转为“已交付/已归档”。

集成后冒烟失败时停止后续发布，记录新的精确版本并回到缺陷修复和复测流程。
