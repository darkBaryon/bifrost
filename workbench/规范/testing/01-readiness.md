# 1. 职责、风险分级与测试准入

[← 测试规范](README.md) · [下一章：执行与证据 →](02-execution.md)

## 职责

| 职责 | 主要责任 | 不得做的事 |
|---|---|---|
| 开发职责 | 提供测试计划初稿、自动化测试、开发自测、精确版本和已知盲区 | 把自己的自测写成独立测试通过 |
| 测试职责 | 独立核对版本和环境、执行用例、补充反例、记录证据并给出结论 | 修改被测代码、采信口头结论、把未执行或阻塞判成通过 |
| 修复职责 | 根据失败证据修复、补回归测试、提供新版本 | 覆盖旧记录或混入无关改动 |
| 决策职责 | 用户确认档位、授权测试条件、接受剩余风险并完成业务验收 | 重复测试职责已经完成的机械检查 |

同一主体实现并执行的测试标记为“开发自测”。独立测试必须重新核对测试对象和运行条件，亲自执行规定范围；正式结论不能直接继承开发者的判断。

## 风险分级

测试分级看失败后果、影响面和验证难度，不按代码行数判断。

| 档位 | 判据 | 最低测试组合 |
|---|---|---|
| 轻量级 | 纯文案/样式、纯函数小修，失败易发现、易回滚且不改变业务数据 | 相关静态检查 + 单元/组件测试或精确人工检查 + diff 复核 |
| 标准级 | 页面/API 交互、状态流转、普通数据解析或兼容性变化 | 轻量级全部 + 可运行产物 + 主路径 + 相关回归 + 独立测试记录 |
| 高风险级 | 支付、合同、身份、权限、关键数据写入、不可逆操作、跨系统或第三方链路 | 标准级全部 + 有效测试数据端到端 + 失败/取消/重试 + 结果状态核对 + 业务验收 |

准备职责提出档位和一句话理由，由用户确认或调高。信息不足时按较高档准备；降档必须说明哪项风险已经被事实排除并由用户确认；执行中发现失败后果或验证难度更高时立即升档。缺账号、数据、服务或平台条件时记为阻塞，不能用低层测试替代高层结论。

## 最小交测包

- 需求或缺陷来源与一句话目标；
- 基线、分支、完整 commit 或版本；
- 构建/部署方式、产物标识和内容哈希；
- 风险档位、必测用例、回归范围和非目标；
- 开发自测事实表和已知盲区；
- 环境、账号、脱敏数据和外部依赖准备说明。

测试记录不得包含 token、密码、完整身份信息、合同全文或生产客户数据。

## Gate T0：测试准入

进入执行前必须确认：

- 测试对象已经提交并可获取，不在持续变化；
- 完整 commit、构建标识或产物哈希与计划一致；
- 构建输入和业务工作区可解释，没有未声明改动；
- 必要静态检查、自动化测试和构建已经完成；
- 实际运行环境、设备或平台与计划一致；
- 账号、测试数据和外部依赖已准备，或阻塞范围已明确；
- 用例写明前置条件、单步操作、每步期望、回归和证据要求。

Gate T0 只证明“可以正确开始测试”，不证明功能正确。测试对象、环境或关键数据在 T0 后改变时，受影响结论失效，必须重新准入。

## 项目落地和共享资源

业务项目负责规定环境地址、构建命令、设备型号、账号、数据和共享资源协议。测试前核对实际运行态，不能只看配置文件中的期望值。项目规则可以细化或收紧本规范；需要放宽时必须登记偏差并由用户确认。

共享模拟器、真机或账号应按短操作窗口串行使用：编辑代码、等待反馈和普通构建期间不默认长期持有资源；确需连续调试时使用明确的限时独占。资源锁的获取、续期、释放和故障处置必须由项目规则定义，测试任务不得擅自抢占或破坏其他会话。

发生冲突时按以下顺序处理：用户明确裁决和安全约束 → 本测试规范 → 业务项目规则 → 单次测试计划。
