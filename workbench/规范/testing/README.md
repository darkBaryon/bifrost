# 测试规范

[← 返回仓库首页](../README.md)

测试规范用于对一个精确的软件版本建立可信结论。它覆盖开发自测、独立测试、缺陷复测和发布准入；模拟器、真机、浏览器、API、数据库和自动化测试只是不同的执行平台。

测试流程原则上不修改被测代码。发现缺陷后固定失败证据，交回开发或修复职责形成新版本，再进入复测。

## 完整流程

```text
1. 测试立案和风险分级
   明确要证明什么、最坏失败后果和最低覆盖
        ↓
2. 固定版本、产物、环境和数据
   Gate T0 确认测试可以正确开始
        ↓
3. 分层执行并记录原始证据
   差异 → 机械检查 → 运行态 → 主路径 → 边界 → 回归
        ↓
4. 缺陷修复与复测循环
   失败证据 → 新版本 → 失败项复测 → 影响面回归
        ↓
5. Gate T1
   独立测试职责对当前精确版本给出结论
        ↓
6. Gate T2
   用户接受业务结果和剩余风险
        ↓
7. 按项目规则形成发布准入结论并归档
```

## 最小清单

- [ ] 测试目标、非目标和风险档位明确；
- [ ] 分支、完整 commit、产物和哈希能够对应；
- [ ] 实际运行环境、平台、账号和数据已核对；
- [ ] 用例具有前置条件、单步操作、每步期望和证据要求；
- [ ] 主路径、关键反例和相关回归已执行；
- [ ] 未执行、阻塞和失败没有被计入通过；
- [ ] 测试对象变化后，旧结论没有继续沿用；
- [ ] Gate T1 和 Gate T2 是两个独立结论；
- [ ] “已推送”“可安装”或“已建 MR”没有被写成“可发布”。

## 状态参考

```text
待测试 → 准备中 → 执行中
  ├→ 阻塞 → 准备中/执行中
  ├→ 未通过 → 修复中 → 待复测 → 执行中
  └→ 已通过 → 待业务验收 → 已验收 → 可发布 → 已归档
```

“已通过”只表示当前精确版本的规定范围通过；“已验收”表示用户接受业务结果；“可发布”还要满足业务项目自己的合并、审批和发布规则。
