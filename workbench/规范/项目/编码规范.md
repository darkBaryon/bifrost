# 编码规范

[← 返回规范主页](../../规范.md)

本规范只适用于 `ee/` 目录，因为只有这里的代码由我们自己维护。`ee/` 以外的代码不按这份规范修改或整理。

确实需要修改上游文件时，先读 [上游改动登记](../../../product/上游改动/README.md)：它规定了允许修改的条件（方案中单列白名单、改动为纯增量、合入后回填登记），并列出已有的全部改动。

## 架构符合性

EE 自有后端必须遵循 product 中的 [EE 后端架构](../../../product/架构/EE后端架构.md)，以该文档作为架构与依赖关系的依据。编码前核对相关章节，不能用上游现状或历史目录替代已确认的架构约定。

- 按业务能力分模块，模块内部保留分层。业务函数或服务负责规则与完整操作；HTTP、插件和 Worker 作为入口适配，调用所属模块的业务能力；存储实现负责持久化。
- 应用装配集中在 `app`，只负责依赖装配与生命周期，不承载运行期业务编排。跨功能的 Bifrost 集成与具体业务插件按架构文档分别归位。
- 保持 EE 内嵌完整 Bifrost HTTP 应用的边界，核对共享 Server、Router、嵌套 Handler 和资源所有权；不因拆包另起一套网关或基础设施。
- 模块边界或依赖方向需要变化时，同步更新 product 中的架构决策；模块内部实现细节写在包 README。

例如，新结构中的品牌模块为 `internal/branding/`，HTTP 入口为 `internal/branding/http/`；护栏的管理接口和推理插件同属 `internal/guardrails/`。不要把所有功能平铺进一个大包。现有品牌功能已迁入上述结构，其他功能按实际任务建立。

## 依赖关系

依赖设计遵循 [EE 后端架构](../../../product/架构/EE后端架构.md) 第 5 节「依赖与协作」和第 7 节「与 Bifrost 的协作边界」：

- HTTP、插件、Worker、存储等实现依赖业务根包；业务根包不反向导入这些实现。fasthttp、GORM、Bifrost 和外部 SDK 的具体类型留在适配实现中。
- 简单配置功能直接调用同模块具体存储的适用条件见架构第 5 节，不要求每个模块都有 Service 和 Repository。
- 接口由使用方按实际需要定义，通过构造函数显式注入依赖；业务服务不从全局 Server、Config 或服务容器查找依赖，不引入万能 Repository 或 BaseService。
- 跨模块通过公开能力和窄接口协作，避免双向包依赖；不直接修改其他模块的表。事务范围由业务服务决定，存储实现执行，不把 `*gorm.DB` 传入业务层。
- 新增依赖、封装或基础设施前，核实已有业务能力和 Bifrost 能力能否复用；按具体缺口引入，不重复包装整套 SDK。共享资源的创建、注入与关闭责任必须明确。

## 硬规则：命名、重复与类型分工

以下规则在收敛评审中按条核对，违反即为本轮修复项，不适用"不机械消灭数字"的校准豁免：

- **对外枚举必须是命名常量。** 会持久化或出现在接口响应里的取值（账号状态、事件动作与结果、操作者标识等）在业务根包定义为类型化常量，代码里不出现同义的裸字符串；测试和脚本按契约独立书写字面量，不受此限。
- **业务限制要命名，派生值要写推导。** 方案规定的阈值、长度、时长、并发上限各有一个命名常量并注明来源；由其他值推导出的数（如编码后长度、秒数）用表达式从源值算出，不手抄结果。
- **同一条规则只在一处实现。** 同一校验、同一比较、同一重试或转换逻辑只有一份；多处需要时抽成包内函数并互相引用。两处逻辑相同但注释说明"用途不同"的，仍算重复。
- **业务类型、接口 DTO、数据库行分开定义。** 业务根包的类型不带 `json`/`gorm` 标签；HTTP 包定义响应与请求结构并做转换；存储包定义行结构并做转换。业务类型加字段不得改变接口输出或表结构。
- **导出符号必须有用途注释；特殊返回值必须交代。** 例如"未找到视为未认证""同状态不升版本""失败事件仍提交"这类语义写在函数注释里，与代码不一致的注释视为缺陷。
- **依赖显式注入，不从其他对象的字段取用。** 需要某个服务就在构造函数里接收它，不通过 HTTP 处理器等中间对象的导出字段间接取得；包外没有使用方的符号不导出。
- **日志经宿主注入的 logger 输出。** `ee/` 内不使用标准库 `log`；需要日志的包按实际用到的方法定义窄接口，由 `app` 把入口配置好的 logger 注入（架构 §7「按缺口扩展」）。
- **文件超过 300 行须评估拆分，超过 500 行必须拆分。** 按业务分组拆（例如会话、账号、密码各一个文件），或把协议管道与端点分开；拆分只搬动代码，不改行为。测试文件同样适用。

## 每个包都要有 README

`ee/` 下每个包的目录中都要有一份中文 `README.md`。**读者是第一次接手这个包、准备改它的人**：他没读过本包代码，也没读过上游代码。读完他应该知道这个包在干什么、该打开哪个文件、动手前要当心什么。

回答三件事：

- **这个包解决什么问题。** 不看代码也能懂：原来哪里不成立，本包怎么让它成立。
- **代码在哪。** 有明显流向的包画一张文件级的调用链，从入口一路到本包各文件，一行一个文件加一句职责；没有单一流向的用文件表，同样一行一个。都不细到函数：函数会改名会挪位置，文件是稳定的路标。
- **改之前要知道什么。** 读代码不容易一眼看出、改错了会出事的约束。

不写这些：函数签名与参数（那是 `godoc` 的事）、实现步骤与算法复述、内部取舍的论证（放代码注释或 Workbench）、过程叙述（「本轮改成了什么」）。判断标准是熟悉代码的人不需要、不熟悉的人也看不懂的内容一律删掉。

**少提外部名词。** 上游类型和其他包的符号能不提就不提；确实绕不开的，第一次出现就地用一句话说明它是什么，不能假设读者读过上游代码。

长度以一屏为限。`ee/internal/pricing/` 及其 `persistence/` 子包是参照样例。包的功能、文件或约束发生变化时同步更新。

## 文件组织以阅读为先

**同一包内，默认把需要一起理解、一起修改的代码放在一起；复杂后再拆。** 分层约束职责和依赖方向，不要求每个类型、接口或概念各占一个文件。

- 一个文件可以承载一组紧密相关的操作及其类型、错误和辅助函数。例如设置的查询、保存、重置通常可以放在一起。
- 小接口可以放在使用它的服务旁，错误和参数类型可以就近定义；不因它们分别叫 Repository、Error、DTO 就单独建文件。
- 某部分已经有足够的独立逻辑，拆出后能让两边更容易阅读和修改时再拆；仅有不同职责名称、未来可能复用或示例中单列了文件，都不是充分理由。
- 拆分前检查：理解一个简单操作是否反而要在更多文件间跳转；文件是否只剩声明、转发或零散辅助代码。若没有清晰收益，保持集中。

文件行数只设上限（见硬规则：300 行评估、500 行必须拆），不设文件数量或“每层几个文件”的指标，也不为减少文件数把业务、HTTP 和存储混回同一个包。架构文档中的模块示例只用于说明边界，不能当成逐文件脚手架；现有 branding 的文件粒度也不作为新功能模板。

## API 接口命名

我们自己的业务接口统一使用 **POST**，查询接口也一样。

路径按 `/api/功能/动作` 组织，动作后不重复功能名。例如用 `/api/branding/update`，不用 `/api/branding/updateBranding`。

命名示例：

```text
POST /api/branding/get       查询设置
POST /api/branding/update    保存设置
POST /api/branding/reset     恢复默认
```

图片等由浏览器直接读取的资源仍使用 **GET**，例如 `<img src="...">` 指向的图片地址。上游已有接口保持原样。

## 注释写清用途、约束和原因

自有代码新增注释统一用中文。注释要补充读代码时不容易看出的信息，不逐行翻译代码。

| 位置 | 怎么写 |
|---|---|
| 每个包 | 说明负责什么、不负责什么，写一处即可。 |
| 每个文件 | 顶部用一句话说明这个文件的职责。 |
| 对外类型和函数 | 说明用途；有特殊输入、返回值或副作用时必须交代。 |
| 内部函数 | 名字已经能说明用途的，不强制加注释；复杂逻辑或特殊处理必须解释原因。 |
| 关键字段和常量 | 单位、空值含义或业务限制不明显时，补充说明。 |

**修改代码时，必须同步检查并更新相关注释。** 已失效的说明及时删除，不能保留与实际行为不一致的注释。
