# 4. 代码复核、终扫与交付

[← 上一章：分期迁移](03-migration.md) · [重构规范](README.md)

## 代码复核

复核职责对照基线、最终方案、实施记录和 commit，亲自验证：

- 基线行为和调用方盘点是否仍然准确；
- 每个 commit 是否只执行声明步骤并保持可验证；
- 正常、失败、空值和兼容行为是否保持或按白名单迁移；
- 公共签名变化是否全部落在白名单；
- 调用方是否完整迁移；
- 旧接缝、临时兼容层和废弃代码是否按计划退出；
- 实际偏差是否与记录一致。

首轮覆盖完整范围。修订后只复核上轮意见、声明修改和受影响区域；无法证明其他区域不受影响时恢复全量复核。实施者自检不能替代复核结论。

## “碰巧同形”

扫描发现相似代码，不代表必须抽象。业务本质不同但结构相似的代码可以带证据留存；判断依据必须能够被事实证伪。没有证据的“以后可能复用”不能成为抽象或保留理由。

## 阶段终扫

项目支持时，阶段结束至少执行：

1. 格式、静态检查、测试和构建；
2. 重复代码与基线逐组对账新增、消除、位移和留存项；
3. 死代码与基线对账，确认没有新增不可达内容；
4. 公共接口签名 diff 与白名单逐项核对；
5. 调用方、旧符号、兼容层和过渡开关清理；
6. 生成代码重建并确认零漂移；
7. 长期架构文档回填。

工具不支持某项时，必须给出替代证据或明确剩余盲区。

## Gate 2：行为与终态验收

向用户提供：

- 精确基线和最终 commit；
- 原行为、允许变化和实际结果对账；
- 目标结构、调用方和公共接口完成情况；
- 自动化、构建、终扫和独立复核结论；
- 未执行、阻塞和遗留风险；
- 通过后如何集成，不通过后回到哪个阶段。

用户确认可观察行为、终态结构和剩余风险。没有明确 Gate 2，不得把“测试通过”或“代码评审通过”解释为可以集成。

## 集成与归档

Gate 2 通过后，按业务项目规则创建或更新合并请求、进入集成分支并执行最小冒烟。通用规范不规定直接推送、MR、squash 或具体分支名。

收口时保留基线、蓝图/方案版本、实施与偏差记录、事实表、评审和验收结论；清理完成分支、Worktree 和临时资源；回填长期架构口径；状态流转为“已处理/已归档”。集成后出现行为差异时停止后续发布，形成新的缺陷或重构轮次，不覆盖原结论。
