# 1. 基线、职责与分级

[← 重构规范](README.md) · [下一章：方案与 Gate 1 →](02-plan-and-review.md)

## 先证明问题存在

重构起点是结构问题、技术债或设计缺陷，而不是“这段代码看起来不舒服”。立案记录至少包含：

- 问题发生在哪里；
- 当前造成的维护成本、错误风险或扩展障碍；
- 文件、接口、依赖或测量证据；
- 希望达到的终态；
- 明确不在本轮解决的内容；
- 可证伪的成功口径。

先查重并确认没有已有方案。模板位于 [`templates/refactoring/issue.md`](../templates/refactoring/issue.md)。

## 固定结构和行为基线

所有盘点、diff、测试和验收绑定完整 commit SHA。开始前确认当前工作目录、分支、未提交修改和生成物状态。

现状盘点至少覆盖：

- 相关文件、模块和公共符号；
- 依赖方向和边界；
- 全部真实生产调用方；
- 当前正常、失败、空值和兼容行为；
- 现有测试、生成代码和架构规则；
- 已知重复、死代码和临时兼容层。

调用方必须向外追到真实生产使用者。零调用者需要说明保留理由，否则按死代码候选处理。不能只根据名称、局部搜索或设计文档推断现状。

## 职责

| 职责 | 在重构流程中的责任 |
|---|---|
| 设计职责 | 建立事实基线、提出档位、设计终态和迁移方案、整理 Gate |
| 实施职责 | 在确认范围内分步迁移、保持行为、记录实施和偏差 |
| 复核职责 | 独立核对基线、行为、调用方、方案、代码和终扫结果 |
| 决策职责 | 用户确认档位、结构方向、允许变化、风险和 Gate |

设计与实施可以由同一主体承担；正式复核必须重新读取基线和产物并亲自验证。复核职责只出结论和意见，不直接修改被复核代码。

## 重构分级

| 档位 | 判据 | 最低流程 |
|---|---|---|
| 轻量级 | 模块内少量文件，无关键契约变化，完整 diff 可核对 | 问题简记 → 修改 → 机械证据和 diff 复核 → 用户 Gate |
| 标准级 | 主体在一个模块内，少量外部调用方需要迁移 | 完整方案 → 方案复核 → Gate 1 → 迁移 → 代码复核 → Gate 2 |
| 蓝图级 | 跨包或子系统、设计模式级变化、重设计广泛依赖的公共 API | 蓝图和分期 → 蓝图复核 → Gate 1 → 各期完整循环 |

设计职责提出档位和一句话理由，由用户确认或调高。信息不足时按较高档准备；降档必须说明哪项风险已经被事实排除并由用户确认；执行中发现结构尺度、调用方、失败后果或验证难度超出原判断时立即停下升档。多个相互关联的小改动按整体影响定档。

## 项目落地边界

分支名、集成方式、语言工具链、重复/死代码工具、生成器和架构禁区由业务项目定义。项目缺少某项扫描能力时，方案必须给出替代核验或明确盲区，不能静默省略。项目规则可以细化或收紧本规范；需要放宽时必须登记偏差并由用户确认。

发生冲突时按以下顺序处理：用户明确裁决和安全约束 → 本重构规范 → 业务项目规则 → 单次任务方案。
