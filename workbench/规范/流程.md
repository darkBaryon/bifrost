# 流程

[← 返回规范主页](../规范.md)

**本页是执行序的唯一权威**——其他任何页面(含 AGENTS.md)只指向这里,不再自画流程图。

## 为什么以 Change 为中心

Change 是工程账本的最小完整单元:**一次有意图的系统变化,从提出、实施、评估影响到知识沉淀的完整生命周期**。以"开发需求"为中心时,重构没有需求可挂、测试结论悬在半空、一次功能引发的连锁治理会散落成互不知晓的文档;以 Change 为中心后,开发、重构、测试只是同一个 Change 内部的流程类型——共享同一套机制(方案/复核/实施纪律/交付),各自只带少量差异(见 [差异/](差异/开发.md))。

本仓 **case 名即账本主键**(不设 CHG/REF 编号);跨 Change 血缘用需求的 `triggered_by` 字段;类型 `feature / bugfix / refactoring / migration / dependency-upgrade / performance / security / maintenance` 决定默认关注点(如 migration 默认关注数据兼容与回滚),不决定流程重量——重量由[风险分级](风险分级.md)决定。

## 执行序

```text
立案定档(reports/;tier ↔ L1/L2/L3,见 风险分级.md)
→ 方案 + 方案复核(需修改则出 v+1,至通过;见 流程/方案与复核.md)
→ [Gate 1 条件触发:有拍板项才打断,见下]
→ 隔离实施(feature 分支;偏差即停;完成后方案尾部补实施记录三章节 → 已实施;见 流程/实施纪律.md)
→ 预飞(checklist.yaml + preflight,全绿才请评审)
→ 代码评审 ∥ 收敛评审(并行、互相独立、均与实施上下文隔离;见 流程/交付.md、流程/收敛评审.md)
→ Gate 2(用户拍板,不可省略;本轮必修项先修复并复核,需用户裁决的事项先裁决)
→ 验收记录 + finding 台账登记 + 知识沉淀 → 方案已归档、需求已交付
```

L1 允许整体简化(见风险分级),但四个事实不可省:目标、精确基线、验证证据、用户放行。

## 职责

| 职责 | 责任 |
|---|---|
| 设计 | 查重、提出档位、定义目标与非目标、写方案、整理 Gate 信息 |
| 实施 | 按确认范围小步执行、自检、记录实际实施与偏差 |
| 复核 | 独立读取基线、方案和产物,给出证据化结论;只出意见不顺手改代码 |
| 决策 | 用户确认档位、业务取舍、风险接受和 Gate 放行 |

设计与实施可由同一会话承担;**正式复核必须重新读取事实,不能采信实施者自我结论**。测试流程的职责细分(测试/修复)见 [差异/测试.md](差异/测试.md)。

## Gate 条件触发

Gate 存在的唯一理由是**用户不可替代的决策**。拍板项清单(判断"要不要出 Gate"只看这张表):

- 多种方案需要取舍;业务规则的解释或取舍;架构方向选择;
- 对外公共接口 / 契约变化;花钱、引入外部依赖或服务;
- 接受某项风险;范围扩大 / 定级变更;
- 高风险操作(删数据、不可逆迁移、对外发布)。

规则:**有拍板项 → 出 Gate 请求**(结论一句话 + 拍板项 + 抽查入口 + 最大剩余风险 + 通过/不通过分别发生什么),等用户裁决;**无拍板项 → 自动继续**,在方案「Gate 决策结果」留一行痕(`Gate 1 自动通过:无拍板项`)——错判"无拍板项"与漏登记偏差同罪。**Gate 2 不可省略**,但重量分级:L1 = 看交付摘要/diff 点头;L2 = 摘要 + 抽查;L3 = 完整验收,涉及对外行为或数据落库推荐实测。

## 交付摘要(所有级别的统一出口)

无论哪级,Change 结束时用户拿到一页内的交付摘要:做了什么、证据在哪(测试/预飞/评审链接)、收敛评审结论、遗留项(REF/Finding)。用户的日常体验应该是**读摘要,而不是读流程**。

## 知识沉淀(归档前必查)

Workbench 记录"系统为什么变成现在这样";主仓库长期文档记录"系统现在是什么样"。归档前逐项过,有则迁移、无则明写"无":

| 本次产生的 | 沉淀到 |
|---|---|
| 新业务规则 | 自动化测试(测试即规则的长期形态) |
| API / Schema 变化 | OpenAPI / contracts / 类型定义 |
| 架构决策 | ADR |
| 模块职责变化 | 架构文档 |
| 部署 / 故障经验 | Runbook |
| Agent 反复踩的项目坑 | AGENTS.md / CLAUDE.md |
| 临时调查、实施过程 | 只留 Workbench,不外溢 |

沉淀不做完,Change 不算归档——这是防止"长期事实永远埋在过程文档里"的唯一闸口。

## 项目落地边界与冲突顺序

主线/分支命名/Worktree/构建命令/共享设备/发布审批由业务项目规定:规范要求"必须证明什么",项目决定"用什么命令和资源证明"。项目规则可以细化或收紧规范;需要放宽必须登记偏差并由用户确认,不能静默覆盖。冲突处理顺序:**用户明确裁决和安全约束 → 本规范 → 业务项目规则 → 单次任务方案**。

## 状态

需求与方案的状态机是 frontmatter 契约,定义在 [SCHEMA.md](../SCHEMA.md);测试专用状态图见 [差异/测试.md](差异/测试.md)。状态只表示已发生的事实——不能因"看起来快完成了"提前流转,不能用聊天口头表达代替 Gate 决策。
