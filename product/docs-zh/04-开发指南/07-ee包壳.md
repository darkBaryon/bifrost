# ee 包壳:企业功能怎么接进上游

> 一句话:**ee 版 bifrost-http = 上游的 main 加两道装配工序**。上游代码一行不改,当库 import;我们的 Bootstrap 把上游的 Bootstrap 包在中间。骨架案:workbench/cases/ee包壳骨架。

## 它是什么、不是什么

- 是:一个独立 Go 模块 `ee/`,import 上游 `transports/bifrost-http/server`,产出自己的可执行文件(仍叫 bifrost-http,版本号 `v2.0.0-ee.<n>`)。
- 不是在上游进程外面包代理。自有实现主要放在 `ee/`；必要的上游接入点保持小且明确。例如 `ui/app/globals.css` 用一条 `@source` 扫描自有企业源码，品牌共享 hook/API 也有接入修改；合并上游时需核对这些差异，不能保证零冲突。
- 上游代码调到我们的东西,只经过上游自己定义的接口(插件接口、fasthttp 的 handler 类型)和导出字段。依赖单向:ee → 上游。

## 目录:ee/ 内每个路径 = 上游同名路径

```
ee/
  go.mod                     单模块覆盖 ee/ 全树;上游 15 个模块 + fasthttp 共 16 行 replace 到本地
  Makefile                   workspace / ui-sync / build-ui / build / test / dev / smoke
  transports/bifrost-http/   ↔ 上游 transports/bifrost-http
    main.go                  照抄上游,只有两处不同:embed 目录、Bootstrap 换成 ee 的
    server/bootstrap.go      Bootstrap = prepare → 上游 Bootstrap → attach
    handlers/                新功能按功能建子包(见编码规范),每个 RegisterRoutes(router, ...),JSON 用上游 handlers.SendJSON
    lib/                     表定义、ShellRewriter 等公共件
    ui/                      embed 用的 UI 产物(gitignore,只留 .keep)
  ui/app/enterprise/         ↔ 上游 ui/app/_fallbacks/enterprise,只放我们覆盖的文件
  ui/sync.sh                 生成上游 ui/app/enterprise 覆盖层
  scripts/smoke.sh           冒烟
```

将来按需新建 `ee/plugins/<name>`(请求路径上的插件,镜像上游 plugins/)。品牌存储按功能放在 `ee/framework/configstore/branding/`，其中 `store.go` 负责读写，`migration.go` 负责版本化迁移，`table.go` 定义表。

## 装配:两道工序包着上游

```go
func Bootstrap(ctx, s) error {
    prepare(s)                 // 上游装配前:上游 Bootstrap 过程中会读的字段(ShellRewriter 等)
    s.Bootstrap(ctx)           // 上游原样
    return attach(ctx, s)      // 上游装配后、Start 前:表 / 插件 / 路由 / Handler 包裹
}
```

- prepare 里的东西必须在上游 Bootstrap 前设好,晚了上游读不到(ShellRewriter 在 RegisterAPIRoutes → NewUIHandler 时被捕获)。
- attach 时上游对象已装配完成但还没监听,Router、Server.Handler、Config、插件链都是可改的活数据。
- 上游 Bootstrap 中间过程碰不到:中间件链在局部变量里拼好即用,不能在上游鉴权和上游 handler **之间**插东西,只能包在最外面(Server.Handler)或用 IsEnterprise 整个换掉鉴权(B2 才做)。

## 插座清单(骨架案实测结论)

| 插座 | 状态 | 用法 |
|---|---|---|
| `s.Config.ConfigStore.DB()` | 实测可用 | 一律 `ee_` 前缀,`TableName()` 固定名;ConfigStore 为 nil(config_store.enabled=false)时 ee 拒绝启动。裸 `AutoMigrate` 仅骨架探针(FIND-013 延期项),正式表走 `ConfigStore.RunMigration` + `RunSingleMigration`(见 `ee/framework/configstore/branding/migration.go`) |
| `s.SyncLoadedPlugin(ctx, name, plugin, placement, order)` | 实测可用 | 进程内注册,不经 .so;**纯内存,不落库**(config_plugins 无记录);placement/order 传 nil = `post_builtin` 组、order 0(lib/config.go:6121-6128);纯 BasePlugin 会显示 active 但不进任何链,至少实现 LLMPlugin |
| `s.Router` | 实测可用 | attach 里 `RegisterRoutes(s.Router)`;`/{filepath:*}` 兜底之后再加静态路由命中正确 |
| `s.Server.Handler` | 实测可用 | attach 里换成包一层的函数,对 404 与错误响应同样生效;审计中间件挂这里 |
| `s.ShellRewriter` | 实测可用 | prepare 里赋值;对所有 HTML 外壳(含 SPA 兜底)生效;**dev 构建走 vite 代理会绕过它**,验证要用 build 产物 |
| `s.AuthMiddleware` | 静态确认 | ee 的正式 API 路由必须 `APIMiddleware()` 包一层;骨架的 `/api/ee/ping` 是无鉴权探针,不要照抄 |
| `OAuth2IdentityResolver` / `ExternalQuotaBudgetResolver` | 静态确认 | "nil on OSS" 字段,prepare 里赋值;B2/Access Profile 时用 |
| `IsEnterprise` ctx 标记 | 静态确认 | 上游 Bootstrap 看到就跳过自己的鉴权中间件与治理插件;B2 换鉴权时在 prepare 设 |
| ServerCallbacks 参数、三处 `callbacks.(XxxProvider)` 断言 | **不可用** | 上游 Bootstrap 硬编码传 `s` 自己;需要时向上游提 PR 加导出字段 |
| `KeySelector` / `KeyPoolFilter` | 未核 | BifrostConfig 的函数字段,自适应路由时再看 |

## UI:覆盖层与企业模式

- 上游 vite 只看 `ui/app/enterprise` 目录存不存在:存在则 `@enterprise` 别名指向它,**并把 IS_ENTERPRISE 编成 true**;不存在则指向 `_fallbacks`。别名是整目录二选一,不逐文件回退,所以 `ee/ui/sync.sh` 先复制 `_fallbacks` 再把 ee/ui 的文件逐个符号链接盖上。
- 上游 `make install-ui`(被 `make dev` 依赖)会删掉 `ui/app/enterprise`,再跑 `make -C ee ui-sync` 即可。
- **企业模式差异**(2026-09-04 验证时的情况):侧栏多 Proxy / Branding 菜单;License、Branding 页可进,但渲染的仍是上游 `_fallbacks` 的占位页(无表单,不会调用 PUT/DELETE;上游 UI 里 update/reset branding 的 mutation 无调用方);Security 页多「Dual Credential Conflict Behavior」区块、标签改为「Enable Auth on Inference」;新版本横幅隐藏;onboarding 多企业步骤;每次整页加载请求 `/api/branding`(ee 已提供默认值,否则会拿到 HTML 解析失败)。
- vite dev 对符号链接文件的热更新有效(实测)。
- Tailwind v4 的扫描器遵守 .gitignore，而上游把 `ui/app/enterprise` 整目录 gitignore 了，覆盖层里只有自己用到的样式类不会生成、页面静默走样（符号链接本身不是问题，实测扫描器会跟进）。`sync.sh` 会生成 `ui/app/.ignore`（内容 `!enterprise`）：这是扫描器所用 ignore 库自己的白名单文件，git 不读它，深层目录的规则优先于仓库根的 .gitignore，于是覆盖层被重新纳入扫描，且不必改上游 `globals.css`。该生成文件通过 `.git/info/exclude` 排除在 git status 之外。
- 换前端:ee 的 Makefile 里 `UI_DIST` 指向新前端的构建产物即可,后端不动。ee 功能一律 API 优先,页面不承载逻辑。

品牌功能后续已实现上传和恢复默认表单，当前查询接口为公开的 `POST /api/branding/get`，保存和重置为 `POST /api/branding/update`、`POST /api/branding/reset`。上面的占位页描述仅记录当时情况，当前行为见 [Logo 品牌设置](08-Logo品牌设置.md)。

## 日常命令

```bash
make -C ee workspace   # 把 ./ee 加进 go.work(上游 make dev / setup-workspace 会重建 go.work 并抹掉它,之后再跑一次)
make -C ee test        # go vet + go test
make -C ee dev         # 源码起 ee 版 API 在 8080(无热重载);UI 开发服务器另起: cd ui && npm run dev
make -C ee build       # 构建 UI + 编译带 UI 的可执行文件到 ee/tmp/bifrost-http
make -C ee smoke       # 起 ee 与 OSS 各一份, 跑 9 条断言
```

## 编码规范

我们自己的代码按功能分包，包内按职责拆文件，注释按统一要求编写并随代码更新。具体见 [编码规范](../../../workbench/规范/项目/编码规范.md)。上游功能由上游维护，不按这份规范整理。

冒烟脚本只清理自己创建的进程，不按端口杀未知进程；既有问题由 FIND-015 跟踪，隔离进程的实现可参考 `ee/scripts/branding-smoke.py`。

## 踩过的坑

- smoke.sh 若 `APP_SRC` 不存在会直接退出(首版会静默用空 app-dir 起服务并全绿)。
- **make 变量赋值行尾不能带注释**:`UI_DIST ?= x   # 注释` 会把空格算进值,`cp $(UI_DIST)/.` 变成两个参数,源目录成了 `/`,把整个文件系统复制进 embed 目录直到磁盘写满(2026-09-04 事故)。build-ui 现在先检查源目录有 index.html。
- fasthttp 会把响应头名规范化成 `X-Bifrost-Ee`,断言用大小写不敏感匹配。
- `go run` 的子进程不随父 shell 退出；旧冒烟脚本曾按端口杀进程，这种做法可能误杀其他会话的进程，后续按上文的进程归属要求处理（FIND-015）。
- go 工具链会改动 `plugins/routing/go.mod`(gorm 由 indirect 变 direct),提交前 `git checkout` 还原,不要带进提交。
