# 依赖注入模式:手工组合根

> 主题:为什么本项目没有 DI 框架,依赖注入在哪里、以什么方式完成。

**本项目没有 wire/fx/dig 等 DI 框架,依赖注入 = `Bootstrap()` 这个函数本身。**这是 Go 生态的主流做法,正式名字叫组合根模式(Composition Root):所有依赖在程序入口处、按拓扑顺序、手工 `New` 出来并层层传入。启动时序见 [01-入口与启动装配.md](01-入口与启动装配.md)。

## 三个 DI 要素

### 1. 依赖倒置——接口定义在最底层的 `core/schemas`

`Account`、`Logger`、`Plugin`(五种 Hook 接口)、`Tracer`、`MCPHeadersProvider`……全部定义在 core/schemas 中。core 只认接口,永远不 import framework/plugins/transports——这就是依赖方向 `core ← framework ← plugins ← transports` 能成立的原因。

### 2. 构造函数注入——没有任何全局魔法

```go
// handlers 层:依赖全部从参数进来
inferenceHandler := handlers.NewInferenceHandler(s.Client, s.Config)
governanceHandler := handlers.NewGovernanceHandler(callbacks, s.Config.ConfigStore, govLogManager, ...)

// 核心引擎:一个配置结构体注入所有依赖
s.Client, err = bifrost.Init(ctx, schemas.BifrostConfig{
    Account:    account,              // 接口,由 lib.NewBaseAccount(s.Config) 实现
    LLMPlugins: s.Config.GetLoadedLLMPlugins(),
    MCPConfig:  mcpConfig,
    Logger:     logger,
    KVStore:    s.Config.KVStore,
    ...
})
```

### 3. 聚合结构体当"容器"——`lib.Config` 与 `schemas.BifrostConfig`

没有反射容器,就用普通 struct 兜住一组依赖往下传。`lib.Config` 是 transport 层的总容器(所有 store、插件实例、特性开关都挂它上面),`schemas.BifrostConfig` 是 core 的注入口。想找"某个依赖从哪来",顺着 struct 字段一路 Cmd+Click 就能追到构造点——这正是手工 DI 的最大优点:**装配路径是可导航的普通代码**。

## 为什么不用 DI 框架?

| DI 框架的适用场景 | Bifrost 的实际情况 |
|---|---|
| 依赖图庞大、动态、随环境变化 | 依赖图**静态且浅**(4 层),启动时一次装好,运行期不变 |
| 需要复杂生命周期管理(懒加载、作用域) | 全部单例,随进程生灭;唯一的"作用域"是请求对象,用 sync.Pool 解决 |
| 多团队解耦,模块间互不知晓 | 装配集中在一个 2800 行的 server.go,单团队完全掌控 |
| 愿意接受反射/代码生成的调试成本 | Go 文化:显式 > 魔法,栈追踪必须可读 |

一句话:**当组合根是一个能从头读到尾的函数时,DI 框架只会把"可读的顺序"变成"不可读的注解"。**Kubernetes、Prometheus、etcd 也都是这么做的。(反例也存在:Grafana 用 wire,Uber 内部用自家 fx——那是数百组件、多团队的规模。)

## 追问一:server.go 2832 行,难道是 2000 行手写 DI?

不是。实测函数边界,真正的"装配"约 **850 行**:

| 函数 | 行数 | 干什么 |
|---|---|---|
| `Bootstrap`(:2355-2713) | 359 | 按依赖序构造 store/插件/引擎/后台服务 |
| `RegisterAPIRoutes`(:2054-2354) | 301 | 27 个 Handler 构造注入 + 挂路由 |
| `LoadPlugins`(plugins.go:149-342) | 190 | 内置 8 插件 + 动态 .so 实例化 |

server.go 其余约 2000 行是 **104 个函数中的 ~85 个运行期回调**:`ReloadVirtualKey`、`OnKeyAdded/Updated/Deleted`、`ReloadProvider`、`AddMCPClient/ReconnectMCPClient/...`(实现 `ServerCallbacks` 接口,支撑控制台改配置即时生效的热更新)。这些是业务逻辑,不是装配——用任何 DI 框架都一行省不掉。

## 追问二:850 行手写装配,wire/fx 不能压缩它吗?

压缩不了,反而更长。关键在于**这个依赖图不是编译期静态的,而是运行时配置决定的**:

- `LogsStore` 可能是 nil(用户没配日志库)、`VectorStore` 可能是 nil(没配语义缓存)、governance 插件可能未启用、企业插件按名单跳过——Bootstrap 里满地的 `if s.Config.LogsStore != nil` 都是**配置驱动的存在性判断**;
- **wire** 是编译期代码生成、纯静态图,根本表达不了"组件存在与否取决于 config.json";
- **fx/dig** 用可选依赖勉强能表达,代价是把清晰的 if 换成反射解析,错误从"第 2441 行 nil 判断"变成运行时依赖图报错;
- 插件的固定顺序(telemetry→…→modelcatalogresolver 垫底)是**业务规则**,不是依赖拓扑能推导的——框架自动排序反而是错的,还得手工标注回去。

850 行换来的是:启动顺序 = 代码顺序,栈追踪干净,Cmd+Click 可导航,新人从头读到尾 20 分钟。什么时候才值得上框架:组件数百、多个二进制共享大量 provider、团队大到没人能通读组合根。

## SDK 模式:用户自己当组合根

不经 HTTP 网关、直接 `go get github.com/maximhq/bifrost/core` 使用时,**你自己就是组合根**:实现 `schemas.Account` 接口,调 `bifrost.Init` 注入——和 Bootstrap 做的事一模一样,只是换你来写。这也解释了为什么接口都定义在 core/schemas:SDK 用户不引入 transport 层也要能实现它们。
