# 控制台账号认证：竞品事实与证据

> 调研日期：2026-09-11。用途：先确认竞品怎样建立账号、登录、维持和终止会话，再讨论本项目方案。本文不确认开发范围；建议单独放在[方案讨论](方案讨论.md)。
>
> **证据边界：**商业产品依据本次访问的官方文档与发布记录，未登录商业实例实测；New API、LiteLLM 依据已克隆仓库的固定提交，本次重新阅读认证链，未启动服务或运行测试。既有架构文档、历史调研中的建议，以及本仓 EE 的命名和目录，不作为竞品事实。

## 1. 调研对象与结论

本次聚焦控制台人员账号，不把厂商 API Key、调用方 VK 或 MCP OAuth 自动等同于控制台认证。角色权限只研究与身份衔接的部分，不重复开展完整 RBAC 调研。

| 产品 / 证据范围 | 账号如何进入系统 | 登录与会话 | 目前能确认的退出 / 撤销行为 |
|---|---|---|---|
| Bifrost Enterprise / 官方说明 | IdP 登录、目录导入、SCIM 推送；历史发布记录另有密码模式 | OIDC 会话、刷新与目录同步；密码模式的完整本地多账号流程待核实 | 文档描述 IdP 停用同步；v2.1.0 有登出遗留会话修复记录 |
| LiteLLM / 官方说明 + 固定源码 | 引导管理员、邀请内部用户、SSO | 默认代码路径为限时 dashboard Key，加封装它的 JWT Cookie | 所读 UI 登出链清理浏览器状态；该链未调用服务端 Key 撤销 |
| New API / 官方说明 + 固定源码 | 初始化 Root；管理员创建、开放注册、第三方登录 | 短期访问 JWT + 可轮换 Refresh Cookie + 服务端会话记录 | 单会话撤销、退出其他会话、改密与账号状态变更失效机制 |
| Kong Manager / Gateway Enterprise 官方说明 | 部署时建立超管；邀请管理员 | Basic Auth、LDAP、OIDC 配合 Session 插件 | Session 插件有登出、续期、过期机制；完整账号停用时序未实测 |

表中事实的逐项出处见下文。“未核实”不代表产品不支持。源码快照不代表当前线上商业实例，也不声称是调研日最新默认分支。

## 1.1 补查：管理员能否重置密码后冒用账号

2026-09-11 用户指出前版遗漏了关键问题。本节专门追查重置入口、凭据交付和密码写入，不以“有邀请流程”“密码有哈希”推断管理员无法冒用。源码沿用文末固定提交；以下是阅读结论，未进行真实登录实验。

| 产品 | 实际流程 | 对管理员冒用问题的结论 |
|---|---|---|
| LiteLLM 本地密码用户 | 管理员点击 Reset password，系统生成链接并在管理员弹窗中展示、允许复制；管理 API 另允许提交用户新密码 | 管理员能接触重置凭据，并有直接指定新密码的能力。这不是“链接只发给用户本人”的设计 |
| New API 本地密码用户 | 有权限的管理员在更新账号时提交非空 password，服务端直接哈希后写入，不需要目标用户旧密码或邮箱验证码 | 对处于其管理权限范围内的账号，可以指定新密码；仅密码登录时存在冒用能力 |
| Kong Konnect（云控制台） | 官方明确：Organization Admin 和 Owner 均不能直接重置用户密码；用户从登录页走本人邮箱找回 | 产品明确限制组织管理员的直接密码重置权限；不能把此结论移植到自托管 Kong Manager |
| Kong Manager（自托管） | 官方提供向登记邮箱发送重置邮件的接口，另用 email、password、token 完成重置 | 已确认邮件重置链；尚不足以证明高权限管理员通过其他账号／邮箱／凭据接口绝对不能代办 |
| Bifrost Enterprise | 官方确认 OIDC 登录和历史密码模式，但本次没有找到本地用户重置密码的具体界面／接口契约 | 不得断言管理员能或不能指定其他本地用户的新密码；SSO 模式的身份验证交给 IdP，不能代替本地模式证据 |

**LiteLLM 的源码链：**[Reset password 按钮处理](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/ui/litellm-dashboard/src/app/%28dashboard%29/users/_components/view_users.tsx#L157) → [链接显示与复制弹窗](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/ui/litellm-dashboard/src/components/onboarding_link.tsx#L54)。另一条[管理员更新账号链](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/management_endpoints/internal_user_endpoints.py#L1412)接收 password、校验策略并哈希，经管理员权限检查后写入用户记录。用户完成注册链接时还校验绑定的 onboarding session，不能简化为任意裸请求都能改密；但这不改变管理员可直接提交新密码的事实。

**New API 的源码链：**[管理路由](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/router/api-router.go#L145) → [UpdateUser 权限检查与 password 处理](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/user.go#L647) → [EditWithTx 写入哈希](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/model/user.go#L880)。启用 2FA 时，单改密码不代表已经通过第二因素；源码还提供独立的[管理员禁用目标用户 2FA](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/twofa.go#L190)，同样受目标角色管理权限约束，并记录审计。因此其设计并未全面排除高权限管理员代管认证凭据。

**Kong 的官方依据：**[Konnect FAQ：组织管理员和 Owner 不能直接重置用户密码](https://developer.konghq.com/konnect-platform/account/#faqs)；[Kong Manager 邮件找回流程](https://developer.konghq.com/how-to/enable-basic-auth-on-kong-manager/)；[Gateway Enterprise 3.14 Admin API 的发送重置邮件与提交重置接口](https://developer.konghq.com/api/gateway/admin-ee/3.14/)。Konnect 是云平台账号，Manager 是自托管管理账号，必须分别看待。

**Bifrost 的证据边界：**[企业密码模式发布记录](https://docs.getbifrost.ai/changelogs/ent-v1.4.0-prerelease6)和[OIDC 身份接入说明](https://docs.getbifrost.ai/enterprise/user-provisioning)未提供足够的本地用户重置流程证据，保留未知。

本次得到的区别是：有产品允许管理员掌握用户密码重置能力，也有产品明确把密码恢复留给用户本人。邀请、重置后强制改密、撤销旧会话或记录审计，都不能单独证明管理员无法冒用。若要防范应用内管理员冒用，必须进一步核对恢复邮箱变更、MFA 重置和直接代登录等旁路；这不同于声称能防住控制服务器或数据库的运维者。

## 2. Bifrost 企业版

### 2.1 密码模式确实存在，但不能据此认定有完整本地账号管理

2026-04-29 的 **Enterprise v1.4.0-prerelease6** 明确加入非 SSO 部署的用户名／密码模式，使用 `BIFROST_ADMIN_USERNAME`、`BIFROST_ADMIN_PASSWORD`，配套认证类型接口、会话中间件和认证配置集群同步。该版本还说明：启用 SCIM provider 会清除密码会话及认证配置。[官方发布记录](https://docs.getbifrost.ai/changelogs/ent-v1.4.0-prerelease6)

这能证明当时存在密码认证以及模式切换处理，**不能证明**管理员可创建任意多个本地密码账号，也不能证明当前版本仍采用完全相同的切换行为。公开网关的共享管理员登录代码不能替代企业实现证据。

### 2.2 企业身份主线：登录、用户供应和停用同步

当前身份文档描述 OIDC Authorization Code + PKCE、JWKS 验证、服务端刷新令牌与 HttpOnly Cookie／会话；用户可通过登录、目录导入或 SCIM 创建。文档给出的生命周期是每 15 分钟进行 OIDC 会话刷新检查、每 24 小时目录对账，SCIM 停用／删除推送则即时处理。[身份接入说明](https://docs.getbifrost.ai/enterprise/user-provisioning)

因此，“IdP 停用后何时失效”取决于使用哪条同步链，不能概括成所有部署都在下一次请求即时失效；也不能把 15 分钟刷新间隔理解成会话的总有效期。

### 2.3 还有身份代理方式，不只是应用自身跳转 SSO

官方支持前置认证代理发送签名 JWT，Bifrost 验证签名和 audience，再识别用户。`login_only` 使用已供应账号；`full` 额外执行属性映射。文档明确指出：断言头缺失会回到 IdP 登录，因此直接访问 Bifrost 可能绕过前置代理策略，部署需要限制直连。[Generic OIDC Proxy](https://docs.getbifrost.ai/enterprise/auth-proxy/generic-proxy)

这说明代理登录仍需要应用内部的身份校验与用户衔接，不等于信任一个普通用户名请求头。

### 2.4 官方材料的冲突与版本限制

| 问题 | 证据 A | 证据 B | 本次结论 |
|---|---|---|---|
| 首个用户是否自动成为 Admin | 身份接入页 FAQ 仍写首个用户可自动获得 Admin，后续默认 Viewer | 身份同步详解明确说所有用户都必须解析出角色，首个用户也不能隐式升级，无角色时拒绝登录 | 当前官方页面存在冲突，不能选择其中一句作为确定规则 |
| 登出是否完整终止会话 | 单纯介绍登录流程不足以确认 | 2026-09-08 的 v2.1.0 发布记录列出修复登出后遗留旧会话 | 行为与版本相关，需要针对目标版本验证 |
| 浏览器凭据存储 | 通用 Gateway 认证入门页仍写 localStorage | 本仓当前 `handlers/session.go` 写入 HttpOnly Cookie | 通用文档与本仓代码不一致；两者都不能直接代指企业版内部实现 |

出处：[身份接入 FAQ](https://docs.getbifrost.ai/enterprise/user-provisioning)、[身份同步详解](https://docs.getbifrost.ai/enterprise/how-identity-sync-works)、[v2.1.0 发布记录](https://docs.getbifrost.ai/changelogs/ent-v2.1.0)、[通用认证入门](https://docs.getbifrost.ai/quickstart/gateway/setting-up-auth)、[本仓登录实现](../../../transports/bifrost-http/handlers/session.go)。本仓代码核对基线为 `01fbd91c67a64b00978c49d523176e3e5c67aa73`，这里仅用来指出不能混用证据。

**仍未验证：**企业版当前本地账号创建／改密／重置流程、密码会话有效期、设备会话管理、密码与 SSO 是否允许共存、切换后如何恢复、账号停用对已建立长连接的影响。需要企业试用实例或对应版本的具体官方说明才能补齐。

## 3. LiteLLM

### 3.1 产品流程：引导管理员，再邀请内部用户

管理员凭据可以通过 `UI_USERNAME`、`UI_PASSWORD` 配置。其他人员走 `Internal Users → New User → 分享邀请链接 → 邮箱与密码登录`；邀请链接可以人工传递，不必把邮件服务当作账号建立的唯一入口。[UI 快速开始](https://docs.litellm.ai/docs/proxy/ui)、[内部用户自助流程](https://docs.litellm.ai/docs/proxy/self_serve)

SSO 文档列出 Google、Microsoft、Okta 和通用提供方；同时提供 `/fallback/login` 密码入口。文档标为企业能力，并列出自 v1.76.0 起最多 5 个 SSO 用户免费这一条件，不能笼统写成全部免费或全部付费。[Admin UI SSO](https://docs.litellm.ai/docs/proxy/admin_ui_sso)

### 3.2 源码：登录得到的是有期限的 dashboard Key

固定提交中，`authenticate_user` 分别验证环境配置的管理员与数据库里的邮箱／密码用户；默认路径调用 Key 生成逻辑，设置 `team_id=litellm-dashboard` 和会话期限。随后将登录结果封装为带 `exp` 的 JWT。默认期限配置为 `24h`，可由环境变量修改。另有实验性登录分支，不能把默认路径概括成唯一实现。[登录与签发](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/auth/login_utils.py#L112)、[期限常量](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/constants.py#L1624)

`token` Cookie 在此快照中明确为 `httponly=False`，前端读取 Cookie 组织 Authorization 请求头，还存在 sessionStorage 备用存储。这是该产品的实现选择，不应写成所有网关统一采用 HttpOnly Cookie。[Cookie 设置](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/management_endpoints/ui_sso.py#L2825)、[前端凭据读写](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/ui/litellm-dashboard/src/utils/cookieUtils.ts#L80)

### 3.3 登出、密码存储和 SSO 共存

所读 `useLogout` 调用浏览器清理函数后跳转；清理函数移除 Cookie、sessionStorage 和 MCP 本地凭据。**这条链没有服务端 Key 撤销请求**，所以不能仅凭退出页面认定已复制的凭据随之失效。本次未测试复制凭据后的实际请求，也不把这一发现扩展到所有 SSO 登出配置。[登出入口](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/ui/litellm-dashboard/src/app/%28dashboard%29/hooks/useLogout.ts#L9)、[清理函数](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/ui/litellm-dashboard/src/utils/cookieUtils.ts#L27)

新密码使用带随机盐的 scrypt；校验兼容旧 SHA256，登录成功后可升级旧哈希。源码另有 `disable_password_login_when_sso_enabled`，在 SSO 完整配置且该开关开启时拒绝密码登录；恢复 UI 需要修改配置，管理 API 的 master key 路径仍独立存在。[密码函数](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/utils.py#L6153)、[登录升级与模式检查](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/auth/login_utils.py#L48)

**仍未验证：**所有密码重置路径是否撤销存量 dashboard Key、账号停用在不同缓存部署下的时延、商业 SAML 登出的完整链。不能因为存在用户状态字段或 Key 删除接口就认定这些行为已自动连通。

## 4. New API

### 4.1 产品范围比单纯企业控制台更大

官方提供用户名／邮箱密码登录、可配置注册、OAuth、Passkey、2FA 和忘记密码。个人资料页支持查看登录会话、撤销某台设备或退出其他会话。是否展示注册和第三方入口由 Root 配置。[注册与登录](https://docs.newapi.pro/zh/docs/guide/feature-guide/user/auth)、[个人资料与安全](https://docs.newapi.pro/zh/docs/guide/feature-guide/user/personal-setting)

源码的初始化入口在尚无 Root 时创建管理员；普通用户也可由管理员创建。这属于同时服务管理人员和平台使用者的产品，开放注册、签到、额度等不能自动成为企业控制台需求。[初始化](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/setup.go#L50)、[管理员创建账号](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/user.go#L969)

### 4.2 会话不是仅靠 JWT 到期

此快照中访问 JWT 有效期为 15 分钟，会话有效期为 30 天；服务端会话记录用户 ID、状态、版本、认证版本、刷新凭据哈希、登录方式和设备信息。JWT 不携带角色与状态作为最终判定依据，认证时继续验证会话和用户的当前状态／版本。[Token 类型与期限](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/auth_token.go#L20)、[会话建立与验证](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/auth_session.go#L51)、[会话模型](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/model/user_session.go#L40)

刷新凭据通过 HttpOnly、SameSite=Strict Cookie 传递；刷新时轮换，有并发刷新宽限和重复使用处理。安全 Cookie 模式下，刷新／登出还检查 Origin 或 Referer；本地非安全模式有不同处理，不能省略这个条件。[刷新与 Cookie](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/auth_session.go#L220)、[刷新存储逻辑](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/model/user_session.go#L459)、[来源校验](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/middleware/auth_origin.go#L13)

### 4.3 改密与撤销有明确业务行为，但有缓存边界

用户改密成功后升级认证版本，为当前会话签发新访问凭据，并撤销其他会话。登出在服务端撤销目标会话，设备管理接口限制为浏览器登录身份，PAT 不能管理浏览器会话。密码重置、删除账号等路径也包含认证版本与会话撤销处理。[用户改密](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/user.go#L850)、[保留当前会话](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/auth_session.go#L170)、[登出及设备接口](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/auth_session.go#L48)、[密码重置](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/model/user.go#L1196)

这并不等于所有部署均即时一致：代码有 Redis 版本保护机制；现有测试专门描述“独立 Redis 节点在缓存过期后收敛”，测试推进 3 秒后再断言旧会话被拒绝。本次只阅读测试，未执行；不把测试中的时间直接当作生产 SLA。[用户缓存保护](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/model/user_auth_cache.go#L15)、[独立缓存测试](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/auth_session_test.go#L358)

新密码默认使用 Argon2id，支持分阶段迁移时写 bcrypt；新密码长度策略不反向用于拒绝历史密码登录。这是可参考的升级兼容思路。[密码策略与哈希](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/common/account_password.go#L16)

## 5. Kong Manager（Gateway Enterprise，非 Konnect）

官方教程通过部署配置启用 Basic Auth 与 RBAC，并在数据库迁移阶段设置初始管理员密码。管理员邀请可以发邮件，也可手工复制注册链接；默认邀请有效期 3 天，可配置。忘记密码的邮件流程依赖 SMTP。[启用 Basic Auth](https://developer.konghq.com/how-to/enable-basic-auth-on-kong-manager/)、[管理员邀请](https://developer.konghq.com/gateway/entities/admin/)

管理界面可选 Basic Auth、LDAP、OIDC，配合 Session 插件。会话可以放在加密 Cookie 中，也可以存于 Kong 数据库；插件具有续期、过期和登出机制，Kong Manager 的会话 secret 要在节点间一致。[Manager 配置](https://developer.konghq.com/gateway/kong-manager/configuration/)、[Session 插件及 Manager 配置](https://developer.konghq.com/plugins/session/)

可确认的是登录方式与会话机制可分别配置；不能从 Session 插件文档推断所有密码修改和管理员停用都会自动销毁已有会话。本次没有企业运行环境，也没有核对企业内部账号表和停用事务实现。

## 6. 可以得出的共性与不能得出的结论

从以上证据可以归纳：账号来源有本地创建、邀请和 IdP 供应；密码验证、登录会话、账号生命周期是相关但不同的问题；“退出页面”和“旧凭据失效”必须分别核实。

不能得出“成熟网关都用 JWT”“都用服务端 Session”“改密都退出所有设备”“启用 SSO 后一定保留本地登录”这样的统一答案。上面已经存在不同实现和版本条件。

与本项目相关的选择应依据实际使用场景和已确认业务规则，再比较实现成本；不从竞品目录名推导本仓必须建哪些包，不把已有架构反过来当成竞品实践的证据。
