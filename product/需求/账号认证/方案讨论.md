## 0. 已确认的账号与密码规则

2026-09-11，用户在核对[竞品重置流程](竞品调研.md#11-补查管理员能否重置密码后冒用账号)后确认：

- 本轮采用本地账号，不以接入企业原有组织结构为前提。管理员创建账号，用户后续自己管理密码。
- 创建账号时使用默认初始密码，用户举例为 `123456`，随后由用户本人修改；具体默认值尚未定。首次登录强制改密是已有建议，尚未单独确认。
- 允许有账号管理权限的管理员修改／重置目标用户密码；遵守既有角色权限约束。
- 管理员修改密码必须记录到可查看的项目操作日志，让发生过的修改可以被看到。这里指管理操作记录，不由此增加资源治理中的 Project 模型。

日志至少能够回答：**哪个管理员、什么时间、修改了哪个账号的密码、操作是否成功**。只记录“密码已修改”等事件摘要，不保存新旧密码、密码哈希或重置凭据。具体查询入口、查看权限及与管理审计功能的交付衔接在工程方案中明确；不能用只有开发者能看到的临时控制台输出代替可查看的记录。

本次决定采用“允许管理员改密、操作可追查”的方式，不再把阻止管理员掌握重置密码作为本轮前提。此前因冒用问题暂停该建议的状态已被本次决定取代；日志是追查依据，不表述为阻止冒用的机制。

## 1. 建议的产品方向

首版方向已确定为**企业内部使用的本地多账号认证**：管理员建立账号，人员用各自密码登录；系统可以终止某个人的会话，后续授权和审计能识别稳定的账号身份。具体规则按已确认事项与下表待讨论项区分。

理由是现有用户裁决已经选择管理员创建账号、个人改密和旧管理员衔接；LiteLLM 和 New API 提供了可复核的本地账号实例，证明这条路径不必依赖企业 IdP 才能成立。Bifrost Enterprise 的 SSO／SCIM 更适合作为以后接入企业目录时的参考，公开材料尚不足以把它当成本地多账号产品的完整蓝本。

## 2. 产品行为建议

| 事项 | 既有依据 / 状态 | 本次建议 |
|---|---|---|
| 账号建立 | 已确认：管理员创建、默认初始密码，后续本人修改 | 具体默认值尚未定；登录名不可修改、邮箱不必填仍为建议 |
| 开放注册、邀请 | 既有需求不包含邀请流程 | 首版不增加；LiteLLM、Kong 的邀请可作为以后减少管理员接触初始密码的增强 |
| 初始管理员 | 既有需求：迁移共享管理员；新实例先初始化 | 保留原用户名密码，旧会话失效；新实例通过部署者持有的一次性初始化凭证建立首个管理员，不能靠“谁先访问谁成为管理员” |
| 本人改密 | 既有需求只确认提供能力，未确认会话策略 | 校验当前密码；成功后保留并轮换当前会话、撤销其他会话，参考 New API 的用户体验 |
| 管理员重置密码 | 已确认：允许管理员修改／重置，并记录可查看的项目操作日志 | 按第 0 节执行；重置后旧会话撤销、是否要求目标用户再次改密仍需明确 |
| 首次登录 | 新建议 | 管理员设置的初始密码要求首次登录修改；旧共享管理员迁移不强制改密，避免改变既有迁移裁决 |
| 停用 / 删除 | 既有需求：停用后下一次操作失效 | 停用或删除成功后，后续管理请求拒绝旧会话；启用账号不恢复以前被撤销的会话 |
| 登出 | 新建议 | 服务端撤销当前会话并清 Cookie；重复登出可成功，不只清理浏览器状态 |
| 会话期限 | 尚无确认值；竞品有 24 小时和 30 天等不同选择 | 先建议绝对有效期 24 小时、可配置；首版不做“记住我”和滑动续期，不把这个数值说成行业标准 |
| 设备会话 | New API 有明确产品流程 | 首版后端能列出本人会话、撤销单个／其他会话；页面随前端阶段接入，不允许查看他人的会话凭据 |
| 忘记密码 | 首版没有邮件前提 | 普通账号由管理员重置；所有管理员均无法登录时，提供需要服务器访问权的显式恢复流程，重置后撤销旧会话 |
| SSO、SCIM、MFA、Passkey | 竞品有不同覆盖；本轮尚无采用决定 | 首版后置；今后先选实际 IdP，再明确账号关联、停用同步、本地恢复方式，不预设共存或互斥 |

除明确标为已确认及既有需求的部分外，上表其余内容仍为建议。账号创建、删除和停用仍须遵守既有主管理员保护及授权规则；认证首版不能通过“所有登录账号都是管理员”来代替权限接入。

## 3. 会话机制的技术取舍

| 方案 | 实际参考 | 适合之处 | 本项目需要承担的代价 |
|---|---|---|---|
| 不透明随机凭据 + 服务端会话 | Kong 的服务端存储选项；本仓现有 Cookie 登录形态 | 撤销、到期和账号状态集中判断；浏览器不需要读取凭据 | 每次管理请求查询权威状态，需要处理 Cookie 来源校验 |
| 短期 JWT + Refresh + 服务端会话 | New API | 访问凭据短期化，多终端会话与刷新机制完整 | 刷新轮换、并发刷新、重放处理更多；要及时停用仍需查服务端状态 |
| 复用 dashboard Key 并以 JWT 包装 | LiteLLM 默认源码路径 | 复用已有 Key 设施 | 会话与 Key 规则耦合；须额外核对登出撤销、用途隔离和浏览器存储 |

**建议首版采用第一种。** 当前目标是浏览器控制台和管理接口，尚无需要跨服务离线验证身份的场景；JWT 不会自动满足“停用后下一次请求失效”。这个选择来自需求与复杂度比较，不由 `identity/` 目录名决定。

建议浏览器持有 HttpOnly Cookie，服务端仅持久化随机凭据的哈希及会话元数据。管理请求读取权威数据库中的账号和会话状态；首版不引入允许旧状态继续生效的本地缓存。多个实例共享同一权威数据库时按同一规则校验，不读取有延迟的只读副本。

账号状态／密码更新与认证版本变更需原子提交，以保证旧会话即使尚未批量清理也不能再次通过验证；当前会话轮换应与改密成功语义一致。具体事务接口、表和中间件位置留到工程设计，不直接复制 New API 的缓存系统。

## 4. 必须讲清的认证边界

- **请求入口：**登录、初始化、本人资料、改密、会话管理和受保护的管理操作均要有明确身份规则；公开品牌资源和健康检查分别列出。已有白名单、旧 Basic／Bearer、导入配置及 WebSocket ticket 必须逐一核对，不能让旧凭据路径绕过新账号状态。
- **推理调用：**控制台登录不自动获得任意模型调用能力。现有 VK、推理 Basic／Bearer 等兼容行为先盘点，再单独约定迁移；不因接入控制台认证擅自改变调用方凭据。
- **浏览器：**Cookie 方案配套明确的 CSRF／来源检查、HTTPS 与可信代理配置；不能把 POST 或 HttpOnly 当成全部保护。脚本调用如需要管理凭据，单独定义用途，避免把控制台密码永久当 API Key。
- **失败和并发：**登录失败限速、错误信息一致、密码与会话不出现在日志／响应中；登录签发与停用／重置同时发生时，以最终账号状态和版本为准。哈希算法候选优先比较现有 bcrypt 兼容与 Argon2id，结合部署资源测量后选择。
- **失效含义：**“下一次操作”先明确为变更提交后开始认证的请求；不承诺撤回已经执行的写入。已建立 WebSocket 在后续操作或续期时如何校验、是否主动断开，需要在实施方案单独给出规则和验证。

以上是建议方案的必要边界，不是声称所有竞品均如此实现。

## 5. 确认与后续顺序

管理员能否修改密码已经确认，不再重复讨论。后续明确首次登录是否强制改密、本人改密／管理员重置后保留哪些会话、默认会话期限，以及操作日志的查询与交付衔接。

确认产品行为后，再落地认证接入方案、接口契约、升级恢复与测试。届时重新评估本仓架构；需要修改现有架构决定时同步修改，不以“文档已经这么写”替代设计论证。

Bifrost Enterprise 的未验证项不阻止我们独立选择方案，但若要求与它保持完全一致，则需先取得目标企业版本的验证证据。本轮完成调研与方案讨论稿，尚未开始认证实现。
