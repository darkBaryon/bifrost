# 竞品源码：角色权限实际上怎样实现

> 2026-09-08 · 已 clone 后阅读实际代码。范围仅限角色、账号授权、接口判权和前端权限展示。本文是源码分析，未启动竞品服务，也未执行其测试套件。

> 2026-09-09 补充：本文仅是公开仓库的源码快照，不代表完整商业产品。产品能力以[开源与商业产品调研](竞品产品调研.md)为当前入口；本文中的采用建议未获确认。

## 先说结论

**最值得参考代码结构的是 New API；LiteLLM 适合参考固定角色的实现；Portkey 只能在这个仓库中看到部分权限执行链。三者都不能直接等同于我们要的“创建岗位角色、勾选权限、给账号分配角色”。**

之前主要根据产品文档提出方案，没有把公开仓库里的实现对应清楚。下面给出实际读到的代码，以及哪些可以借鉴、哪些不符合我们的目标。

| 仓库 | 实际实现 | 与我们目标的关系 |
|---|---|---|
| New API | 独立权限模块、权限目录、统一判权、前端权限矩阵；实际账号角色仍映射为固定角色，另有逐账号权限覆盖。 | 模块拆分很值得参考；账号覆盖这部分不采用，角色分配需要独立设计。 |
| LiteLLM | 用户记录一个全局角色，角色来自枚举；后端根据角色和路由判权，前端也有角色分类。 | 能参考如何分配预设角色，不能据此声称支持任意岗位角色编辑。 |
| Portkey Gateway | 默认分支主要是网关；2.0 分支增加 API Key 的 scopes 检查，权限数据由外部服务提供。 | 可参考统一的接口权限检查；没有在该仓库找到完整岗位角色管理实现。 |

## 一、New API：把一条权限从定义跟到页面

以“管理员能不能修改渠道”为例，它的代码链是：

```text
定义 channel 的 read / write 等操作
  → 系统角色映射为 root 或 admin
  → 读取角色默认权限及该账号的覆盖项
  → 接口调用 Can 判断
  → 后端返回最终权限矩阵
  → 页面据此显示编辑按钮
```

### 权限在哪里定义

它使用“资源 + 操作”表示权限，例如 `channel.write`。资源文件同时登记操作名称、说明和哪些内置角色默认拥有它。权限目录由后端提供，前端不用再维护另一套勾选项。

渠道没有机械地只有增删改查，还区分日常操作、普通配置修改、敏感配置修改和查看完整密钥。这些分类可以借鉴，但需要按 Bifrost 的实际功能重新列项。

证据：[权限类型](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/permission.go#L5)、[权限登记与目录](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/registry.go#L5)、[渠道权限定义](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/resources_channel.go#L23)、[权限目录接口](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/authz.go#L13)。

### 角色怎样分给账号——这里与我们的需求不同

数据库有 `AuthzRole` 表，看起来像完整角色系统。但继续读 `assignment.go`，实际通过用户的系统角色数值映射成 `root` 或 `admin`，没有在这条链里查询“账号关联了哪些自定义角色”。`role.go` 返回的也是代码定义的两个内置角色。

因此不能因为存在角色表，就把它当作现成的“新建运维角色，再分给张三李四”。当前 `/authz` 路由提供权限目录；用户编辑页提供的是对这个账号覆盖管理员默认权限。

证据：[角色表](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/model/authz_role.go#L3)、[实际角色分配逻辑](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/assignment.go#L7)、[内置角色](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/role.go#L19)、[授权模块路由](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/router/authz-router.go#L13)、[账号权限编辑器](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/web/src/features/users/components/users-mutate-drawer.tsx#L434)。

### 最终怎么决定允许还是拒绝

`Can` 先解析角色：超级管理员直接允许；其他账号先检查权限是否已登记，再检查账号的显式覆盖项，最后检查角色默认授权。账号覆盖优先于角色，既可以允许，也可以拒绝。

它使用 Casbin 存储和读取策略，但上述优先顺序是在自己的 `resolver.go` 中实现的，不是仅仅引入 Casbin 就自动获得完整角色产品。

**我们可以参考统一的判权入口，但不需要复制逐账号覆盖机制。我们的授权来源就是分配给账号的角色，多个角色的允许权限合并。**

证据：[最终权限计算](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/resolver.go#L10)、[策略初始化与同步](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/enforcer.go#L34)、[账号权限覆盖](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/override.go#L42)。

### 接口怎么接，是否只隐藏按钮

渠道路由先执行管理员身份检查，再执行 `RequirePermission`。例如修改渠道要求 `ChannelWrite`，不满足返回 403。进入业务处理后，如果修改内容包含密钥、上游地址等敏感字段，还会检查 `ChannelSensitiveWrite`。

这说明一个“编辑渠道”接口里可以包含不同权限等级的操作，不能只保护页面入口。另一个细节是：虽然权限目录有 `secret_view`，实际读取渠道完整 Key 的路由还要求 Root 和安全验证。**勾选一个权限点不代表就通过该接口的所有条件。**

证据：[接口权限中间件](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/middleware/auth.go#L235)、[渠道路由权限映射](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/router/channel-router.go#L18)、[敏感字段检查](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/channel_authz.go#L5)、[修改时的额外判权](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/channel.go#L1024)。

### 页面怎么知道当前账号能做什么

后端的 `Capabilities` 生成最终权限矩阵，用户信息接口返回给前端。前端 `hasPermission` 读取这张矩阵，渠道编辑和操作按钮使用它。权限编辑器则从 `/api/authz/catalog` 获取资源、操作和说明，生成勾选项。

这个结构与我们的目标很接近：权限清单由后端统一定义，前端使用最终结果。我们需要把勾选项放到“角色编辑”页面，账号页面负责选择角色。

证据：[最终权限计算](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/resolver.go#L10)、[用户有效权限返回](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/controller/user.go#L491)、[前端权限判断](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/web/src/lib/admin-permissions.ts#L84)、[渠道操作按钮](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/web/src/features/channels/components/channels-primary-buttons.tsx#L87)、[账号权限编辑器](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/web/src/features/users/components/users-mutate-drawer.tsx#L434)。

### 修改权限后，怎样生效

用户权限修改写入数据库事务，提交后重新加载本节点策略；其他节点通过定期加载同步。它不是修改数据库后所有节点立即同步完成。

相关测试明确检查：事务提交后、调用 `ReloadPolicy` 之前仍是旧结果；加载后才变成新结果；事务回滚不能产生新授权。这些是读到的现有测试断言，本次没有运行。

我们实施时要明确策略缓存如何失效，不能只在登录时把权限永久放进会话。多实例同步的生效时限也要单独验收。

证据：[策略初始化与同步](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/enforcer.go#L34)、[权限覆盖、刷新和回滚测试](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/authz_test.go#L80)。

还有一个不能照搬的细节：初始化会重新写入内置角色的默认策略。若我们允许编辑角色，就不能让用户保存的角色权限在重启时被默认值覆盖。证据：[默认策略重建](https://github.com/QuantumNous/new-api/blob/ea7cb0ba4e0f82e2bfa5e55752eb68bdf902f71b/service/authz/seed.go#L40)。

## 二、LiteLLM：实际是预定义角色驱动

它的全局角色在 `LitellmUserRoles` 中定义，例如 `proxy_admin`、`proxy_admin_viewer` 和 `internal_user`。用户表有一个 `user_role` 字段；编辑用户页面是选择已有角色，不是编辑该角色包含哪些权限。

证据：[角色枚举](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/_types.py#L127)、[用户表](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/schema.prisma#L236)、[用户角色选择器](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/ui/litellm-dashboard/src/app/(dashboard)/users/_components/user_edit_view.tsx#L218)。

沿普通用户管理请求的鉴权路径看，后端取得用户对象，解析角色，再进入 `RouteChecks.non_proxy_admin_allowed_routes_check`。管理员只读、普通内部用户等走不同的路由规则，有些接口还会自行检查目标用户或资源。

证据：[鉴权时读取用户](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/auth/user_api_key_auth.py#L1953)、[用户角色与路由检查](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/auth/auth_checks.py#L1150)、[角色路由规则](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/auth/route_checks.py#L243)。

修改用户角色也由后端约束：`_check_user_update_authz` 不允许非 `proxy_admin` 提交角色变更，批量用户修改另有同类检查。前端 `roles.ts` 则维护角色分组，控制哪些页面和操作可以出现。

这证明角色分配和后端限制确实有实现，但若我们要动态创建“运维”“财务”等岗位，就不宜照搬到处按固定角色名称分支的方式。

证据：[修改角色授权检查](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/management_endpoints/internal_user_endpoints.py#L1326)、[前端角色分组](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/ui/litellm-dashboard/src/utils/roles.ts#L9)。

只读角色的路由检查还包含 HTTP 方法、路由分组、明确允许或禁止的路径，以及个人资料修改例外。对应测试覆盖禁止管理写操作和允许读取等情形。这里值得借鉴的是接口级保护和回归场景，而不是把它的路由规则原样搬过来。

证据：[角色路由规则](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/litellm/proxy/auth/route_checks.py#L243)、[路由权限测试](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/tests/test_litellm/proxy/auth/test_route_checks.py#L146)。

仓库根许可将 `enterprise/` 与其他代码区分；企业目录可读，不等于 MIT 开源许可。本文上述主链证据均指向企业目录之外的文件，不把整个企业权限产品视作可直接复用的开源模块。证据：[LiteLLM 许可边界](https://github.com/BerriAI/litellm/blob/1af7a403c66e037bec2e0ae6ea455a1c10b17b1b/LICENSE#L1)。

## 三、Portkey：检查到了执行端，没找到完整角色管理端

默认分支 README 仍把 2.0 标为预发布，所以本次额外获取并检出了 `2.0.0` 分支，没有停在默认分支的搜索结果。

在 2.0 中，`authNMiddleWare` 获取 API Key 信息，将其 scopes 放进请求上下文；接口声明允许的 scopes，`authZMiddleWare` 检查是否至少匹配一个，不匹配则拒绝。

证据：[身份与 scopes 获取](https://github.com/Portkey-AI/gateway/blob/8febc1dc1d85053dd374922e547b4db1af0fab79/src/middlewares/auth/authN.ts#L32)、[scopes 判权](https://github.com/Portkey-AI/gateway/blob/8febc1dc1d85053dd374922e547b4db1af0fab79/src/middlewares/auth/authZ.ts#L5)、[接口声明权限](https://github.com/Portkey-AI/gateway/blob/8febc1dc1d85053dd374922e547b4db1af0fab79/src/index.ts#L185)。

继续追查 scopes 来源，`fetchApiKeyDetails` 先查缓存，再请求 `ALBUS_BASEPATH` 指向的服务，读取 `/v2/api-keys/self/details`。这里拿到的是已经配置好的权限结果，未在该仓库找到对应的账号角色表、角色编辑接口和角色分配页面。

因此这个仓库能帮助我们理解“接口如何使用权限”，不能据此证明已经拿到了 Portkey 控制台的完整 RBAC 实现，更不能把 API Key scopes 直接等同于员工岗位角色。

证据：[权限数据来源](https://github.com/Portkey-AI/gateway/blob/8febc1dc1d85053dd374922e547b4db1af0fab79/src/services/albus/index.ts#L49)。上述“未找到”限定于本次下载的仓库和分支，不断言其他 Portkey 仓库一定没有。

## 四、回到我们的需求，借鉴哪几块

建议以 New API 的模块拆分为主要参考，但保持我们自己的角色模型：

```text
权限清单：系统支持哪些操作
角色：一个岗位的名称与说明
角色权限：这个岗位允许哪些操作
账号角色：哪些账号担任这个岗位

请求到来 → 识别账号 → 取关联角色的权限 → 检查目标操作
```

具体采用三点：后端统一权限清单；后端统一判权；前端根据有效权限展示功能。补上竞品这几份代码没有直接提供的角色编辑和账号角色关联即可，不因此扩展成人员管理系统。

不采用逐账号 allow/deny 覆盖，不依靠角色名字在各业务接口硬编码，不把 Key 的调用权限与后台岗位权限混在一起。是否使用 Casbin 可以在实施设计时比较，当前源码研究不足以证明必须引入它。

New API 当前细粒度目录覆盖的是渠道、任务插件和审计，并非全站所有功能都已接入。Bifrost 仍需按自己的管理接口整理权限清单，不能只拷贝三类资源就宣布权限完成。
