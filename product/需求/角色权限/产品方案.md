我们需要的是：创建角色，为角色配置权限，再把角色分配给员工账号。权限跟着角色走，不给每个人单独配置一套规则。

例如创建“运维”角色，允许管理模型和路由；给张三、李四分配“运维”，两人就获得相同权限。以后修改这个角色，两人的权限一起变化。

## 竞品中值得借鉴的部分

| 产品 | 官方文档明确的做法 | 我们借鉴什么 |
|---|---|---|
| LiteLLM | 区分平台管理员、平台只读等角色；团队范围的管理角色另有划分，其中团队管理角色属于企业能力。 | 按工作职责组织权限，提供开箱即用的角色。 |
| Portkey | 组织和工作区分别设置角色；组织管理员可以调整工作区角色对日志、分析、API Key 等资源的访问权限。 | 把角色的权限展示清楚，区分查看与修改等操作。 |

来源：[LiteLLM 角色说明](https://docs.litellm.ai/docs/proxy/access_control)、[Portkey 角色与权限](https://portkey.ai/docs/product/enterprise-offering/org-management/user-roles-and-permissions)。这些资料支持上述产品思路，不代表两家的所有角色均可任意编辑，也不代表其企业功能都开源。本次未登录商业版实测。

下面是我们的方案，不要求照搬竞品完整的组织管理体系。

## 用户只需要操作两个地方

### 1. 角色管理

创建一个角色，填写名称和说明，再勾选它允许执行的操作。例如：

| 功能 | 可配置的权限示例 |
|---|---|
| 模型与厂商 | 查看、新增、修改、删除 |
| 路由 | 查看、新增、修改、删除 |
| Virtual Key | 查看、新增、修改、删除、查看完整密钥 |
| 团队与预算 | 查看、修改等实际支持的操作 |
| 日志与费用 | 查看费用、查看基本日志、查看请求正文、导出 |
| 账号与角色 | 查看账号、分配角色、管理角色 |
| 系统设置 | 查看、修改；认证设置与执行代码的能力单独控制 |

这是权限分类示例。实施前应按现有功能整理准确清单，不机械地给每个模块都加一套增删改查。“查看 Key 信息”与“查看密钥完整值”也不能混成同一个权限。

建议提供“管理员”等预设角色作为起点，同时允许创建符合实际岗位的角色。预设角色是方便开始使用，不应成为只能选几种固定身份的限制。

### 2. 账号分配角色

在账号列表中选一个账号，为它分配角色。账号详情显示已分配的角色，以及由这些角色获得的权限，不提供逐人修改权限的入口。

允许一个账号分配多个角色，权限取并集（2026-09-09 用户确认）。例如“运维”能修改路由，“费用查看”能看报表，两者同时分配就同时拥有这些能力。没有任何角色授予的操作，默认不允许。

角色改动对所有关联账号生效；移除某个角色后，账号失去该角色带来的权限。如果其他角色仍授予同一权限，该操作仍然可用。页面应说明权限来自哪个角色，避免管理员不明白为什么还有权限。

## 机制需要守住的几条规则

- **后端决定能否操作。** 页面按权限显示按钮，接口也执行相同检查，不能只隐藏菜单。
- **授权变化及时生效。** 修改角色或账号分配后，后续请求使用新权限，不等用户重新登录。
- **角色管理本身也有权限。** 能编辑角色或分配角色的人掌握授权能力，默认仅交给主管理员，避免普通账号通过编辑自己的角色获得更多权限。
- **保留一个受保护的主管理员角色。** 用于初始配置和授权管理；不能移除最后一个有效主管理员，也不能把这个内置角色改成没有管理权限。
- **角色删除要看影响。** 显示有多少账号正在使用；仍有关联时先要求重新分配，不静默让一批账号失去权限。
- **查看与修改分开。** 请求正文、完整凭证和导出等敏感操作单独列出，不由笼统的“只读”自动包含。
- **批量操作也遵守权限。** 配置导入不能绕过认证设置的授权检查；可执行服务端代码的插件等能力需要单独保护。

当前这些角色作用于整个网关。团队和预算是可管理的业务资源，本轮不增加团队成员关系、团队数据隔离或团队自助流程。以后确有“只能管理某个团队”的需求，再给角色分配增加作用范围；现在不展开建设。

## Bifrost 需要补什么

当前登录仍围绕一组管理员凭据，会话没有关联独立用户；前端已有 RBAC 资源和操作名称，但开源占位实现直接允许。因此要把角色分配给具体账号，必须补足账号识别和会话关联这个基础。

这部分只需支持管理员建立可登录账号并分配角色，以及必要的密码维护、账号停用；不引入入职、调岗、离职审批等人员管理流程。邀请、组织同步、应用身份交接等不纳入这次角色机制设计。

实际交付按以下内容组织：

| 内容 | 用户获得什么 |
|---|---|
| 权限清单 | 知道每个勾选项允许做什么 |
| 角色管理 | 创建、查看、修改和删除角色，为角色选择权限 |
| 账号与角色分配 | 每个账号独立登录，获得所分配角色的权限 |
| 后端授权与页面适配 | 无权限的操作被拒绝，界面显示与实际权限一致 |

角色和账号授权关系应独立保存，不在各个业务接口里硬编码“角色名等于运维就允许”。这样以后增加“费用查看员”，只需要创建角色并选择已有权限；新增业务功能时，增加相应权限点并分配给角色。

## 用四个例子验收

1. 创建“运维”角色，只允许查看和修改路由。张三、李四分配该角色后，都能改路由，都不能修改预算。
2. 从“运维”中取消修改路由。张三、李四的后续修改请求都被拒绝，已有页面也不能继续修改。
3. 给张三再分配“费用查看”角色。张三可以看费用，李四不可以；张三仍不能修改预算。
4. 李四直接请求角色修改接口，试图给自己增加权限。后端拒绝，不能靠绕过页面获得授权。
