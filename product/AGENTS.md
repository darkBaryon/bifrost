# 产品与技术文档约定

本目录负责产品经理和技术负责人级别的文档：产品资料、竞品调研、需求方案、路线图、整体架构、模块边界、技术选型和长期技术决策。具体开发人员的实施方案、代码改动设计、测试、评审和交付记录遵循 `../workbench/` 约定。整体架构不能放进 Workbench 的开发蓝图或编码规范目录。

- 先读 `README.md` 和对应需求资料，避免另起一份重复文档。
- 新产品需求按“竞品调研 → 总结 → 产品方案”推进。调研阶段只陈述竞品事实与证据，不能提前把自己的建议写成确认规则。
- 开源实现核对记录仓库、commit 和代码出处；区分运行验证、源码阅读、官方说明和推断。
- 产品方案引用调研依据，区分沿用、适配和未确认事项；用户未确认的建议不得作为已批准需求交给开发。
- `竞品调研/` 放公共背景；`需求/<中文名称>/` 放具体需求；`架构/` 放整体架构与长期技术决策；`docs-zh/` 放参考资料，不再向其中添加需求和产品路线图。
- 小需求可合写，复杂需求再拆。产品方案描述业务行为；架构文档可以规定目录结构、模块职责、依赖方向和技术约束；某次功能的逐文件实现步骤与测试方案放 Workbench。
- Workbench 引用产品方案和架构，不复制另一套规则；实施发现业务或架构决策缺口时反馈到本目录。
- 每份文档说明用途、确认情况及必要的适用版本。当前有效内容与历史证据分开，旧方案被替代时明确链接接替文档。
- 移动文档时修复相对链接；功能 worktree 中同源文档先比较再整合，不覆盖并行修改。
