# EE 与上游接入重设计

用途：规定本次 EE 后端重构中，EE 与 Bifrost（下称 BF）的长期接入边界。模块组织见 [EE 后端架构](EE后端架构.md)，具体接口草图、逐文件改动和验证安排见 [一期方案](../../workbench/cases/EE与上游接入重构/期1/方案v1.md)。

- 更新日期：2026-09-29；代码基线：自有 `develop@9e78d3bdb`。
- 确认状态：下文的职责、接入方向和删除条件来自本轮讨论。用户随后授权小批实施；第一批新增三个 BF 启动接入口，第二批迁移 EE 并删除旧认证工厂，详见[一期方案 §13](../../workbench/cases/EE与上游接入重构/期1/方案v1.md#13-第二小批迁移-ee-并删除旧工厂)。当前为工作区改动；第三批已独立实现 auth/session 并接入实际调用；认证 HTTP 入口随后补齐到 auth/http，并由 app 独立注册；其它模块重写、公共认证/RBAC 中间件拆分和类型化业务检查仍未完成。
- 范围：现有身份、权限、品牌、内容安全和国内定价的接入；usage 不在本次范围。基线使用当前代码，不回退到早期身份模块引入前的提交。
- 本稿替代本文件此前的阶段化启动拆分和统一路由注册器方案。旧调研仍是历史证据，不能以其中的建议覆盖本稿。

## 1. 接入结论

保留一个完整的 `BifrostHTTPServer`，继续调用 BF 的完整 `Bootstrap` 和 `Start`。EE `app` 创建并连接业务对象；需要 BF 资源且必须赶在 BF handler 构造之前完成的部分，通过明确的启动回调装配。其他部分按依赖放在 `Bootstrap` 前或完成后的 attach 阶段。

HTTP 接入复用现有 `RegisterAPIRoutes`、各 handler 的 `RegisterRoutes` 和通用 middleware 参数。公共认证与 RBAC middleware 只处理身份和接口级权限。BF Router 匹配请求后，权限层使用它已经命中的路由模板，不维护第二个 matcher。

涉及具体数据的权限检查放在 BF handler 已完成解析、默认值处理、保留字段恢复和合并之后，在保存、配置热更新、外连等副作用之前调用。稳定的类型化规则通过构造参数注入；响应字段可见性在序列化前处理。普通 EE 业务仍由自己的 service 和事务负责，不能全部搬进 middleware。

允许为上述边界维护少量明确的 BF 扩展补丁。补丁应提供通用能力，BF 不依赖 EE 包，也不认识 EE 的具体权限码。

## 2. 当前源码已有的能力

以下是当前分支的源码事实，不表示它们全部来自纯上游：

| 现有能力 | 当前用途与局限 |
|---|---|
| `BifrostHTTPServer.Bootstrap` | 初始化配置、共享资源、core、Router、handler 和 HTTP Server；EE 已复用完整流程 |
| `RegisterAPIRoutes(ctx, callbacks, middlewares...)`、handler 的 `RegisterRoutes(router, middlewares...)` | 已能给 BF 管理接口接入 middleware；不需要统一更换所有路由注册参数 |
| `SaveMatchedRoutePath` 与 `PrepareCommonMiddlewares` | Router 保存命中模板；common middleware 将它转存到 `BifrostContextKeyHTTPRoute`，可供后续权限层直接读取 |
| `BeforeAPIRoutes`、`ConsoleMiddlewares`、`RegisterConsoleSessionRoutes` | 分别负责启动装配、控制台中间件替换和 session 路由替换；EE 已迁入，基线中的 `ConsoleAuthFactory` / `ConsoleAuthProvider` 已删除 |
| EE `app/identity.go` 的模块注册 | 身份、RBAC、基础状态接口独立注册并使用 common 链；四条旧会话兼容接口独立替换；已删除 `AdditionalRoutes` 与自有接口路径豁免 |
| 自有补丁 `handlers/consolepolicy.go` | 已有 provider、MCP、配置、通知等操作接点，但通过请求上下文传策略函数，构造依赖不明确 |
| `ServerCallbacks`、现有 resolver、原生插件接口 | 可复用其真实覆盖的能力；并非所有控制台 CRUD 都有合适的现成回调 |

主要依据：[BF server](../../transports/bifrost-http/server/server.go)、[当前 EE 启动](../../ee/internal/app/bootstrap.go)、[现有策略接点](../../transports/bifrost-http/handlers/consolepolicy.go)。历史核对记录见 [调研证据](../../workbench/evidence/EE与上游接入重构-接入调研.md)。

不能通过设置 `IsEnterprise` 来概括完成接入。当前 BF 对这个标记的判断还涉及推理认证和插件等行为，不是仅关闭 OSS 控制台认证的开关；本设计只显式替换需要替换的控制台链。

## 3. 对象与资源归属

| 所有者 | 负责内容 | 依赖边界 |
|---|---|---|
| BF Server | 配置与热更新、共享数据库连接、core、模型目录、Router、HTTP Server、BF 后台任务与协议运行时 | 继续维护完整初始化和运行流程 |
| EE 各业务模块 | 账号、会话、角色权限、品牌、内容安全和国内定价的业务规则与存储访问 | 接收实际需要的依赖，不接收整个 BF Server |
| EE 接入适配 | BF 数据与 EE 规则之间的转换、控制台接口权限映射、旧配置兼容、WS 身份与受众适配 | 可以了解 BF 的窄接口和数据类型，不反向成为业务服务的依赖 |
| EE `app` | 创建模块、传递依赖、安装接入能力、调用模块注册、最后做完整性检查 | 可以持有模块对象和 BF Server，不实现业务规则 |

EE 不另建一个复制 BF 运行时的新 Server。模块通过构造注入获得依赖，handler 持有自己的 service；不靠运行时从全局 Server 查找全部业务对象。

共享数据库、core、模型目录等资源只借用，由 BF 负责其生命周期。需要热更新视图的适配读取 BF 当前资源，不能永久保存一份启动时配置副本。EE 若将来创建独立资源，再由 EE 明确负责释放，不因此预先建立新的生命周期框架。

## 4. 启动顺序：保留 Bootstrap，明确必要回调

目标顺序如下。这里描述调用时点，不规定新的函数名称：

```text
EE main / app
  → 构造 BF Server；准备不依赖 BF 已加载资源的 EE 配置与对象
  → 安装启动回调及启动前必须设置的扩展，例如 HTML shell 重写
  → 调用完整 BF Bootstrap
      → BF 加载配置、创建共享资源、core 和 Router
      → 在资源已满足且 BF API handler 尚未构造的时点，回调 EE app
          创建需要这些资源的 EE store / service
          完成其必要迁移与兼容导入
          提供控制台 middleware、session 替换及类型化 handler 依赖
      → BF 按自己的流程构造 handler、注册路由并完成 Bootstrap
  → EE attach：完成适合此时安装的插件、定价及模块路由
  → 校验当前启用模块、路由分类和必需策略完整性
  → BF Start，开始监听和服务
```

回调有必要，是因为共享数据库和 core 由 BF 创建，而 BF 的 handler 又需要 EE 已构造的策略。仅把所有工作放在 `Bootstrap` 前拿不到资源；全放在其后又错过 handler 构造与旧 session 路由替换的时点。无需为此复制或全面拆分 BF 的初始化流程。

基线 `ConsoleAuthFactory` 的位置满足本批需求：配置、core、Router 以及控制台认证依赖已经存在，BF API 路由尚未注册。现已在该时点改用 `BeforeAPIRoutes` 调用 `app` 装配；BF 通过独立字段取得控制台 middleware 与 session 注册方法。

这个时点不代表 BF 所有资源都已完成初始化。当前 Sidekiq runner、tracing 等仍有后续步骤；若某个新增依赖需要它们，应依据真实顺序调整接点，不能把回调命名为“全部资源就绪”后默认可用。第一批采用 `BeforeAPIRoutes(context.Context, *BifrostHTTPServer) error`，仅装配层接收宿主；业务模块仍只接收所需依赖。类型化业务依赖如何传给 handler 留在后续批次确定。

模块自有 HTTP 接口由模块独立注册，`app` 显式调用。第二批在启动回调中注册身份、RBAC 和基础状态接口，仅接 BF common 链，由现有端点负责认证；四条 BF `/api/session/*` 由专用回调替换，同样只接 common 链。`AdditionalRoutes` 已删除。后续模块重写再把端点内通用认证/授权搬到公共薄中间件，不在接线迁移时改变业务规则。

attach 可以承担品牌路由、内容安全插件同步、国内定价等依赖已完成 BF 初始化且不必参与 BF handler 构造的工作。某项能力若实际需要更早参与 BF 初始化，应按其依赖移动，不把 attach 定成所有 EE 能力的统一入口。

`Start` 前仍可能有 BF 后台活动或初始化外连；本设计没有把它们全部推迟到监听之后。当前 main 在启动失败时退出进程，不能把它描述成必然留下常驻泄漏。错误清理按资源所有者补齐即可；同进程重试、通用幂等关闭等能力若有真实使用场景，再单独设计。

## 5. HTTP：公共薄 middleware 与真实路由模板

BF 管理接口沿用已有调用链：

```text
真实 BF Router 选中 handler 并保存模板
  → common middleware 保存稳定的 route template
  → EE 认证：验证此入口接受的凭据，取得身份
  → EE RBAC：按 HTTP method + 命中模板查询接口访问规则
  → 原 BF handler
```

权限表仍需要表达“某条 BF 接口要求什么权限”，这是跨项目接入的实际依赖。键必须使用 BF Router 本次命中的模板，例如 `GET + /api/providers/{provider}`，不能再拿原始 URL 做一次路径匹配。表查询只选择规则，不负责 URL 解码、路径参数匹配或 404/405 判断。

BF 现有 common middleware 会移除 Router 自己的模板键并写入稳定键，因此 EE 权限层应读取稳定键，并排在 common 之后。需要此模板的权限链若读不到模板，应按接线错误拒绝，不能回退到原始路径猜规则。EE 自有路由也接入必要的 common 链，然后在模块注册处显式选择公开、个人会话或某项权限要求。每条链的组装者要明确，避免重复认证、重复 telemetry 或误用可追加 slice。

### 入口不能一概按 `/api` 拦截

| 入口 | 认证与授权负责人 |
|---|---|
| BF 控制台管理接口 | EE 会话认证与该接口的权限规则；替换 OSS 控制台认证，不能两套叠加 |
| EE 自有业务接口 | 模块注册时声明要求，复用公共认证/RBAC middleware；业务对象校验留在 service |
| 登录、初始化、品牌公开读取 | 显式公开或初始化规则；仍保留各自需要的来源、部署令牌和输入校验 |
| 控制台 bootstrap、当前用户 | 个人会话入口，保留无角色或需要改密账号可读的基本信息，不强加 `Settings.View` |
| 推理、MCP、OAuth、VK 自服务 | 按具体协议保留原有认证链；控制台 Cookie 不替代协议凭据 |
| 限定用途临时令牌 | 单独的作用域、期限和来源规则；保留现有可降级条件，503 不转为令牌放行 |
| 控制台 WebSocket | 专门握手与连接期校验，见下文；推理 WebSocket 仍归原协议 |

某些 BF 协议路由有意不使用管理接口的通用 middleware 参数，不能声称一个公共 middleware 自动覆盖它们。它们需要明确分类并核对真实认证负责人；确需额外保护时，修改该入口的接线，而非绕到外层重新匹配 URL。

提取公共认证时还需保留各入口的凭据来源、同源校验及失败响应约定。当前不同入口的校验顺序并不完全相同，抽出公共函数不等于已经证明行为不变；若统一顺序会改变可见行为，应明确记录决定。

保留启动完整性检查，但只读取真实 Router 的注册信息，与当前启用模块的规则表核对，不生成第二个 Router。管理接口缺规则、规则指向不存在的活跃接口、冲突声明或入口归属不明应阻止启动。条件模块按启用状态校验，纯协议路由无需被迫拥有控制台权限码。

### RootGuard 的删除条件

真实命中模板只能用于已命中的 handler，不能独自解决未知 API 被 SPA 通配符接走、错误 method 返回 HTML 等问题。必须先在真实 Router 与 UI 兜底边界完成以下行为，再删除现有 `RootGuard` 和第二 matcher：

- 未知 API 返回 API 404，不返回前端 HTML。
- 已知 API 使用错误方法时保持约定的 405；CORS OPTIONS 按实际预检流程处理。
- 合法前端路径和静态资源仍可访问。
- 现有路径规范化拒绝行为，以及 HEAD、尾斜杠、编码路径、重复斜杠行为有明确保留或变更决定。

具体采用 NotFound、收窄 UI fallback 或其他小范围修改尚待实施核对；不在架构层提前承诺替换整个 UI 注册方式。这里可以有简单入口边界判断，不能重新建立一套管理接口路由匹配器。

## 6. 数据规则：在实际执行数据形成之后检查

接口权限回答“能否调用此操作”；敏感数据规则回答“能否对这些具体数据做这次操作”。例如允许编辑 provider，不代表可以将已保存的凭据发送到任意新地址。

```text
BF handler 解析输入
  → BF 处理默认值、保留标记并与当前状态合并
  → 注入的类型化规则检查 before / desired
  → BF 使用同一份获准数据保存、热更新或外连
  → BF 构造响应对象
  → 注入的类型化可见性规则产生允许返回的视图
  → BF 序列化
```

规则按资源族提供小接口，通过 handler 构造参数或其明确的构造选项注入。诸如 `AuthorizeUpdate(ctx, before, desired)` 只是职责示意，尚未确定实际 Go 签名；不同操作不必强行统一成一个万能策略接口。

BF 负责自己的解析与合并语义，EE 接入实现负责读取请求身份、调用 EE 业务规则并映射决定。稳定策略不捕获单个请求；请求上下文只携带身份、权限快照等小型事实，不再携带待执行策略函数。上下文在 BF 转换链中必须保持这些事实；已启用 EE 的必需策略缺失，应在启动检查时失败，不能落入 OSS 的可选默认行为。

检查必须位于该操作第一个相关副作用之前，不只是在数据库写入之前。例如更新 provider/MCP 可能触发发现模型或新建连接；配置修改可能先更新运行时再持久化。获准的 desired 必须就是实际执行的数据，不能检查后又按新的状态重新合并执行；沿用该操作必要的锁、版本或事务边界。

### 输入处理不能一删了之

当前 EE 存在对 BF 输入的二次解码、占位符恢复、合并和请求体改写。目标是将其中属于 BF 数据语义的部分收回 BF，随后删除 EE 的重复实现；删除前必须覆盖实际行为：

- 密钥及普通配置字段的保留标记都要保持原语义，不能只覆盖已有 BF secret helper 就宣布完整。
- 默认值、嵌套合并、清空与省略的区别仍由实际 handler 负责。
- 当前严格 JSON 校验中的重复字段、大小写等行为，要明确保留位置或记录有意变更。
- 旧 `auth_config` 等只读兼容投影与禁止修改规则使用专门配置接点，不混进一般权限检查。

## 7. 输出处理：序列化前投影，覆盖真实出口

把敏感字段投影从“handler 返回后再解析 JSON”迁到响应类型已确定、尚未序列化的位置。投影只改响应副本或独立 DTO，不能修改共享配置、存储对象或缓存中的原对象。

每个资源族都要核对列表、详情、嵌套响应和导出等真实出口；错误响应也可能包含敏感内容。当前输出适配还承担 `no-store`、错误清理、异常响应结构拒绝及部分响应头修正，类型化投影不会自动替代这些职责。应分别交给响应辅助函数、错误转换或保留的窄适配。

迁移以资源族为边界：新输入规则和输出保护已完整接线、覆盖真实行为后，删除对应旧 guard、上下文回调和 JSON 包装。尚未覆盖的保护明确保留为临时适配，并标明删除条件，不能因“已有公共 middleware”提前删除。

## 8. WebSocket、通知和原生插件

控制台 WebSocket 是长连接边界。握手成功后保存独立的会话/用户标识及连接所需依赖，不能在长期回调中捕获池化 `fasthttp.RequestCtx`。后续消息与 ping 写出时按连接生命周期重验会话；通知发送还要判断当前权限和受众。连接失效则关闭，消息不面向该用户则按消息规则跳过。

当前 BF 已有通知发布/可见性接点和 WS 写出前重验接点，可在其上改造依赖传递，无需再造通知系统。现有 WS 过滤仍以序列化字节为输入；若要彻底删除 EE 的消息 JSON 反解析，应补结构化事件投影接点，并保证校验与受保护写出之间的同步边界。不能仅把检查提前到广播遍历时，就宣称撤权后的写出窗口已受控。具体事件类型和接口签名仍待定。

内容安全继续使用 BF 原生推理插件流水线，共享同一业务检查能力供其他入口调用。保留缓存前检查、拒绝后不回退等既有行为。国内定价继续使用实际存储与模型目录；插件注册、配置同步和重载沿用已有 BF 能力，不通过控制台 middleware 实现。

## 9. 旧职责如何退出

| 当前职责 | 目标与删除条件 |
|---|---|
| `ConsoleAuthFactory` 顺带装配 identity / RBAC | 第二批已迁到启动回调，旧工厂及 provider 接口已删除；业务策略注入仍待后续调整 |
| 身份适配器持有其他模块的 `AdditionalRoutes` / `OwnsRoute` | 第二批已删除，各模块独立注册；真实的会话、初始化及兼容行为保留 |
| `VerifyRoutes` 同时建第二 matcher | 保留注册覆盖校验，删除 matcher 构造和请求期二次匹配 |
| `RootGuard` 模拟 API 404/405 | 真实 Router/UI 边界承担全部约定行为后删除 |
| EE 请求反解析、合并、回写 | BF 数据准备及类型化检查覆盖对应行为后逐项删除 |
| 请求上下文中的 policy 函数 | 稳定规则构造注入完成后删除；上下文保留请求事实 |
| handler 返回后整体 JSON 投影 | 类型化投影及错误、缓存等独立保护覆盖全部出口后逐项删除 |

以上是职责迁移，不是预先承诺删除整类或整文件。现有适配中有些业务能力仍然有效，需移到清楚的位置保留。

## 10. BF 最小改动面与待定项

| 位置 | 接入改动方向 |
|---|---|
| `server/server.go` | 保留 Bootstrap；明确启动回调与控制台链/session 替换接线；将必需策略传入 handler 构造；明确 OSS 默认路径 |
| `handlers/consolepolicy.go` 及已有调用点 | 将请求上下文函数改为稳定、类型明确的构造依赖；复用当前正确的副作用前接点，纠正时机不足的部分 |
| 各涉及敏感操作或敏感输出的 handler | 在合并后、首个相关副作用前检查；在序列化前投影；仅修改真实需要这些能力的资源族 |
| `handlers/notifications.go`、`handlers/websocket.go` | 复用现有通知规则与连接重验能力；按需要补充结构化消息投影 |
| Router 与 UI fallback 边界 | 建立 RootGuard 的替代行为；不统一更换所有 handler 的路由注册 API |

现有通用 middleware 和命中模板机制可以直接承接认证/RBAC 重组，这部分不要求批量改写 BF handler。类型化输入与输出接点则需要按资源逐项核实，不能提前承诺固定文件数、改动行数或一个 hook 覆盖全部语义。补丁评审要同时确认 EE 必需扩展完整，以及未安装扩展时 OSS 行为成立。

启动接入口与 session/自有路由分工已按前两批落地。具体待定项仍包括：类型化依赖传递；各资源族 before/desired/响应类型；API 404/405 与 UI 的实现方式；WS 结构化消息接口。具体实施阶段和测试安排归 [一期方案](../../workbench/cases/EE与上游接入重构/期1/方案v1.md)，不在本文件另设一套。

本稿依据源码阅读形成，各批实际验证记录见一期方案。后续整体验收必须包含实际 handler 的最小权限访问、敏感操作副作用时机、各类输出、会话撤销、无角色 bootstrap、临时令牌、WS、推理原认证、插件及定价行为。仅路由数量或 hash 一致，不能证明这些行为成立。
