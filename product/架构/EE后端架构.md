# EE 后端架构

[← 产品与技术文档](../README.md) · [BF 接入设计](EE与上游接入重设计.md) · [详细设计](../../workbench/cases/EE与上游接入重构/期1/方案v1.md)

更新：2026-09-29。重构起点为当前自有 `develop` 的 `9e78d3bdb73c850f103c93d7de498597c6ac5369`。

本文描述重构目标，不表示代码已经按此实现。第 1 节记录本轮讨论已经确定的方向；第 8 节的 auth/session 位置、普通 Store 接口与显式 GORM 事务已随第三批获准实施；其它模块细节仍是建议。本文替代原架构中由认证接口承担装配、将账号与会话集中到 identity 的目标约定；显式事务的规范已同步。历史验收记录仍描述当时版本。

## 1. 重构要解决什么

问题集中在调用关系：普通业务经由认证适配器注册，账号操作通过策略回调间接调用 RBAC，多个 Service 共用一份业务 core，辅助函数的名字隐藏了实际检查和写入。调整目录或删掉 Store 接口本身不能解决这些问题。

以下方向已在本轮讨论中确定：

| 决定 | 对实现的要求 |
|---|---|
| 在当前提交上重构整个 EE 后端 | 身份、权限、品牌、定价、内容安全和接入层都纳入审视；不预设某模块必须保持原实现 |
| usage 单独处理 | 不把 usage 分支现有实现作为设计约束，也不操作其分支、代码或数据 |
| 继续内嵌完整 BF | 复用 Bootstrap、HTTP Server、Router、推理链和运行时；不复制装配中心 |
| 可以合理修改 BF | 增加职责明确的装配、中间件和业务调用点；保留未启用扩展时的 OSS 行为 |
| 认证、授权有公共薄中间件 | 中间件读取请求身份、调用服务、拒绝或放行；业务规则在对应模块 |
| 账号、登录认证、会话分开 | 分为 account、auth、session；角色与权限归 rbac，不再共用 identity.core |
| 普通 Store 接口保留 | 接口表达真实数据能力，不用动作枚举、策略工厂和生命周期回调转发业务 |
| 业务入口显式组织操作 | 更新密码、撤销会话、记录事件分别调用；初始化直接分配管理员角色，删除账号直接清理角色关系 |
| 跨模块操作可以共用事务 | 业务入口决定提交范围；事务中不临时构造业务 Service 或选择业务策略 |
| 取消最后一个可用主管理员保护 | 去掉为此设置的计数、拒绝逻辑和策略钩子；其它未讨论的产品规则不由此自动取消 |
| 命名准确表达行为 | 从调用处读出查什么、检查什么、修改什么；不能用缩写或长函数名掩盖混合职责 |

现有表结构、API 和业务规则需要逐项核对。除明确取消的规则外，本稿以保持外部行为为迁移建议；额外改变单独列明。它不要求保留现有代码组织，也不要求为了凑“重写”丢掉清楚的实现。

## 2. 应用和运行时边界

EE 是独立 Go 模块和可执行程序，在一个进程内使用完整 BF HTTP 应用。

```text
EE main → app 装配 → BF Bootstrap / Start

控制台请求 → 共享 Router → 认证中间件 → 权限中间件 → Handler
                                                    ├─ EE Service → Store
                                                    └─ BF 原业务流程
                                                        → 必要的 EE 业务检查

推理请求 → BF 原协议认证与推理链 → EE 内容安全插件 → 检测服务
```

BF Server 负责 BF 组件的构建、持有、更新和生命周期。请求匹配以后，正常沿 Handler 和业务调用链执行。EE 无须为与其对称再造一个持有所有业务的 Server。

`app` 负责创建依赖、连接依赖、注册入口和释放资源。密码重置、角色分配、定价计算、安全配置更新等运行期业务由所属模块负责。

共享数据库、模型目录、BF Client 和 Server 由原创建者管理。EE 借用资源，不重复关闭。EE 自己创建的后台任务、检测器资源由创建方登记并释放。启动中途失败也走清理路径。

## 3. 业务模块边界

| 模块 | 拥有的业务 | 主要入口与协作 |
|---|---|---|
| `account` | 账号资料、状态、密码、初始化状态、离线恢复、密码事件 | HTTP/CLI 调用业务操作；显式调用会话撤销和角色清理/分配 |
| `auth` | 登录流程、请求身份验证 | 读取账号凭据和会话；验证后返回身份；提供认证中间件 |
| `session` | 会话和一次性票据的存储、签发、失效、消费、清理 | 被登录、退出、账号操作和 WS 接入调用；不决定账号角色或路由权限 |
| `rbac` | 角色、权限目录、角色分配、权限计算与判断 | 管理 API 和权限中间件共同调用；不承包装配和其它模块的路由 |
| `branding` | 品牌设置、图片有效性、资源选择 | 公开读取及受保护的修改接口 |
| `pricing` | 国内厂商识别、价格转换、覆盖同步 | 启动时调用；显式区分持久化覆盖和本节点内存目录更新 |
| `guardrails` | 检测规则、检测执行、配置更新、运行配置快照 | 配置 API 与 BF 插件各有入口，共用规则和运行状态 |

`auth` 读取凭据不意味着依赖整个 `AccountService`。`session` 保存 account ID 不意味着负责账号状态或密码校验。`rbac` 提供管理接口，是因为角色和角色分配本身需要管理；中间件使用这些数据判断请求权限。

本轮不建立独立 audit 模块承接所有副作用。已有密码事件仍归 account。以后扩展管理审计时按明确需求设计。

### 模块间调用

业务操作由最能说明用户意图的服务负责，例如：

```text
account.ResetPassword
  → 校验操作者和目标账号
  → 计算密码哈希
  → 开启事务
      复核当前会话、权限及目标状态
      AccountStore.UpdatePassword
      session.RevokeAccountSessions
      AccountStore.InsertPasswordEvent
  → 提交
```

`UpdatePassword` 可以一起写密码哈希、认证版本和强制改密标记；撤销会话、记录事件由调用者明确列出。删除账号的 Store 只删除账号记录，清理会话、票据和角色关系在业务入口可见。

上图是重置成功路径。预检通过才计算哈希；需要留痕的业务失败仍进入相应事务分支，先保存失败事件，再返回错误，不能在预检时全部直接结束。

各模块的 Store 只写自己拥有的数据，跨模块写入调用其公开能力。例如 auth.Login 通过 account Store 更新最近登录时间、通过 session 签发会话，不直接写两者的表。跨模块查询可以针对具体用途提供小型只读结果，例如认证一次读取账号与会话的联合结果；不能因为拆模块把这次一致读取变成两个没有约束的查询。

## 4. HTTP、中间件和 BF 接入

公共认证与权限中间件分别放在所属模块的 HTTP 入口包中，供 EE 和 BF 管理接口复用。公共意指应用内共享，不要求建立万能的 `pkg/middleware` 包。

Handler 负责解码、协议约束、调用服务和响应映射。认证中间件检查 Cookie、来源等 HTTP 事实并调用 auth；权限中间件调用 rbac。会话有效性、强制改密状态和权限计算不能在各 Handler 重复实现。

中间件负责入口准入，事务内复核阻止检查后状态已变化的操作。复核调用同一业务方法，不复制权限规则。需要记录失败事件的重置密码接口有明确例外，见详细设计。

BF 管理接口使用已有通用中间件入口；共享链按真实匹配的路由模板查权限。EE 不再实现第二个路径匹配器，也不逐个 Handler 手写相同认证逻辑。推理、OAuth、临时令牌和 WS 保持各自协议认证。

涉及具体业务数据时，BF Handler 先完成解析、默认值、合并和保留字段恢复，再调用注入的 EE 检查，获准后才能写库、外连或改变运行时。响应在序列化前按类型投影可见字段。接入代码转换类型、调用业务能力，不从外层反复解析 JSON、修改请求体再猜测输出。

新增 EE 模块自行创建服务、注册路由、声明访问要求，不改认证适配器，也不借“注册会话接口”接入。具体调用点和特殊协议见 [BF 接入设计](EE与上游接入重设计.md)。

## 5. 启动顺序及原因

保留 BF Bootstrap。依赖 BF 内部资源或路由注册时点的步骤通过对应回调衔接；其余步骤在 EE 启动前或 attach 阶段直接执行。

| 时点 | 做什么 | 为什么放这里 |
|---|---|---|
| BF Bootstrap 前 | 读取 EE 部署配置，创建不依赖 BF 的工具对象，配置回调 | 错误配置尽早失败；回调在 BF 到达相关阶段前可用 |
| BF 数据库就绪、管理路由注册前 | 迁移 EE 表；创建 Store 和服务；构造中间件 | Store 需要数据库，中间件需要服务，路由需要中间件 |
| BF 注册管理接口时 | 接中间件、替换必要的旧会话入口、注入业务检查 | 只有与注册时点相关的事情在这里完成 |
| BF Client/模型目录就绪后 | 装配安全和定价；注册其它 EE 接口；完成启动同步 | 分别需要实际 BF 调用能力和模型目录，不必借认证工厂启动 |
| 接收请求前 | 核对路由覆盖、重复注册和依赖，装好插件及初始配置 | 避免半装配状态对外运行 |

这是依赖顺序，不要求按表格数量拆分 BF 阶段函数。若 BF 组件在 Bootstrap 内提前执行依赖 EE 的任务，应核对该调用点的先后关系，不因此重写整套 Bootstrap。

## 6. 更新和生命周期

| 数据/运行状态 | 更新责任 |
|---|---|
| BF Provider、插件列表、配置及运行时 | 沿用 BF 的完整更新链；EE 不绕过它只改表 |
| 账号、会话和角色 | 数据库业务操作；后续请求重新验证状态和权限 |
| 内容安全配置 | 配置服务构建新快照、持久化后发布；单个请求使用同一快照 |
| 国内定价 | 当前功能为启动同步；本轮不顺带新增定价热更新产品功能 |
| 品牌设置 | 业务更新存储；资源读取遵守已有版本标识和缓存语义 |

EE 各模块按数据性质更新，不要求全部挂在同一个 EE Server 上。数据库事务只保证数据库操作的一致性；定价的“数据库→内存目录”、安全的“数据库→快照发布”须分别规定失败语义。

## 7. 可读性规则

- 一条业务流程能在具名入口顺着读完。辅助函数承担明确的查询、校验、计算或写入，不隐藏另一套业务编排。
- 保留职责明确的接口；删除 `AccountAction → AccountPolicy → RBAC permission` 这样的重复翻译。
- Store 执行持久化，不创建 Service、不选择策略、不注册路由。
- 构造函数列出实际依赖。密码哈希器、并发限制可共享实例，多种业务不共享 core。
- `Login`、`CreateAccount` 已经足够清楚；`actor`、`current`、`Prepare` 按实际行为拆分或改名。
- 同一字段组的持久化可以集中，跨职责的动作由入口组合。提取函数服务于规则一致和阅读，不为消灭几行顺序相似的调用。
- HTTP DTO 只暴露该接口的字段；账号凭据、数据库行和公开响应不因省一个结构而混用。

## 8. 目录和事务

用户已确认 auth/session 放在 `ee/internal/` 下并开始编写新模块，采用普通 Store 接口和显式事务；其余模块的具体落法仍按批讨论。

```text
ee/cmd/bifrost-http/          入口及恢复命令
ee/internal/app/             装配和资源生命周期
ee/internal/account/         账号、密码、初始化/恢复、事件
ee/internal/auth/            登录与身份验证
ee/internal/session/         会话和票据
ee/internal/rbac/            角色与权限
ee/internal/branding/        品牌业务
ee/internal/pricing/         价格规则和同步
ee/internal/guardrails/      检测、配置服务和运行快照
ee/internal/host/            BF 类型转换及具体接入
```

模块根包放业务操作和使用方需要的 Store 接口，`http/` 放 Handler 和中间件，`persistence/` 放数据库实现。真实存在的插件、检测器和 BF 接入按职责另放。小接口、参数、错误就近放，不为每个概念建文件或空子包。

沿用目录名不代表沿用调用关系。详细设计逐项说明旧入口移到哪里、删掉什么间接层，用调用链核对收益。

事务采用显式 `*gorm.DB`：业务入口开启事务，跨模块方法接收同一事务，Store 通过普通接口注入并绑定本次副本。SQL 和数据库行仍留在存储实现；不修改共享 Store，不创建事务版 Service。

[编码规范](../../workbench/规范/项目/编码规范.md)已允许业务服务显式传递 GORM 事务，SQL 与数据库行仍只在持久化包。第三批 auth/session 按此落地，旧账号/RBAC 的事务策略工厂留待它们迁移时删除。
