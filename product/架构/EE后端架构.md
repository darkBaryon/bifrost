# EE 后端架构

[← 产品与技术文档](../README.md) · [编码规范](../../workbench/规范/项目/编码规范.md)

**已确认，2026-09-11（账号认证段 2026-09-12 更新）。** EE 自有后端采用 **feature-first：按业务能力分模块，模块内部保留分层**。本文约定整体架构；现有入口、装配和品牌模块已完成目录迁移，账号认证后端已于 2026-09-12 通过 Gate 2（仅后端：账号、凭据、会话、密码事件与管理路由接管；认证页面、项目操作日志页面与完整 RBAC 后续交付），其余示例模块按需开发。

## 1. 应用边界

EE 是拥有独立 Go 模块、可执行入口和自有业务的后端应用，在同一进程中内嵌完整的 Bifrost HTTP 应用，复用其网关能力。

```text
HTTP Server
  └─ EE 外层 Handler（按需）
       └─ Bifrost Handler 链
            └─ 共享 Router
                 ├─ Bifrost 功能 Handler → 上游实现
                 └─ EE 功能 Handler → EE 业务服务

Bifrost 插件链 → EE 插件适配 → EE 业务服务
```

当前先由EE注入ConsoleAuthFactory，再执行上游Bootstrap（在管理路由注册前装配身份服务），随后EE attach装配品牌并调用上游Start。双方共享Server、Router和配置数据库，推理链保持宿主实现。identity及宿主认证适配已实现并通过Gate 2；认证页面、项目日志页面和完整RBAC后续开发。验收依据见[Gate2验收摘要2](../../workbench/evidence/账号认证-期1-Gate2验收摘要2.md)与[验收记录](../../workbench/cases/账号认证/期1/验收记录.md)，本文架构约定本身不作为功能已交付的证据。

图中的“EE 外层 Handler”包装整个请求链，“EE 功能 Handler”处理具体接口。Bifrost 的 Handler 链内嵌在 EE 中，双方通过共享 Router 分发请求。调整 EE 的业务组织时，继续复用上游的协议适配、Provider、推理编排与治理实现。

## 2. 为什么按业务模块组织

一个业务的模型、规则及入口放在同一模块，让功能变更集中、业务边界清晰，并支持 HTTP、插件和后台任务复用规则。模块按业务能力划分，不与页面、表或插件一一对应。

例如品牌设置主要是配置管理，账号认证涉及凭据与会话，护栏同时有管理接口和实时检测。与将所有功能按层集中到 `handlers/`、`services/`、`repositories/` 相比，按业务组织更容易看清一个功能包含什么、修改会影响哪里。

模块内部保留职责分层；公共技术能力按实际需要复用，简单功能不强行拆层，也不提前建立空包或通用框架。

## 3. 总体布局

```text
ee/
├── cmd/bifrost-http/       程序入口
├── internal/
│   ├── app/               配置、依赖装配、生命周期
│   ├── identity/          账号、凭据、会话
│   ├── rbac/              角色、权限目录、账号角色关系
│   ├── branding/          品牌设置
│   ├── audit/             管理审计
│   ├── guardrails/        内容护栏
│   └── bifrost/           宿主与上游能力集成
├── ui/                    自有前端覆盖层
├── scripts/
├── go.mod
└── Makefile
```

现有代码已落在 `cmd/bifrost-http/`、`internal/app/`、`internal/branding/`、`internal/identity/`及`internal/bifrost/`；完整角色权限等模块后续按需建立。前端继续放在 `ee/ui/`，本次保留上游 UI 覆盖机制，构建产物嵌入 `cmd/bifrost-http/ui/`。

## 4. 模块内部的职责

以账号认证为例，模块根包承载账号、凭据与会话规则，`http/` 处理请求与响应，`persistence/` 实现存储与事务。这是职责和依赖边界，**不是每个模块必须照建的文件清单**。

各模块按需要选择入口和适配实现，职责划分如下：

| 位置 | 职责 |
|---|---|
| 模块根包 | 业务模型、服务、规则、错误及所需接口 |
| `http/` | 解析请求、调用服务、映射 HTTP 响应 |
| `plugin/` | 接入 Bifrost 钩子，转换输入与处理结果 |
| `worker/` | 执行后台任务，调用业务服务 |
| `persistence/` | 存储、表映射、迁移与事务实现 |
| `providers/` | 外部服务的协议适配 |

业务规则由模块内函数或服务负责，入口和存储实现各司其职。业务模型、HTTP DTO 与数据库模型按各自用途定义，避免直接暴露内部字段。同一包内优先将需要一起理解的操作、类型、接口和错误放在一起，有明确阅读与维护收益后再拆文件。简单模块无需为这些概念逐一建文件，也不要求具备所有子包；具体遵循 [编码规范](../../workbench/规范/项目/编码规范.md#文件组织以阅读为先)。

例如，Handler 将停用账号的请求交给业务服务，由服务检查账号保护规则、安排状态更新与会话撤销，存储实现负责执行查询和事务。这样同一操作由 HTTP 或后台任务触发时，都能遵守相同规则。

## 5. 依赖与协作

```text
http / plugin / worker / persistence / providers → 业务根包
app → 业务服务 + 具体实现（构造函数注入）
```

### 模块内部

简单配置功能可由 HTTP 直接调用同模块的具体存储，独立规则用普通函数表达，不强制增加转发用的 Service/Repository。品牌换图按此组织；出现需要复用的业务流程时再引入服务，HTTP 仍不直接操作数据库或跨模块改表。

业务根包使用标准 `context.Context`、自有类型和接口，不反向导入 HTTP、插件或存储等适配子包。fasthttp、GORM、Bifrost 及外部 SDK 的具体类型留在适配实现中。

接口由使用方按实际需要定义，`app` 通过构造函数将具体实现传入业务服务。服务不从全局 Server、Config 或服务容器取依赖，也不建立万能 Repository 或 BaseService。

### 模块之间

每个模块拥有自己的数据和规则，通过公开能力和窄接口协作，不直接改对方的表，避免双向依赖。例如 RBAC 需要确认账号是否存在时，只依赖账号查询能力，由装配连接实现。跨模块流程由明确的业务服务负责，`app` 只做装配。

`identity` 管账号、凭据与会话，`rbac` 管角色、权限目录与账号角色关系，两者分别交付。认证成功后，仍需检查具体操作权限。控制台账号与 VK、最终调用用户保持独立概念。

### 事务

业务服务决定哪些操作必须一起成功或失败，存储实现保证它们在同一事务中执行，不向业务层传递 `*gorm.DB`。例如停用账号与撤销会话需要作为完整操作处理，不能由 Handler 连续调用两个各自提交的方法来代替。

调用上游存储方法前，要核实它使用的事务连接与提交边界；复用方法不意味着它会自动加入 EE 的事务。

## 6. 插件与普通业务

需要在 Bifrost 请求、响应、工具执行或观测阶段参与处理时，使用插件入口。例如护栏的管理接口放在 `guardrails/http/`，实时检测入口放在 `guardrails/plugin/`，共同调用模块内的业务服务。

因此，一个功能可以同时包含普通接口、插件和 Worker。是否写插件取决于它从哪里被调用；业务归属仍由它负责的能力决定。多个入口可以复用同一服务，也可以调用模块内职责不同的服务，无需集中成一个巨大的 Service。

插件负责把业务结果转换为放行、修改或短路行为；普通插件 error 不等于阻断请求。集成时核对钩子顺序、重试/回退、缓存及流式生命周期，不能假设一次请求只调用一次。

流内容状态由有容量限制和清理责任的管理器持有，BifrostContext 只保存小型句柄；异步任务不能持有已归还对象池的请求对象。

## 7. 与 Bifrost 的协作边界

- **集成归位**：`internal/bifrost/` 负责宿主、管理路由、会话兼容等跨功能接入；具体业务插件留在所属模块。
- **复用完整操作**：保留上游的存储与运行状态更新链。例如 Provider 修改还涉及内存配置、Core 和模型发现，不能只写表；审计也不能只凭 HTTP 状态判断变更结果。
- **按缺口扩展**：先评估已有数据库、迁移、日志、向量库、插件与 Sidekiq，再增加实现；不重复包装整套 SDK 或另建基础设施。
- **生命周期统一协调**：共享资源由创建者管理，EE 的初始化失败清理和关闭流程须与上游协调，避免重复关闭共享连接。
- **核实接入影响**：扩展前检查实际调用链。外层 Handler 不能覆盖所有业务接入需求；`IsEnterprise` 还影响治理插件，不能作为单独替换认证的开关。

## 8. 适用与维护

新增 EE 功能遵守本文，已有功能随明确任务逐步调整。目录迁移本身不改变 API、表名、迁移 ID、认证方式或配置契约。
