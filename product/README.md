- 看开发候选与先后关系：[路线图](路线图.md)。其中的历史路径和讨论背景不代表功能已实现。
- 了解 Bifrost 现有代码：[中文参考资料](docs-zh/README.md)。它保留源码导读、阅读笔记、开发和部署经验，不是一套额外的需求工作流程。

## 文档怎么放

```text
product/
  竞品调研/             跨需求共用的市场、竞品和能力背景
  需求/<需求名称>/      该需求的竞品研究、总结和产品方案
  路线图.md             产品优先级，引用具体需求
  docs-zh/              项目参考资料与已有源码学习笔记
```

一个产品需求先研究竞品实际行为，再总结差异，最后形成我们的产品方案。有开源实现且需要核实机制时，clone 后记录仓库和 commit；未验证的内容明确标注。小需求可以一篇文档完成，大需求按调研、源码证据、产品方案分开，不为凑目录强制生成多篇。

产品文档说明用户能做什么、业务规则与验收标准；技术实现由 Workbench 引用产品方案后设计。两者各自维护，不建立统一状态机，不重复复制产品正文。

## 功能 worktree 的文档怎么合并

文档随所在的 Git 分支提交与合并，worktree 只是不同分支的工作目录。

1. 在功能工作区先检查并保存自己的改动，再合入最新 `develop`，同步这次目录调整。仍在运行其他开发会话时，先交接，不由主工作区强行整理它。
2. 已有文档的修改随 Git 重命名合并；旧路径新增文件须人工放到上面的对应目录。权限与品牌调研已被主树收录过副本，应逐段比较后保留双方有效增量，不能整份覆盖，也不要重新建立根目录 `docs-zh/`。
3. 每个需求维护自己的 `product/需求/<需求名称>/` 和 Workbench case。公共路线图、README 等共享文件发生冲突时按内容合并，不统一选择一方。
4. Workbench 的索引和导航属于生成物。合并源文档后运行 `python3 workbench/tools/build_views.py`，再运行 `--check`；不要手工拼接生成内容。需要看站点时再运行 `build_site.py`。
5. 审查通过后把功能分支合入 `develop`，产品文档、工程记录和实现一起整合。若只交付文档，先做独立的文档提交，再选择性合入该提交，避免带入未审查的业务代码。
