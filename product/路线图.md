## 一、先明确三种顺序

- **产品优先级**：哪个问题最先需要解决。当前首先是多人能安全共用控制台。
- **开发依赖**：哪些约定和能力没准备好，后续功能就无法可靠接入。
- **交付顺序**：哪些功能必须一起验收。开发可以并行，不代表未接真实权限的页面已经可以交付。

“权限先于审计”的准确含义：先确定可靠的用户身份、角色与数据归属，再交付能按人追责的审计。不是必须等所有高级权限功能完工，审计才能写第一行代码。

## 二、推荐主线：权限 → 审计，SSO 可在中途分出去

### M1a：用户、基础角色与数据归属（B2，当前最高优先级）

先确定产品问题：有哪些角色，各自能做什么、看什么；哪些资源全局共享，哪些属于团队。

建议首版采用超管、团队管理员、只读角色，明确只读角色的数据范围。支持独立账号、登录、停用、会话失效、用户与团队绑定；管理接口执行权限检查；列表、详情、统计、导出统一遵守团队可见范围。

**验收：** 两个人用自己的账号操作；只读人员不能修改；团队管理员不能查看其他团队的数据；停用账号后不能继续使用旧会话；原有 VK、预算、限流和推理调用仍可用。

暂不做自定义角色设计器、复杂组织层级和所有企业 IdP。团队管理员是否有权修改预算等业务规则必须先明确。

### M1b：管理操作审计（B1，在身份权限约定稳定后可并行开发，完整验收依赖 M1a）

产品需求以[审计功能调研与需求建议](需求/管理操作审计/产品调研.md)为讨论依据，不沿用旧方案“只记 HTTP 操作”的范围假设。

首版候选：关键配置变更、登录与敏感操作，操作人/对象/时间/结果，可读变更详情、检索、基础导出、查看权限和保留规则。预算、权限等关键非敏感值应能解释前后变化；凭据不展示秘密内容。

**可提前开发：** 在身份和事件约定已明确后，开发事件查询、页面、选定业务动作采集；测试数据用于开发，不能替代真实账号联调。

**验收：** 用真实账号修改一个团队预算，审计能显示谁改了什么；无权限人员不能查询；新增用户、停用用户、授权变更也纳入确认的覆盖清单。正式启用时才开始记录，不承诺补出开发期间未采集的历史。

### B3：企业 SSO（条件支线）

依赖稳定的用户 ID、角色和团队映射、账号停用与会话规则。它是另一种登录方式，不能自己再建一套用户和权限。

**可与审计并行：** 用户模型稳定后，选择一个实际需要的 IdP 接入；登录、角色映射、停用事件接入审计。完整验收依赖 B2 的真实权限和会话行为，不必等审计全部页面完成才开发 SSO。

有强制统一身份要求的客户，把 B3 并入上线门槛；否则可后置。不要先开放未经角色映射的新用户进入控制台。

## 三、可并行支线与依赖表

| 功能 | 优先级 / 触发条件 | 最早可以开始什么 | 必须等什么才能完整交付 | 并行判断 |
|---|---|---|---|---|
| B2 用户与基础权限 | P0 主线 | 现在先定义角色和资源归属，再实现 | 权限、账号停用、数据隔离的联调验收 | 先行，其他控制面功能依赖其约定 |
| B1 管理审计 | P0 | 现在讨论功能；身份/事件约定稳定后开发 | 真实身份、资源可见范围、关键业务变更信息 | 与 B2 后半段、SSO 可部分并行 |
| B3 SSO | P1；强制企业登录时 P0 | 现在准备 IdP；用户/角色映射约定稳定后开发 | 用户、会话、停用与真实授权能力 | 可与审计并行 |
| B4 官方定价与人民币 | P1；费用错误影响使用时提前 | 现在确定覆盖模型、计价与货币规则，准备价格资料 | 费用展示与预算扣减一致；管理页受权限保护；定价变更审计可接入 | 可与 B2 独立推进核心功能 |
| B5 离线部署 | P1；断网交付时 P0 | 现在盘点离线资源、安装/更新流程 | 对最终版本做断网安装、升级、重启与恢复验收 | 前期基本独立，最终包后汇总 |
| B8b 备份恢复 | 基础随交付 | 与 B5 一起准备恢复方案 | 用户/审计等表确定后验证一致备份、凭据保护和恢复 | 与 B5 合并一条交付支线 |

| A3 国内观测导出 | P2；客户指定日志平台时提前 | 确认 trace/日志字段与目标平台后 | 导出可用、数据范围明确、管理配置受权限保护 | 推理日志导出可独立；审计导出需等审计事件稳定 |
| B8a 告警 | P2；运维需求触发 | 先做已有预算/错误率告警和单一通知渠道 | 对应指标源、阈值、接收人及权限规则 | 基础通知可并行；审计/护栏告警等对应事件源 |
| B1b 高级审计 | P2；留存存证要求时提前 | 可提前确认归档、完整性和保存要求 | 基础审计事件与权限稳定 | 依赖 B1；不能抢先定义另一套审计模型 |
| B7 事后审查 | P2 | A1 规则和检测结果稳定后做复核流程 | A1 检测后端、可补检的日志内容、审查角色与可见范围 | 通常后置；没有留存正文就不能承诺补检 |
| B6 集群 | P2；高可用要求或容量触发 | 需求调查、技术可行性可提前 | 配置同步、身份/策略生效、预算一致性、故障恢复与升级验证 | 与用户/预算/配置改造耦合高，不适合直接独立分支一路写完 |
| B8c 品牌定制 | 对外交付前 | 现在可确认名称、Logo、页面品牌范围 | 与最终 UI 构建整合 | 较独立；避免与其他人同时改 UI 覆盖生成脚本 |
| A2 长期记忆、会话状态 | 暂缓 | 只确认有没有真实场景 | 可信最终用户身份、作用域、删除与隔离要求 | 不为了并行而启动 |
| B8d License | 暂缓 | 商业模式明确后定义产品规则 | 授权与离线策略、失败行为 | 不阻塞内部功能验证 |
| 钉钉/飞书薄适配器 | 有需求时独立交付 | 消息转发、有限历史、现有 VK 调用 | 若承诺按人治理，需要可信最终用户身份；不是控制台账号直接复用 | 基础转发可独立；完整助手另立产品 |

**重要区别：** A1 按 VK 检测并不需要先知道某个员工是谁；而 B1 要按管理员追责，必须可靠识别控制台用户。两者不能套用同一条身份依赖。

## 四、怎样安排并行开发

### 4.1 开工前先统一少量约定

不再建一个大而全的 infra 项目。先由主线负责以下公共基础，避免各支线自行发明：

1. 用户唯一标识、角色、团队归属与账号生命周期；全局和团队资源的边界。
2. 功能需要的权限名称、真实操作人取得方式，以及未来审计的基本事件信息。
3. 费用与预算的货币口径：B4 改货币不改变 B2 的资源归属，B1 记录金额时携带当时币种。
4. 公共迁移与构建约定：M0 两项技术债先由一个负责人处理，后续功能遵循同一方式。

契约稳定不要求全部业务代码写完；但纯口头约定或各自 Mock 不算最终集成验证。

### 4.2 当前选定三个独立任务

用户已选择：**价格、用户权限、Logo 品牌页面**。各自一个功能分支和 worktree，做完后独立验收、合入整合主分支；不要求开发者接着做同类任务，也不默认做完权限就开始审计。

| 任务 | 当前范围起点 | 尚需明确 |
|---|---|---|
| 价格 | 检查现有官方模型定价与覆盖能力，优先补实际使用模型的缺价/错误 | 厂商与模型范围；是否需要人民币预算，不能默认扩大为计费平台 |
| 用户权限 | 定义角色、账号与团队可见范围，再实施多用户与基础权限 | 权限矩阵、账号生命周期与团队预算管理规则 |
| Logo | 用户在了解现有 Branding 占位页后表示可以做，先明确该页的产品范围 | 固定替换资源还是可上传/重置的品牌页；Logo 素材与产品名待提供 |

整合主工作区只用于整理基线与合并，不承载这三个功能的实施。审计需求保留待规划，等身份权限约定明确后再由用户选取。

### 4.3 可以并行写，但不能并行随意改公共入口

- 每条功能线使用独立分支/工作目录、端口和测试数据；不共用会被迁移或清理的 config.db，不互相清理生成目录。
- 用户/权限、公共迁移、启动装配、共享导航、UI 覆盖脚本、构建脚本由明确负责人整合。涉及同一文件的改动先约定，不让多个会话各改一套。
- 共享基础形成可用提交后，各分支引用同一基线；合并时统一迁移编号、权限点和导航。
- 先集成公共基础与身份权限，再接审计/SSO；独立的检测和定价核心可以先合并，但管理入口开放前必须完成授权验证。
- 每条线自己通过测试不等于整体通过：还要验证停用账号、跨团队可见性、预算换算、配置变更审计及恢复后的状态。

## 五、交付里程碑与暂不承诺的工期

保留 M0 已交付事实。M1 改为先后明确的 M1a 用户权限、M1b 审计；M2 国内定价/部署、M3 内容安全保留原功能名称，但不再表示必须等 M1 全完才能开工。

| 里程碑 | 用户能得到什么 | 退出条件 |
|---|---|---|
| M0 已交付 | 自研功能可接入上游 | 已有 Gate 2，不重做 |
| M1a 用户权限 | 多人安全使用控制台 | 独立账号、角色和团队隔离可验收 |
| M1b 基础审计 | 能追查真实人员做过的关键管理操作 | 真实身份、可读变化、查询权限及确认的导出/留存能力 |
| M2 国内交付 | 覆盖选定模型的准确费用和可复现部署 | 货币/预算一致，目标环境安装升级恢复通过 |
| M3 内容安全 | 所选调用场景有明确检测策略 | 真实服务、支持协议、流式、超时与拒绝行为验收 |
| B3 条件交付 | 使用企业账号进入同一套权限体系 | 登录、组映射、离职失效、会话与审计联调 |

**原来的 5–8 周 / 9–14 周估算不再作为当前排期依据。** 用户权限和审计功能尚未定范围，人民币也可能涉及账务口径；不能沿用旧的缩减范围估算，更不能按会话数直接除工期。范围明确后按功能拆任务，分别估算开发、外部条件等待和集成验收时间。

可并行的准备工作不保证并行上线。若客户要求强制 SSO、内容检测、断网或高可用，相关能力须作为该客户上线前置条件；不能为了沿用默认顺序而删掉要求。
